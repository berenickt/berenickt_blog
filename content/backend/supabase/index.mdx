## 1. Supabase란?

**PostgreSQL을 중심으로 백엔드에 필요한 기능을 한 번에 제공하는 오픈소스 플랫폼** 이다.
흔히 "Firebase의 오픈소스 대안"이라고 소개된다.

서버를 직접 만들지 않아도, 프론트엔드에서 바로 다음 기능을 쓸 수 있다.

| 기능               | 하는 일                                                                       |
| ------------------ | ----------------------------------------------------------------------------- |
| **Database**       | 프로젝트마다 전용 PostgreSQL DB 제공. 테이블 에디터, SQL 에디터 내장          |
| **자동 API**       | 테이블을 만들면 REST API(PostgREST)와 GraphQL API가 **자동으로** 생성됨       |
| **Auth**           | 이메일·비밀번호, 매직 링크, 소셜 로그인(Google, GitHub, 카카오 등), 전화번호, 익명 로그인, SSO |
| **Storage**        | 이미지·파일 업로드와 저장, 이미지 리사이즈, 권한 관리                         |
| **Realtime**       | DB 변경 사항 실시간 구독, 채팅용 브로드캐스트, 접속자 표시(Presence)          |
| **Edge Functions** | 서버 코드를 실행하는 서버리스 함수 (TypeScript, Deno 런타임)                  |
| **Vector**         | pgvector로 AI 임베딩 저장·의미 검색                                           |
| **Cron · Queues**  | 예약 작업(pg_cron), 메시지 큐(pgmq)                                           |

> 💡 핵심은 **"결국 그냥 PostgreSQL"** 이라는 점이다.
> 인증, 권한, 스토리지 메타데이터까지 모두 PostgreSQL 안에 있기 때문에, SQL로 모든 것을 다룰 수 있고 언제든 다른 PostgreSQL로 옮길 수 있다.

cf. PostgreSQL 자체는 [PostgreSQL](/backend/postgresql), DB 종류 비교는 [데이터베이스 종류](/backend/database-type) 참고

## 2. 동작 구조

```
브라우저 / 앱
   │  supabase-js (publishable key + 로그인한 사용자 토큰)
   ▼
Supabase API (PostgREST · Auth · Storage · Realtime)
   │  요청한 사용자 정보로 RLS 정책 검사
   ▼
PostgreSQL
```

- 클라이언트가 **DB에 거의 직접 접근** 하는 구조다. 그래서 별도의 백엔드 서버 없이도 CRUD를 만들 수 있다.
- 대신 "아무나 DB를 읽고 쓰면 어떡하지?"라는 문제가 생기는데, 이를 막는 것이 **RLS(Row Level Security)** 다. (4장)

## 3. 시작하기

### 3.1 프로젝트 생성과 키

1. [supabase.com](https://supabase.com/)에서 프로젝트 생성 (리전은 사용자와 가까운 곳, e.g. 서울 `ap-northeast-2`)
2. 대시보드 **Settings → API Keys** 에서 키 확인

| 키                                   | 쓰는 곳                 | 권한                                       |
| ------------------------------------ | ----------------------- | ------------------------------------------ |
| **Publishable key** (`sb_publishable_...`) | 브라우저·앱 (공개 가능) | RLS 정책이 허용하는 만큼만                 |
| **Secret key** (`sb_secret_...`)     | 서버에서만              | **RLS를 무시** 하는 관리자 권한            |

- 예전 이름은 각각 `anon` key, `service_role` key 다. 지금은 새 키 체계로 옮기는 중이며, 두 방식이 한동안 함께 동작한다.
- ⚠️ **Secret key(service_role)는 절대 프론트엔드 코드나 `NEXT_PUBLIC_` 환경 변수에 넣지 말자.** 노출되면 DB 전체가 열린다.

### 3.2 클라이언트에서 사용하기

```bash
npm install @supabase/supabase-js
```

```ts
import { createClient } from '@supabase/supabase-js'

const supabase = createClient(
  import.meta.env.VITE_SUPABASE_URL,
  import.meta.env.VITE_SUPABASE_PUBLISHABLE_KEY,
)

// 조회 : SELECT id, title FROM posts WHERE published = true ORDER BY created_at DESC
const { data, error } = await supabase
  .from('posts')
  .select('id, title, author:profiles(name)') // 외래 키로 연결된 테이블도 함께
  .eq('published', true)
  .order('created_at', { ascending: false })

// 생성
await supabase.from('posts').insert({ title: '첫 글', published: true })

// 수정 · 삭제
await supabase.from('posts').update({ title: '수정' }).eq('id', 1)
await supabase.from('posts').delete().eq('id', 1)
```

- 에러가 나도 예외를 던지지 않고 `error`에 담아 반환하므로, **`error`를 꼭 확인** 하자.

### 3.3 타입 생성

```bash
npx supabase gen types typescript --project-id <프로젝트ID> > database.types.ts
```

```ts
import type { Database } from './database.types'
const supabase = createClient<Database>(url, key)
// → .from('posts')의 컬럼 이름과 타입이 자동 완성된다
```

## 4. RLS (Row Level Security) ⭐

Supabase를 쓸 때 **가장 중요한 개념** 이다.
RLS는 PostgreSQL 기능으로, **"이 사용자는 이 테이블의 어떤 행을 읽고 쓸 수 있는가"를 DB가 직접 검사** 한다.

```sql
-- 1. RLS 켜기 (켜는 순간 정책이 없으면 아무것도 못 읽는다)
alter table posts enable row level security;

-- 2. 공개된 글은 누구나 읽을 수 있다
create policy "공개 글 읽기" on posts
  for select using (published = true);

-- 3. 로그인한 사용자는 자기 글만 작성할 수 있다
create policy "본인 글 작성" on posts
  for insert to authenticated
  with check (auth.uid() = author_id);

-- 4. 자기 글만 수정·삭제할 수 있다
create policy "본인 글 수정" on posts
  for update to authenticated
  using (auth.uid() = author_id);
```

- `auth.uid()` : 요청을 보낸 로그인 사용자의 ID
- `using` : 기존 행 중 **어떤 행에 접근할 수 있는지** (select, update, delete)
- `with check` : 새로 쓰는 값이 **조건을 만족하는지** (insert, update)

주의할 점

- **RLS가 꺼진 테이블은 publishable key만 있으면 누구나 읽고 쓸 수 있다.** 대시보드의 Security Advisor 경고를 꼭 확인하자.
- 프론트엔드에서 버튼을 숨기는 건 보안이 아니다. 권한은 반드시 RLS(또는 서버 코드)에서 검사한다.
- 정책 조건에 쓰는 컬럼(e.g. `author_id`)에는 인덱스를 걸어야 테이블이 커져도 느려지지 않는다.

## 5. 주요 기능 살펴보기

### 5.1 Auth

```ts
// 이메일 회원가입 / 로그인
await supabase.auth.signUp({ email, password })
await supabase.auth.signInWithPassword({ email, password })

// 소셜 로그인
await supabase.auth.signInWithOAuth({ provider: 'github' })

// 현재 사용자, 로그아웃
const { data: { user } } = await supabase.auth.getUser()
await supabase.auth.signOut()
```

- 사용자 정보는 `auth.users` 테이블에 저장된다. 닉네임·프로필 사진 같은 추가 정보는 보통 `public.profiles` 테이블을 따로 만들어 `auth.users.id`와 연결한다.
- 다중 인증(MFA), 이메일 템플릿, 리다이렉트 URL 등을 대시보드에서 설정한다.

### 5.2 Storage

```ts
await supabase.storage.from('avatars').upload(`${user.id}/profile.png`, file)
const { data } = supabase.storage.from('avatars').getPublicUrl(`${user.id}/profile.png`)
```

- 버킷(bucket) 단위로 공개·비공개를 정하고, 접근 권한은 RLS 정책으로 관리한다.

### 5.3 Realtime

```ts
supabase
  .channel('room-1')
  .on('postgres_changes', { event: 'INSERT', schema: 'public', table: 'messages' }, payload => {
    console.log('새 메시지', payload.new)
  })
  .subscribe()
```

- `Postgres Changes` : 테이블 변경 구독
- `Broadcast` : 클라이언트끼리 빠르게 메시지 주고받기 (커서 위치, 타이핑 표시)
- `Presence` : 현재 접속 중인 사용자 목록

### 5.4 Edge Functions

- 결제 웹훅 처리, 외부 API 호출, Secret key가 필요한 작업처럼 **클라이언트에서 하면 안 되는 일** 을 맡긴다.
- TypeScript로 작성하고 `supabase functions deploy`로 배포한다.

## 6. Next.js에서 사용하기

서버 컴포넌트·Server Actions에서는 쿠키로 로그인 세션을 주고받아야 하므로 `@supabase/ssr` 패키지를 쓴다.

```ts
// lib/supabase/server.ts
import { createServerClient } from '@supabase/ssr'
import { cookies } from 'next/headers'

export async function createClient() {
  const cookieStore = await cookies()
  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
    {
      cookies: {
        getAll: () => cookieStore.getAll(),
        setAll: list => list.forEach(({ name, value, options }) => cookieStore.set(name, value, options)),
      },
    },
  )
}
```

```tsx
// app/posts/page.tsx (서버 컴포넌트)
import { createClient } from '@/lib/supabase/server'

export default async function PostsPage() {
  const supabase = await createClient()
  const { data: posts } = await supabase.from('posts').select('id, title')
  return <ul>{posts?.map(p => <li key={p.id}>{p.title}</li>)}</ul>
}
```

- 서버에서 사용자를 확인할 때는 `getSession()`보다 **`getUser()`(또는 `getClaims()`)** 처럼 토큰을 검증하는 메서드를 쓰자. 쿠키 값만 믿으면 위조될 수 있다.
- 세션 갱신은 Next.js 미들웨어(Proxy)에서 처리한다. 자세한 설정은 [공식 가이드](https://supabase.com/docs/guides/auth/server-side/nextjs) 참고

## 7. 로컬 개발과 마이그레이션

대시보드에서 테이블을 클릭으로 만들면 편하지만, 팀 작업에서는 **변경 이력을 코드로 관리** 해야 한다.

```bash
npx supabase init          # supabase/ 폴더 생성
npx supabase start         # Docker로 로컬에 Supabase 전체 실행
npx supabase migration new create_posts   # SQL 마이그레이션 파일 생성
npx supabase db push       # 원격 프로젝트에 마이그레이션 적용
```

- 마이그레이션 SQL을 Git에 커밋하면, 다른 팀원과 운영 환경에 같은 스키마를 재현할 수 있다.
- **Branching** 기능으로 PR마다 별도의 미리보기 DB를 만들 수도 있다.
- ORM을 함께 쓰고 싶다면 Prisma나 Drizzle을 Supabase의 PostgreSQL 연결 문자열에 연결하면 된다. (이 경우 서버 코드에서 접속하므로 RLS 대신 코드에서 권한을 검사해야 한다) → [Prisma](/backend/prisma)
- Supabase MCP 서버를 연결하면 AI 코딩 도구가 테이블 조회, 마이그레이션 작성 등을 도와줄 수 있다. (운영 DB에는 읽기 전용으로 연결하는 것을 권장)

## 8. Supabase vs Firebase

|                  | Supabase                                         | Firebase                                         |
| ---------------- | ------------------------------------------------ | ------------------------------------------------ |
| 데이터베이스     | **PostgreSQL (관계형)**                          | Firestore (NoSQL 문서형)                         |
| 쿼리             | SQL, JOIN, 집계 모두 가능                        | 단순 조건 조회 위주, JOIN·복잡한 집계는 어려움   |
| 권한             | RLS (SQL 정책)                                   | Security Rules (전용 문법)                       |
| 오픈소스·자체 호스팅 | ✅ 가능 (Docker로 직접 운영)                  | ❌ 구글 클라우드 전용                             |
| 데이터 이전      | 일반 PostgreSQL이라 다른 곳으로 옮기기 쉬움      | 다른 DB로 옮기려면 변환 작업 필요                |
| 강점             | 관계형 데이터, 복잡한 쿼리, AI(pgvector)         | 모바일 SDK, 오프라인 동기화, 푸시 알림(FCM), 분석 등 구글 생태계 |

- 데이터 사이의 관계가 많고(사용자-주문-상품), SQL이 익숙하다면 → **Supabase**
- 모바일 앱 중심이고, 오프라인 동기화와 구글 서비스 연동이 중요하다면 → **Firebase**
- cf. Firebase도 PostgreSQL 기반의 Data Connect를 내놓는 등, 두 서비스의 영역은 점점 겹치고 있다.

## 9. 장단점

**장점**

- 백엔드 서버 없이 **인증 + DB + 파일 + 실시간** 을 빠르게 갖출 수 있다. (MVP, 사이드 프로젝트에 특히 좋음)
- 표준 PostgreSQL이라 SQL 지식을 그대로 쓰고, 확장(pgvector, PostGIS 등)도 쓸 수 있다.
- 오픈소스라 **특정 회사에 묶이는 위험(벤더 락인)이 적다.**
- 대시보드, 타입 생성, 로컬 개발 환경 등 개발 경험이 좋다.

**단점과 주의점**

- **RLS를 제대로 설계하지 않으면 보안 사고로 이어진다.** 클라이언트가 DB에 직접 접근하는 구조이기 때문이다.
- 복잡한 비즈니스 로직이 많아지면 SQL 함수·Edge Functions·RLS에 로직이 흩어질 수 있다. 이때는 별도 백엔드 서버를 두는 것도 고려하자.
- 무료 플랜은 일정 기간 사용하지 않으면 프로젝트가 일시 정지된다.
- 트래픽이 커지면 컴퓨팅·저장소·전송량에 따라 요금이 늘어나므로 사용량을 모니터링하자.

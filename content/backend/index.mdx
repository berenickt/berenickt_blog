| 17   | AI와 백엔드                  | AI 기능을 서비스에 어떻게 붙이나?                          |

공부 순서 팁

- **2 → 3 → 4 → 5 → 6** 까지가 "혼자 CRUD API 서버를 만들 수 있는" 최소 단계다.
- **7 → 11 → 13** 을 더하면 로그인이 되는 서비스를 테스트하고 배포할 수 있다.
- 8~10, 14~15는 실제 사용자가 생기고 트래픽이 늘어날 때 필요해진다. 프로젝트를 하나 배포해 본 뒤 보면 훨씬 잘 이해된다.
- 처음부터 MSA, 쿠버네티스, 메시지 큐를 쓰려고 하지 말자. **단순한 구조로 만들고, 문제가 생겼을 때 그 문제를 푸는 기술을 배우는 것** 이 가장 빠르다.

## 1. 백엔드 개발자가 하는 일

사용자 눈에 보이지 않는 곳에서 **데이터와 비즈니스 규칙을 책임지는 일** 이다.

- **API 개발** : 웹·앱이 요청하면 데이터를 처리해 응답
- **데이터 모델링과 관리** : DB 설계, 쿼리 작성, 데이터 정합성 유지
- **비즈니스 로직** : "재고가 없으면 주문 불가", "쿠폰은 1인 1회" 같은 규칙을 코드로 구현
- **인증·보안** : 로그인, 권한, 개인정보 보호
- **외부 연동** : 결제, 메일·문자 발송, 소셜 로그인, AI API
- **성능과 안정성** : 트래픽이 몰려도 느려지거나 죽지 않게, 장애가 나면 빠르게 복구
- **배포와 운영** : 서버 인프라 구성, 모니터링, 장애 대응

> 프론트엔드가 "사용자가 보는 화면"을 책임진다면, 백엔드는 **"데이터가 틀리지 않고, 서비스가 멈추지 않는 것"** 을 책임진다.

## 2. CS 기초 지식

프레임워크는 몇 년마다 바뀌지만, CS 기초는 변하지 않는다. 장애를 분석하고 성능 문제를 해결할 때 결국 이 지식이 필요하다.

- **네트워크** : IP·포트, DNS, TCP/UDP, HTTP/HTTPS, TLS, 로드 밸런서·프록시 → [네트워크](/cs/network/01-intro)
- **운영체제** : 프로세스와 스레드, 컨텍스트 스위칭, 동기화와 교착 상태(데드락), 메모리, 파일 시스템 → [운영체제](/cs/operating-system/01-intro)
  - 왜 필요? "Node.js는 싱글 스레드인데 어떻게 동시 요청을 처리하지?", "스레드 풀이 꽉 차서 응답이 멈췄다" 같은 문제를 이해하려면
- **자료구조와 알고리즘** : 배열, 해시 테이블, 스택·큐, 트리, 그래프, 정렬·탐색, 시간 복잡도 → [자료구조&알고리즘](/cs/algorithm-js/01-Intro)
  - 왜 필요? DB 인덱스(B-Tree), 캐시(해시), 작업 큐 등 백엔드 도구 대부분이 자료구조 위에 만들어져 있다.
- **Linux 기본** : 터미널 명령어, 권한, 프로세스 확인(`ps`, `top`), 로그 확인(`tail -f`), SSH → 서버는 대부분 Linux에서 돈다.

| **TypeScript (Node.js)**  | **NestJS**, Express, Fastify, Hono    | 프론트엔드와 같은 언어, 빠른 개발, 스타트업에서 많이 사용            |

| **Go**                    | 표준 라이브러리, Gin, Echo            | 가볍고 빠름, 동시성에 강함. 인프라·클라우드 도구에 많이 쓰임        |

- 런타임 : Node.js 외에 **Bun**, **Deno** 도 실무에서 쓰이기 시작했다.

## 4. HTTP와 웹 서버

백엔드의 거의 모든 일은 **HTTP 요청을 받아 응답을 돌려주는 것** 에서 시작한다.

- **HTTP 기본** : 메서드(GET·POST·PUT·PATCH·DELETE), 상태 코드(200·201·400·401·403·404·500), 헤더, 쿠키
- **요청이 처리되는 흐름**

```
클라이언트 → DNS → 로드 밸런서 / 리버스 프록시(Nginx)
          → 애플리케이션 서버 (라우터 → 미들웨어 → 컨트롤러 → 서비스 → DB)
          → 응답
```

- **미들웨어** : 로깅, 인증 확인, 요청 본문 파싱처럼 모든 요청에 공통으로 적용하는 처리
- **리버스 프록시(Nginx 등)** : HTTPS 처리, 정적 파일 서빙, 여러 서버로 부하 분산
- **CORS** : 다른 출처(도메인)의 브라우저 요청을 허용하는 설정. 프론트엔드와 연동할 때 가장 먼저 만나는 문제
- **입력값 검증** : 클라이언트가 보낸 값은 절대 믿지 않는다. DTO·스키마(e.g. class-validator, Zod)로 검증

cf. HTTP 상세 내용은 [프론트엔드 로드맵 - 네트워크 통신](/frontend) 7장 참고

## 5. 데이터베이스

백엔드 실력의 상당 부분은 **데이터를 잘 설계하고 다루는 능력** 이다.

### 5.1 RDBMS와 SQL ✅ 가장 먼저

- 대표 : **PostgreSQL**, **MySQL**, MariaDB, Oracle
- 꼭 알아야 할 것
  - **SQL** : `SELECT`·`JOIN`·`GROUP BY`·서브쿼리를 손으로 쓸 수 있을 정도
  - **모델링** : 테이블 설계, 관계(1:1, 1:N, N:M), 기본 키·외래 키, ERD
  - **정규화** 와 언제 반정규화할지
  - **인덱스** : 왜 빨라지는지(B-Tree), 어떤 컬럼에 걸지, 실행 계획(`EXPLAIN`) 읽기
  - **트랜잭션과 ACID**, 격리 수준, 락(lock)과 동시성 문제
  - **마이그레이션** : 스키마 변경을 코드로 관리
- **ORM / 쿼리 빌더** : SQL을 코드로 다루는 도구
  - Node.js : Prisma, Drizzle, TypeORM / Java : JPA(Hibernate) / Python : SQLAlchemy, Django ORM
  - ORM을 쓰더라도 **실제로 어떤 SQL이 나가는지** 확인하는 습관이 중요하다. (N+1 문제)

### 5.2 NoSQL과 목적별 DB

- **Redis** : 캐시, 세션, 순위표, 요청 횟수 제한
- **MongoDB** : 구조가 자주 바뀌는 문서형 데이터
- **Elasticsearch / OpenSearch** : 검색
- **DynamoDB, Cassandra** : 대규모 트래픽의 키-값·와이드 컬럼 데이터
- **벡터 DB(pgvector 등)** : AI 의미 검색

cf. [데이터베이스 종류](/backend/database-type), [PostgreSQL](/backend/postgresql), [MySQL](/backend/mysql), [Oracle](/backend/oracle), [Redis](/backend/redis), [Prisma](/backend/prisma), [Supabase](/backend/supabase)

## 6. API 설계

| 방식          | 특징                                                              | 주로 쓰는 곳                        |
| ------------- | ----------------------------------------------------------------- | ----------------------------------- |
| **REST** ✅   | URL(자원) + HTTP 메서드(행위). 가장 보편적                        | 대부분의 웹·앱 API, 공개 API        |
| **GraphQL**   | 클라이언트가 필요한 필드를 골라 요청                              | 화면이 다양하고 데이터 관계가 복잡한 서비스 |
| **gRPC**      | Protocol Buffers 기반의 빠른 이진 통신                            | 서버 간(마이크로서비스) 통신        |
| **WebSocket / SSE** | 실시간 양방향 통신 / 서버 → 클라이언트 스트리밍             | 채팅, 알림, AI 응답 스트리밍        |
| SOAP          | XML 기반의 엄격한 규약                                            | 금융·공공 레거시 시스템             |

좋은 REST API를 위해 알아 둘 것

- 일관된 URL 규칙(`/users/1/orders`), 올바른 상태 코드, 일관된 에러 응답 형식
- 페이지네이션(offset / cursor), 필터·정렬
- **API 문서화** : OpenAPI(Swagger)로 명세를 만들면 문서와 클라이언트 코드를 자동 생성할 수 있다.
- **버전 관리** 와 하위 호환성 : 이미 배포된 앱이 깨지지 않게
- 멱등성 : 결제처럼 중복 요청이 위험한 API는 `Idempotency-Key`로 중복 처리를 막는다.

cf. [GraphQL](/backend/graphql), [gRPC](/backend/grpc), [NestJS Swagger](/backend/nestjs/42-swagger)

## 7. 인증과 인가

- **인증(Authentication)** : 너는 누구니? (로그인)
- **인가(Authorization)** : 너는 이걸 해도 되니? (권한)

| 방식                  | 특징                                                                    |
| --------------------- | ----------------------------------------------------------------------- |
| 세션 + 쿠키           | 서버에 로그인 상태 저장. 강제 로그아웃이 쉬움                           |
| JWT                   | 토큰에 정보를 담아 서버가 상태를 저장하지 않음. Access + Refresh Token 조합 |
| OAuth 2.0 / OpenID Connect | 구글·카카오·네이버 등 소셜 로그인, 외부 서비스 권한 위임            |
| 패스키(Passkey)       | 비밀번호 없이 기기의 생체 인증으로 로그인. 빠르게 확산 중               |

- 비밀번호는 절대 그대로 저장하지 않는다 → **bcrypt, Argon2** 로 해시
- 권한 모델 : RBAC(역할 기반, e.g. 관리자·일반 사용자), 리소스 소유자 확인("내 글만 수정 가능")
- 직접 구현이 부담된다면 인증 서비스(Auth0, Clerk, Supabase Auth, Keycloak 등)를 쓰는 것도 방법이다.

cf. [로그인의 역사(feat. JWT)](/backend/login), [NestJS 인증](/backend/nestjs/11-authentication), [RBAC](/backend/nestjs/34-rbac)

## 8. 보안

백엔드는 해커의 직접적인 공격 대상이다. **OWASP Top 10** 은 꼭 한 번 읽어 보자.

- **인젝션(SQL Injection 등)** : 사용자 입력을 쿼리에 문자열로 이어 붙이지 않는다 → 파라미터 바인딩, ORM 사용
- **접근 제어 실패** : URL의 ID만 바꿔서 남의 데이터를 보는 문제(IDOR) → 모든 요청에서 소유자·권한 확인
- **XSS, CSRF** : 출력 이스케이프, SameSite 쿠키, CSRF 토큰
- **민감 정보 관리** : 비밀번호·API 키를 코드에 하드코딩하지 않고 환경 변수나 Secret Manager로 관리, 로그에 개인정보 남기지 않기
- **전송·저장 암호화** : HTTPS 필수, 민감한 개인정보는 DB에서도 암호화
- **Rate Limiting** : 로그인 무차별 대입, API 남용 방지
- **의존성 취약점** : 라이브러리 보안 업데이트 꾸준히 적용 (Dependabot, `npm audit`)
- 개인정보보호법 등 법적 요구사항도 백엔드가 지켜야 하는 경우가 많다.

## 9. 캐싱과 성능

> 최적화의 첫걸음은 **측정** 이다. 추측으로 고치지 말고, 느린 곳을 먼저 찾자.

- **DB 최적화** : 느린 쿼리 로그 확인, 인덱스 추가, N+1 쿼리 제거, 필요한 컬럼만 조회
- **캐싱**
  - 애플리케이션 캐시 : **Redis** 에 자주 읽는 데이터 저장 (Cache-Aside 패턴)
  - HTTP 캐시 : `Cache-Control`, `ETag` 헤더
  - CDN : 이미지·정적 파일을 사용자 가까운 곳에서 응답
  - 캐시 무효화(데이터가 바뀌었을 때 캐시 지우기)와 만료 시간 설계가 핵심
- **커넥션 풀** : DB 연결을 재사용해 연결 비용 절감
- **확장** : 수직 확장(서버 사양 업) vs 수평 확장(서버 대수 증가 + 로드 밸런서), DB 읽기 복제본
- **부하 테스트** : k6, nGrinder, JMeter로 "몇 명까지 버티는지" 미리 확인

cf. [NestJS 캐시](/backend/nestjs/40-cache)

## 10. 비동기 처리와 메시지 큐

메일 발송, 이미지 변환, 정산처럼 **오래 걸리거나 실패할 수 있는 일** 은 요청-응답 안에서 처리하지 않고 뒤로 넘긴다.

```
요청 → API 서버 : "주문 완료" 바로 응답
             └→ 메시지 큐에 "주문 생성됨" 이벤트 발행
                    ├→ 메일 서버 : 주문 확인 메일 발송
                    ├→ 재고 서버 : 재고 차감
                    └→ 정산 서버 : 매출 기록
```

- **작업 큐** : BullMQ(Redis 기반), Celery(Python) → 백그라운드 작업, 재시도
- **메시지 브로커** : **Kafka**(대용량 이벤트 스트리밍), **RabbitMQ**, AWS SQS·SNS
- **스케줄링** : 매일 새벽 통계 집계 같은 정기 작업(cron)
- 알아 둘 개념 : 재시도와 멱등성, 실패한 메시지 처리(Dead Letter Queue), 순서 보장, **이벤트 기반 아키텍처**

cf. [NestJS 작업 스케줄링](/backend/nestjs/41-task-scheduling), [NestJS 웹소켓 큐](/backend/nestjs/45-websocket-queue), [RxJS](/backend/rxjs)

## 11. 테스트

| 종류                  | 무엇을 검증하나                                         | 도구 예시                          |
| --------------------- | ------------------------------------------------------- | ---------------------------------- |
| 단위 테스트           | 함수·서비스 하나의 로직                                 | Jest, Vitest, JUnit, pytest        |
| 통합 테스트           | DB·외부 시스템과 함께 동작하는지                        | **Testcontainers**(실제 DB를 Docker로 띄워 테스트) |
| E2E / API 테스트      | 실제 HTTP 요청부터 응답까지                             | Supertest, REST Assured, Postman   |
| 인수 테스트           | 요구사항(사용자 시나리오)을 만족하는지                  | Cucumber 등                        |
| 부하 테스트           | 트래픽을 얼마나 버티는지                                | k6, nGrinder                       |

- 백엔드는 **비즈니스 로직 단위 테스트 + DB를 포함한 통합 테스트** 가 가장 효과적이다.
- DB를 모킹(mock)만 해서는 실제 쿼리 오류를 못 잡는다. Testcontainers로 진짜 DB를 띄워 테스트하는 방식이 표준이 되었다.
- 개발 방법론 : **TDD**(테스트 먼저 작성), **BDD**(사용자 행동 시나리오 중심으로 테스트 작성)

cf. [NestJS 테스트](/backend/nestjs/43-testing), [프론트엔드 테스트](/frontend/front-test) (테스트 원칙은 공통)

## 13. 배포와 인프라

```
코드 푸시 → CI (테스트·빌드) → Docker 이미지 → 레지스트리 → CD (배포) → 서버 / 쿠버네티스
```

- **Docker** ✅ : 앱과 실행 환경을 이미지로 묶어 어디서나 똑같이 실행 → 이제는 기본기
- **클라우드** : AWS가 국내에서 가장 많이 쓰임 (EC2, RDS, S3, Lambda, ECS 등). GCP, Azure, 국내 클라우드(NCP 등)
- **PaaS** : 인프라 관리 없이 배포 (Render, Railway, Fly.io, Vercel, AWS App Runner 등) → 사이드 프로젝트에 적합
- **Kubernetes** : 컨테이너 여러 개를 자동으로 배포·확장·복구. 서비스 규모가 클 때 사용
- **CI/CD** : **GitHub Actions**(가장 보편적), Jenkins, GitLab CI/CD, Argo CD(쿠버네티스 GitOps)
- **IaC(Infrastructure as Code)** : 인프라를 코드로 관리 (Terraform, AWS CDK, Pulumi)
- 배포 전략 : 롤링, 블루-그린, 카나리 배포, 그리고 무엇보다 **롤백** 방법

cf. [Docker](/devops/docker/01-intro), [Kubernetes](/devops/kubernetes), [AWS](/devops/aws/01-cloud), [Jenkins](/devops/jenkins), [CI/CD](/cs/terms-principles/ci-cd), [NestJS 배포](/backend/nestjs/44-deploy)

## 14. 아키텍처

| 아키텍처                     | 설명                                                                     | 언제                                   |
| ---------------------------- | ------------------------------------------------------------------------ | -------------------------------------- |
| **모놀리식(계층형)** ✅       | 하나의 앱 안에 Controller → Service → Repository 계층으로 나눔            | 대부분의 서비스는 여기서 시작          |
| **모듈러 모놀리스**          | 하나의 배포 단위지만, 내부를 도메인별 모듈로 엄격하게 분리               | 팀과 코드가 커지기 시작할 때           |
| **마이크로서비스(MSA)**      | 도메인별로 독립 배포되는 여러 서비스로 분리                              | 팀이 많고 독립 배포·확장이 꼭 필요할 때 |
| **서버리스**                 | 함수 단위로 실행, 사용한 만큼 과금 (AWS Lambda 등)                       | 트래픽이 불규칙하거나 이벤트 처리 위주  |
| **이벤트 기반**              | 서비스끼리 이벤트(메시지)로 느슨하게 연결                                | 비동기 처리, 서비스 간 결합도를 낮출 때 |

- 코드 설계 원칙 : SOLID, 레이어드 아키텍처, **헥사고날(포트와 어댑터)·클린 아키텍처**, **DDD(도메인 주도 설계)**
- MSA는 만능이 아니다. 네트워크 장애, 분산 트랜잭션, 운영 복잡도라는 대가를 치른다. **"모놀리스로 시작해서 필요할 때 나누자"** 가 일반적인 조언이다.

cf. [MSA](/backend/msa), [NestJS 아키텍처](/backend/nestjs/51-architecture), [디자인 패턴](/cs/design-pattern/01-OOP)

## 15. 관측성 (Observability)

운영 중인 서버에서 문제가 생겼을 때 **"무슨 일이, 어디서, 왜"** 일어났는지 알 수 있어야 한다.

- **로그(Logs)** : 무슨 일이 있었는지. JSON 형태의 구조화된 로그, 요청마다 고유 ID(trace id)를 남기기
- **메트릭(Metrics)** : 숫자로 본 상태. 응답 시간, 에러율, 초당 요청 수, CPU·메모리 → Prometheus + Grafana
- **트레이스(Traces)** : 요청 하나가 여러 서비스·DB를 거쳐 간 경로와 각 구간의 시간 → MSA에서 필수
- 표준 : **OpenTelemetry** 로 로그·메트릭·트레이스를 한 번에 수집
- **에러 추적** : Sentry / **알림** : 에러율이 높아지면 슬랙·전화로 알림 / 장애 회고(Postmortem)
- 상용 도구 : Datadog, New Relic, AWS CloudWatch, Grafana Cloud

## 17. AI와 백엔드

2026년 지금, AI 기능은 많은 서비스의 기본 기능이 되었고, 그 연결은 대부분 백엔드가 맡는다.

- **LLM API 연동** : AI 제공사의 API를 서버에서 호출 (API 키는 반드시 서버에서만), 스트리밍 응답(SSE) 전달
- **RAG(검색 증강 생성)** : 사내 문서·DB 데이터를 임베딩해서 **벡터 DB** 에 저장하고, 질문과 관련된 내용을 찾아 AI에게 함께 전달
- **MCP(Model Context Protocol) 서버** : 우리 서비스의 기능·데이터를 AI 에이전트가 도구로 쓸 수 있게 제공
- **운영 고려사항** : 비용(토큰 사용량) 관리, 응답 지연, 요청 제한, 프롬프트 인젝션 같은 새로운 보안 위협, 결과 품질 평가
- **AI 코딩 도구 활용** : 테스트·타입·명확한 요구사항이 갖춰진 프로젝트일수록 AI가 만든 변경을 안전하게 검증할 수 있다. 결국 **기본기(1~16단계)로 결과물을 판단하는 능력** 이 더 중요해진다.

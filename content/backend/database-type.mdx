| -------------------- | ------------------------------ | ----------------------------------------- | --------------------------------------- |
| **관계형(RDBMS)**    | 표(행·열) + 테이블 간 관계     | PostgreSQL, MySQL, Oracle, SQLite         | 대부분의 서비스, 돈·주문처럼 정확해야 하는 데이터 |

- 실무에서는 하나만 쓰기보다 **메인 DB(보통 RDBMS) + 목적별 보조 DB** 를 함께 쓰는 경우가 많다.
  - e.g. PostgreSQL(메인) + Redis(캐시) + Elasticsearch(검색)

## 1. 관계형 데이터베이스 (RDBMS)

데이터를 **표(table)** 로 저장한다. 열(column)에 항목 이름과 타입을 정해 두고, 행(row)마다 데이터 하나를 저장한다.
그리고 표와 표를 **키(key)로 연결** 해서 관계를 표현한다.

```
users                         orders
| id | name   |               | id | user_id | product  | price  |
|----|--------|               |----|---------|----------|--------|
| 1  | 철수   |  ◀──────────  | 10 | 1       | 키보드   | 50000  |
| 2  | 영희   |               | 11 | 1       | 마우스   | 30000  |
```

- `Primary Key(기본 키)` : 행을 구별하는 고유 값 (e.g. `users.id`)
- `Foreign Key(외래 키)` : 다른 표의 기본 키를 가리키는 값 (e.g. `orders.user_id`)

> 💡 "Relational(관계형)"의 relation은 테이블끼리의 연결이 아니라, 수학(집합론)의 **관계(relation)** 에서 온 말이다.
> 1970년 에드거 F. 코드(E. F. Codd)가 논문에서 "데이터를 relation(= 표)으로 다루자"고 제안한 것이 시작이다.
>
> cf. 엑셀 시트도 표처럼 생겼지만, 스키마·관계·트랜잭션이 없으므로 관계형 DB는 아니다.

### 1.2 SQL

RDBMS의 데이터는 **SQL(Structured Query Language)** 로 다룬다.

```sql
-- 철수의 주문 목록과 총액
SELECT u.name, o.product, o.price
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.name = '철수';
```

- `JOIN`으로 여러 표를 연결해서 원하는 모양으로 꺼낼 수 있다는 것이 가장 큰 장점이다.
- 백엔드 코드에서는 SQL을 직접 쓰거나, **ORM·쿼리 빌더** 를 통해 쓴다. (e.g. Prisma, Drizzle, TypeORM, JPA)
  - cf. [Prisma](/backend/prisma)

---

### 1.3 정규화(Normalization)

**같은 데이터를 여러 곳에 중복해서 저장하지 않도록, 표를 나누는 것** 이다.

- e.g. 주문마다 사용자 이름·주소를 같이 저장하면, 사용자가 주소를 바꿨을 때 모든 주문 행을 고쳐야 한다.
  - → `users` 표에 한 번만 저장하고, 주문에는 `user_id`만 둔다.
- 장점 : 데이터가 **한 곳에만** 있으므로 수정이 쉽고, 서로 다른 값이 생기는(불일치) 문제가 없다.
- 단점 : 데이터를 꺼낼 때 `JOIN`이 많아지고, 쿼리가 길어지고 느려질 수 있다.
  - 그래서 읽기 성능이 중요한 부분은 일부러 중복을 허용하기도 한다. → **반정규화(Denormalization)**

---

### 1.4 트랜잭션과 ACID

**트랜잭션(Transaction)** = 여러 작업을 **하나의 단위** 로 묶어서, 전부 성공하거나 전부 실패하게 만드는 기능이다.

- e.g. 계좌 이체 : "A 계좌에서 1만 원 빼기" + "B 계좌에 1만 원 넣기"
  - 빼기만 되고 넣기가 실패하면 돈이 사라진다. → 둘 중 하나라도 실패하면 **롤백(Rollback)** 해서 처음 상태로 되돌린다.

트랜잭션이 보장하는 4가지 성질 **ACID**

- `Atomicity(원자성)` : 전부 성공하거나 전부 실패한다.
- `Consistency(일관성)` : 트랜잭션 전후로 데이터가 규칙(제약 조건)을 항상 만족한다.
- `Isolation(고립성)` : 동시에 실행되는 트랜잭션끼리 서로 간섭하지 않는다.
- `Durability(지속성)` : 성공(커밋)한 결과는 서버가 꺼져도 사라지지 않는다.

그래서 **돈, 주문, 재고처럼 정확성이 가장 중요한 데이터** 는 대부분 RDBMS에 저장한다.

---

### 1.5 RDBMS의 한계와 진화

- 전통적인 RDBMS는 서버 한 대의 성능을 올리는 **수직 확장(Scale-up)** 에 맞춰져 있어서, 여러 대로 나누는 **수평 확장(Scale-out)** 이 어렵다.
- 이 문제를 풀려고 **분산 SQL(NewSQL)** 이 등장했다. SQL과 ACID를 유지하면서 여러 서버에 데이터를 나눠 저장한다.
  - e.g. Google Cloud Spanner, CockroachDB, TiDB, YugabyteDB, Amazon Aurora DSQL
- 또 서버 관리 없이 쓰는 **서버리스 DB** 도 대중화되었다.
  - e.g. Neon·Supabase(PostgreSQL), PlanetScale(MySQL·PostgreSQL), Turso(SQLite 기반)
  - cf. [Supabase](/backend/supabase)
- 그리고 PostgreSQL은 JSON 저장(`jsonb`), 전문 검색, 벡터 검색(pgvector)까지 지원하면서 **"웬만한 건 PostgreSQL 하나로"** 라는 흐름도 강해졌다.

## 2. 키-값 데이터베이스 (Key-Value)

데이터를 `key → value` 형태로 저장한다. 사전처럼 키로 값을 바로 찾는 구조라 **매우 빠르다.**

```
session:abc123   →  { "userId": 1, "expires": "..." }
rank:game        →  [철수: 980, 영희: 950, ...]
```

구조가 단순해서 복잡한 조회(조건 검색, JOIN)는 못 하지만, 그만큼 빠르기 때문에 **메인 DB를 돕는 보조 DB** 로 많이 쓴다.

---

### 2.1 Redis

- 데이터를 디스크가 아니라 **메모리(RAM)** 에 저장하는 인메모리 DB → 응답이 매우 빠르다. (보통 1ms 이하)
- 메모리에만 있으면 꺼질 때 사라지므로, 스냅샷(RDB)이나 기록 로그(AOF)로 **디스크에 백업** 하는 기능도 있다.
- 단순한 문자열뿐 아니라 리스트, 해시, 셋, 정렬된 셋(Sorted Set), 스트림 등 다양한 자료구조를 지원한다.

**대표적인 사용 방식 : 캐시(Cache)**

```
요청 → Redis에 있나?
        ├─ 있음(Cache Hit)  → 바로 응답 ⚡
        └─ 없음(Cache Miss) → 메인 DB 조회 → Redis에 저장 → 응답
```

자주 읽히는 데이터를 Redis에 복사해 두면 메인 DB 부하가 줄고 응답이 빨라진다.

**용도**

- 자주 쓰는 데이터 **캐싱**
- 로그인 **세션** 저장, 토큰 블랙리스트
- 실시간 **순위표** (Sorted Set)
- 요청 횟수 제한(Rate Limiting)
- 채팅·알림을 위한 **Pub/Sub**, 작업 큐(e.g. BullMQ)
- 선착순 이벤트처럼 동시성 제어가 필요한 카운터

> 💡 라이선스 변화 : Redis는 2024년 오픈소스 라이선스를 바꿨고, 이에 반발해 리눅스 재단 아래에서 **Valkey** 라는 포크가 만들어졌다.
> 이후 Redis 8(2025)에서 다시 AGPL 오픈소스 선택지를 추가했다. AWS·구글 클라우드 등은 Valkey 기반 서비스도 제공한다.

cf. [Redis](/backend/redis)

---

### 2.2 그 밖의 키-값 DB

- **Amazon DynamoDB** : AWS의 서버리스 키-값·문서 DB. 규모가 아무리 커져도 응답 속도가 일정하게 유지되도록 설계됨
- **Memcached** : 캐시 전용의 단순한 인메모리 저장소
- **etcd** : 설정 정보 저장용 분산 키-값 저장소 (쿠버네티스가 사용)

## 3. 문서 데이터베이스 (Document)

데이터를 **JSON 같은 문서** 단위로 저장한다.

```json
// posts 컬렉션의 문서 하나
{
  "_id": "665f...",
  "title": "MongoDB 입문",
  "author": { "id": 1, "name": "철수" },
  "tags": ["db", "nosql"],
  "comments": [{ "user": "영희", "text": "좋아요" }]
}
```

- `collection(컬렉션)` : 문서를 모아 두는 폴더 같은 것 (RDBMS의 테이블)
- `document(문서)` : JSON 형태의 데이터 하나 (RDBMS의 행)

---

### 3.1 특징

- **스키마가 유연하다** : 미리 열을 정해 둘 필요가 없어서, 문서마다 필드가 달라도 된다.
  - e.g. 어떤 사용자에게만 `phone` 필드를 추가해도 된다.
  - 단, "아무렇게나 넣어도 된다"는 뜻은 아니다. 애플리케이션 코드나 스키마 검증 기능으로 구조를 관리해야 나중에 고생하지 않는다.
- **관련 데이터를 한 문서에 함께 넣는다(임베딩)** : 위 예시처럼 게시글에 작성자·댓글을 함께 저장해서 **한 번에 읽는다.**
  - RDBMS의 정규화와 반대로, 중복을 어느 정도 허용하고 **자주 함께 읽는 데이터끼리 묶는** 설계를 한다.
  - 대신 같은 데이터가 여러 문서에 복사되어 있으면, 바꿀 때 모두 고쳐야 한다.
- **수평 확장(샤딩)이 쉽다** : 처음부터 여러 서버에 나눠 저장하는 것을 염두에 두고 만들어졌다.
- 트랜잭션 : 예전에는 약했지만, MongoDB는 4.0(2018)부터 **여러 문서에 걸친 ACID 트랜잭션** 을 지원한다.

### 3.2 종류

- **MongoDB** : 가장 대표적인 문서 DB
- **Cloud Firestore** : 구글 Firebase의 서버리스 문서 DB, 실시간 동기화가 강점
- CouchDB, Amazon DocumentDB(MongoDB 호환)

### 3.3 용도

- 상품 정보처럼 **항목마다 속성이 다른 데이터** (옷은 사이즈, 노트북은 CPU…)
- 게시판, CMS, 사용자 프로필처럼 **한 덩어리로 읽고 쓰는 데이터**
- 빠르게 구조가 바뀌는 초기 서비스, 로그·이벤트 데이터

## 4. 와이드 컬럼 데이터베이스 (Wide-Column)

겉보기에는 표처럼 생겼지만, **행마다 서로 다른 열을 가질 수 있는** 거대한 분산 테이블이다. (Column-family DB라고도 부른다)

- 데이터를 **파티션 키** 기준으로 여러 서버에 나눠 저장해서, **쓰기 성능과 확장성이 매우 뛰어나다.**
- 대신 JOIN이 없고, **"어떤 쿼리를 할지"를 먼저 정한 뒤 그에 맞춰 테이블을 설계** 해야 한다. (쿼리 중심 설계)
- 그래서 같은 데이터를 조회 방식별로 여러 테이블에 중복 저장하는 경우가 많다.

### 4.1 종류

- **Apache Cassandra** : 가장 유명함. 장애가 나도 멈추지 않는 고가용성이 강점
  - 쿼리 언어는 SQL과 비슷한 **CQL(Cassandra Query Language)**
- **ScyllaDB** : Cassandra와 호환되면서 C++로 다시 만들어 더 빠름
- Apache HBase, Google Cloud Bigtable

### 4.2 용도

- 초당 수십만 건 이상 쓰이는 데이터 : 메시지 기록, 시청 기록, 활동 로그, IoT 데이터
- e.g. 넷플릭스는 시청 기록 같은 대규모 데이터에 Cassandra를 사용하고, 디스코드는 메시지 저장소로 Cassandra를 쓰다가 ScyllaDB로 옮겼다.

## 5. 그래프 데이터베이스 (Graph)

데이터 사이의 **관계** 자체를 1급 데이터로 저장한다.

- `노드(Node)` : 데이터 (e.g. 사람, 상품, 공항)
- `엣지(Edge, 관계)` : 노드 사이의 연결 (e.g. 친구다, 구매했다, 운항한다)
- 노드와 엣지 모두 속성을 가질 수 있다.

```cypher
// 철수의 친구의 친구 중, 철수와 아직 친구가 아닌 사람 (친구 추천)
MATCH (me:Person {name: '철수'})-[:FRIEND]->()-[:FRIEND]->(fof)
WHERE NOT (me)-[:FRIEND]->(fof) AND me <> fof
RETURN DISTINCT fof.name
```

- RDBMS로 "친구의 친구의 친구"를 찾으면 JOIN이 계속 늘어나 느려지지만, 그래프 DB는 연결을 따라가기만 하면 돼서 빠르다.

### 5.1 종류

- **Neo4j** : 가장 유명한 그래프 DB. 쿼리 언어는 **Cypher**
- Amazon Neptune, ArangoDB(다중 모델), Memgraph
- 2024년 그래프 쿼리 언어의 국제 표준 **GQL(ISO/IEC 39075)** 이 제정되었다. (Cypher의 영향을 많이 받음)

### 5.2 용도

- SNS 친구 관계, 팔로우 추천
- 상품·콘텐츠 추천
- 비행기 노선, 경로 탐색
- 금융 사기 탐지(계좌 간 수상한 연결 찾기), 감염 경로 추적
- 지식 그래프 (AI의 RAG에서 관계 정보를 함께 활용하는 GraphRAG에도 쓰임)

---

## 6. 검색 엔진 (Search Engine)

**전문(全文) 검색** 을 빠르게 하기 위한 저장소다.

- RDBMS의 `LIKE '%키워드%'`는 모든 행을 다 훑어야 해서 느리고, 형태소·유사어·오타를 처리하지 못한다.
- 검색 엔진은 **역색인(Inverted Index)** 을 만든다. 책 뒤의 찾아보기처럼 "단어 → 그 단어가 들어 있는 문서 목록"을 미리 만들어 두는 것이다.

```
"데이터베이스" → [문서 3, 문서 7, 문서 12]
"검색"         → [문서 7, 문서 9]
```

- 그 밖에 관련도 순 정렬, 형태소 분석(한국어 검색에 중요), 자동 완성, 오타 교정, 하이라이트 등을 지원한다.

### 6.1 종류

- **Elasticsearch** : 가장 널리 쓰이는 검색 엔진. 로그 분석(ELK 스택 : Elasticsearch + Logstash + Kibana)에도 많이 사용
- **OpenSearch** : Elasticsearch 라이선스 변경 후 AWS 주도로 만든 오픈소스 포크
- **Meilisearch, Typesense** : 설정이 간단한 가벼운 검색 엔진
- **Algolia** : 검색 SaaS, 빠른 도입

### 6.2 사용 방식

- 보통 **메인 DB의 데이터를 검색 엔진으로 복사(동기화)** 해서, 검색만 검색 엔진에 맡긴다.
- 메인 DB와 검색 엔진 사이의 데이터가 잠시 다를 수 있으므로, 원본은 항상 메인 DB로 본다.
- 최근 검색 엔진들은 키워드 검색과 벡터(의미) 검색을 섞은 **하이브리드 검색** 도 지원한다.

---

## 7. 시계열 데이터베이스 (Time-series)

**시간 순서로 쌓이는 측정값** 에 특화된 DB다.

- e.g. 서버 CPU 사용률(1초마다), 주가, IoT 센서 온도, 앱 응답 시간
- 쓰기가 끊임없이 들어오고, "최근 1시간 평균", "일별 최대값"처럼 **시간 구간으로 묶어 집계** 하는 조회가 많다.
- 오래된 데이터는 자동으로 요약하거나 지우는 기능(보존 정책)이 있다.
- 종류 : **InfluxDB**, **TimescaleDB**(PostgreSQL 확장), **Prometheus**(모니터링 지표 수집)

---

## 8. 분석용 데이터베이스 (OLAP)

| 구분 | OLTP (Online Transaction Processing)         | OLAP (Online Analytical Processing)                |
| ---- | -------------------------------------------- | -------------------------------------------------- |
| 목적 | 서비스 운영 (주문, 회원가입)                 | 분석 (매출 통계, 사용자 행동 분석)                 |
| 쿼리 | 몇 개의 행을 빠르게 읽고 씀                  | 수억 개의 행을 훑어 집계                           |
| 저장 | 행 단위 저장                                 | **열(column) 단위 저장** → 필요한 열만 읽어 빠름   |
| 예시 | PostgreSQL, MySQL                            | ClickHouse, BigQuery, Snowflake, Redshift, DuckDB  |

- 운영 DB에서 무거운 통계 쿼리를 돌리면 서비스가 느려지므로, 데이터를 **데이터 웨어하우스(OLAP DB)** 로 옮겨서 분석한다.
- **DuckDB** 는 "분석용 SQLite"로 불리며, 서버 없이 노트북에서 대용량 CSV·Parquet 파일을 SQL로 바로 분석할 수 있어 인기가 높다.

---

## 9. 벡터 데이터베이스 (Vector)

AI 시대에 새로 떠오른 DB다. 텍스트·이미지를 AI 모델로 **임베딩(embedding, 의미를 담은 숫자 배열)** 해서 저장하고, **의미가 비슷한 데이터** 를 찾는다.

```
"강아지 사료 추천"  → [0.12, -0.83, 0.45, ...]   ← 1,536개의 숫자
"반려견 먹이 고르는 법" → [0.11, -0.80, 0.47, ...]   ← 단어는 달라도 벡터가 가까움
```

- 키워드가 정확히 일치하지 않아도 **뜻이 비슷하면** 찾아 준다.
- 수백만 개의 벡터 중 가까운 것을 빠르게 찾기 위해 근사 최근접 이웃(ANN, e.g. HNSW) 색인을 쓴다.
- 용도
  - **RAG(검색 증강 생성)** : 사내 문서 중 질문과 관련된 내용을 찾아 AI에게 함께 전달
  - 의미 기반 검색, 비슷한 상품·이미지 추천, 중복 탐지
- 종류
  - 전용 DB : Pinecone, Qdrant, Weaviate, Milvus, Chroma
  - 기존 DB의 확장 기능 : **pgvector**(PostgreSQL), MongoDB·Elasticsearch·Redis의 벡터 검색
  - 데이터가 아주 많지 않다면, 전용 DB를 새로 두기보다 **이미 쓰는 DB의 벡터 기능** 으로 시작하는 경우가 많다.

## 10. 알아 두면 좋은 개념

### 10.1 확장 방법 : 수직 확장 vs 수평 확장

- **수직 확장(Scale-up)** : 서버 한 대의 CPU·메모리를 키운다. 간단하지만 한계와 비용이 있다.
- **수평 확장(Scale-out)** : 서버 대수를 늘린다.
  - **복제(Replication)** : 같은 데이터를 여러 서버에 복사. 보통 쓰기는 주(Primary) 서버, 읽기는 복제(Replica) 서버로 나눠 부하 분산
  - **샤딩(Sharding)** : 데이터를 기준(e.g. 사용자 ID)에 따라 여러 서버에 **나눠** 저장

### 10.2 CAP 정리

분산 시스템은 네트워크가 끊기는 상황(Partition)이 생기면, 다음 둘 중 하나를 포기해야 한다.

- `Consistency(일관성)` : 모든 서버가 항상 같은 최신 데이터를 보여 줌
- `Availability(가용성)` : 일부 서버에 문제가 있어도 항상 응답함
- `Partition tolerance(분할 내성)` : 네트워크가 끊겨도 시스템이 동작함 (분산 시스템이라면 사실상 필수)

→ 그래서 분산 DB는 **CP(일관성 우선, e.g. 은행)** 나 **AP(가용성 우선, e.g. SNS 좋아요 수)** 쪽으로 성향이 나뉜다.

### 10.3 ACID vs BASE

- **ACID** : 정확성 우선 (전통적인 RDBMS)
- **BASE** : 가용성·확장성 우선 (많은 NoSQL)
  - `Basically Available` : 기본적으로 항상 응답한다.
  - `Soft state` : 데이터 상태가 시간에 따라 바뀔 수 있다.
  - `Eventually consistent(최종적 일관성)` : 잠시 서버마다 값이 다를 수 있지만, **결국에는** 같아진다.
    - e.g. 좋아요를 눌렀는데 다른 사람 화면에는 몇 초 뒤에 반영
- 요즘은 경계가 흐려져서, NoSQL도 트랜잭션을 지원하고 RDBMS도 분산을 지원한다.

## 11. 어떤 DB를 골라야 할까?

```
처음 시작하는 서비스인가?
└─ 대부분의 경우 → PostgreSQL ✅ (또는 MySQL)
     관계형 + JSON + 전문 검색 + 벡터 검색까지 하나로 시작할 수 있다.

그 다음, 필요해질 때 목적별 DB를 추가한다.
├─ 응답 속도·캐시·세션·순위표 → Redis / Valkey
├─ 구조가 제각각인 데이터, 문서 단위 읽기·쓰기 → MongoDB, Firestore
├─ 쓰기가 폭발적으로 많고 규모가 매우 큼 → Cassandra, ScyllaDB, DynamoDB
├─ 관계 탐색(추천, 친구, 경로)이 핵심 → Neo4j
├─ 검색 품질이 중요(형태소, 자동 완성, 오타) → Elasticsearch, OpenSearch, Meilisearch
├─ 모니터링 지표·센서 데이터 → InfluxDB, TimescaleDB, Prometheus
├─ 대용량 통계·분석 → ClickHouse, BigQuery, DuckDB
└─ AI 의미 검색·RAG → pgvector로 시작, 규모가 커지면 전용 벡터 DB
```

- **"유행하는 DB"보다 "데이터의 모양과 쿼리 패턴"으로 고르자.**
  - 데이터 사이의 관계가 많고 정확성이 중요하다 → 관계형
  - 한 덩어리로 읽고 쓰고, 구조가 자주 바뀐다 → 문서형
- DB를 하나 추가할 때마다 **운영(백업, 모니터링, 장애 대응)과 데이터 동기화 부담** 도 함께 늘어난다는 점을 잊지 말자.

## 0. 한눈에 보기

앱을 만드는 방법은 크게 **네이티브, 크로스 플랫폼, 웹 기반** 세 가지로 나뉜다.

| 방식                 | 대표 기술                                         | 언어                      | 한 번 작성으로             | 성능·네이티브 기능 | 개발 속도 |
| -------------------- | ------------------------------------------------- | ------------------------- | -------------------------- | ------------------ | --------- |
| **네이티브**         | Android(Jetpack Compose), iOS(SwiftUI)            | Kotlin, Swift             | 한 플랫폼                  | ⭐⭐⭐              | ⭐        |
| **크로스 플랫폼**    | **React Native**, **Flutter**, Kotlin Multiplatform | TypeScript, Dart, Kotlin | iOS + Android (+ 웹·데스크톱) | ⭐⭐               | ⭐⭐⭐     |
| **웹 기반 (하이브리드)** | Capacitor, Ionic, PWA                         | HTML·CSS·JS              | 웹 + iOS + Android         | ⭐                 | ⭐⭐⭐     |
| **데스크톱**         | Electron, Tauri, Flutter, 네이티브                | JS·TS, Rust, Dart, C# 등  | Windows + macOS + Linux    | 기술마다 다름      | -         |

- 정답은 없다. **팀이 아는 언어, 필요한 성능, 플랫폼 수, 일정** 에 따라 고른다.
- 웹 프론트엔드 개발자라면 **React Native(모바일)** 와 **Electron·Tauri(데스크톱)** 가 가장 진입하기 쉽다.

## 1. 앱 개발 방식 이해하기

### 1.1 네이티브 앱

각 플랫폼 회사가 제공하는 **공식 언어와 도구로** 만드는 앱이다.

- Android : **Kotlin** + Android Studio
- iOS : **Swift** + Xcode (Mac 필요)
- 장점 : 가장 좋은 성능, 새 OS 기능을 바로 사용, 플랫폼다운 사용자 경험
- 단점 : iOS와 Android를 **각각 따로** 만들어야 한다. → 개발 인력과 시간이 두 배

### 1.2 크로스 플랫폼 앱

**하나의 코드로 iOS와 Android 앱을 함께** 만든다. 화면을 그리는 방식에 따라 나뉜다.

| 방식                         | 설명                                                         | 예시                                   |
| ---------------------------- | ------------------------------------------------------------ | -------------------------------------- |
| **네이티브 UI 사용**         | 내 코드가 각 플랫폼의 **진짜 네이티브 UI 컴포넌트** 를 그린다 | React Native                           |
| **자체 렌더링 엔진**         | 플랫폼 UI를 쓰지 않고, 앱이 **화면의 모든 픽셀을 직접** 그린다 | Flutter, Compose Multiplatform         |
| **비즈니스 로직만 공유**     | 데이터·네트워크 로직은 공유하고, UI는 각 플랫폼 네이티브로    | Kotlin Multiplatform                   |

### 1.3 웹 기반 앱

- **하이브리드 앱** : 웹 기술(HTML·CSS·JS)로 만든 화면을 앱 안의 **WebView** 로 띄우고, 앱 스토어에 배포한다. (Capacitor, Ionic)
  - 기존 웹 서비스를 빠르게 앱으로 만들 때 좋지만, 복잡한 화면은 네이티브보다 덜 부드러울 수 있다.
- **PWA(Progressive Web App)** : 앱 스토어 없이, 웹사이트를 홈 화면에 **설치** 해서 앱처럼 쓰게 한다.
  - 오프라인 지원, 푸시 알림 가능 (iOS도 홈 화면에 설치한 웹 앱에서 웹 푸시 지원)
  - 단, 블루투스·결제 등 일부 기기 기능과 스토어 노출에는 한계가 있다.

## 2. React Native

**React와 JavaScript/TypeScript로 iOS·Android 앱을 만드는** 메타(페이스북)의 오픈소스 프레임워크다. (2015년 공개)

```tsx
import { Text, View, Pressable } from 'react-native'

export default function App() {
  return (
    <View style={{ flex: 1, alignItems: 'center', justifyContent: 'center' }}>
      <Text>안녕하세요!</Text>
      <Pressable onPress={() => alert('눌렀다')}>
        <Text>버튼</Text>
      </Pressable>
    </View>
  )
}
```

- `<div>` 대신 `<View>`, `<p>` 대신 `<Text>`처럼 **네이티브 컴포넌트** 를 쓰지만, 컴포넌트·Hooks·상태 관리 등 **React 지식을 그대로** 쓸 수 있다.
- **Expo** : React Native 공식 문서가 권장하는 프레임워크. 빌드, 기기 테스트, 앱 스토어 배포, 무선 업데이트(OTA)를 쉽게 해 준다. 처음 시작한다면 Expo로 시작하자.
- **New Architecture** : 0.76 버전(2024)부터 기본으로 켜진 새 구조. JS와 네이티브 사이의 통신 병목(Bridge)을 없애 성능이 크게 좋아졌다.
- 장점 : 웹 개발자가 진입하기 쉽다, npm 생태계, 웹(React)과 코드·인력 공유
- 단점 : 복잡한 애니메이션이나 특수한 네이티브 기능은 네이티브 코드를 직접 다뤄야 할 수 있다.
- 사용 사례 : 메타의 앱 일부, Shopify, Discord, 국내 다수 스타트업

cf. [React Native 시리즈](/mobile/react-native)

## 3. Flutter

**구글의 Dart 언어 기반 크로스 플랫폼 UI 프레임워크** 다. (2017년 공개, 2018년 1.0)

```dart
import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: HomePage()));

class HomePage extends StatelessWidget {
  const HomePage({super.key});

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: Center(child: Text('안녕하세요!')),
    );
  }
}
```

- 화면의 모든 것을 **위젯(Widget)** 으로 조립한다.
- 플랫폼 UI를 쓰지 않고 **자체 렌더링 엔진(Impeller)** 으로 직접 그려서, iOS와 Android에서 **모양과 동작이 똑같고** 애니메이션이 부드럽다.
- 하나의 코드로 **모바일 + 웹 + Windows·macOS·Linux 데스크톱** 까지 지원한다.
- **핫 리로드** : 코드를 고치면 앱 상태를 유지한 채 즉시 반영
- 장점 : 일관된 디자인, 높은 렌더링 성능, 풍부한 기본 위젯(Material, Cupertino)
- 단점 : Dart를 새로 배워야 한다, 앱 크기가 비교적 크다, 플랫폼 고유의 느낌을 내려면 추가 작업이 필요
- 사용 사례 : 구글 앱 일부, BMW, 토스·당근 등 국내 서비스 일부 화면

cf. [Flutter 시리즈](/mobile/flutter/01-intro), [Dart 문법](/languages/dart/01-basic)

## 4. React Native vs Flutter

| 구분              | React Native                                 | Flutter                                     |
| ----------------- | -------------------------------------------- | ------------------------------------------- |
| 만든 곳           | 메타                                         | 구글                                        |
| 언어              | JavaScript / TypeScript                      | Dart                                        |
| UI                | 플랫폼 **네이티브 컴포넌트**                 | **자체 렌더링** (위젯)                      |
| 플랫폼마다 모양   | 플랫폼다운 모양 (iOS는 iOS답게)              | 어디서나 똑같은 모양                        |
| 생태계            | npm, React 생태계 공유                       | pub.dev 패키지                              |
| 웹 개발자 진입    | 쉬움 ✅                                      | Dart 학습 필요                              |
| 데스크톱·웹       | 커뮤니티·마이크로소프트 확장(Windows, macOS) | 공식 지원                                   |
| 잘 맞는 팀        | React 웹 개발자가 있는 팀                    | 디자인 일관성이 중요하고 앱 중심인 팀       |

## 5. Android 네이티브

- 언어 : **Kotlin** (구글 공식 권장 언어, 예전에는 Java)
- UI : **Jetpack Compose** (선언형 UI, 지금의 표준) — 예전에는 XML 레이아웃
- 도구 : **Android Studio**
- 배포 : **Google Play** (개발자 등록비 1회 $25), 국내 원스토어 등
- 국내 스마트폰 사용자 중 Android 비중이 높아 국내 서비스에서는 특히 중요하다.

## 6. iOS 네이티브

- 언어 : **Swift** (예전에는 Objective-C)
- UI : **SwiftUI** (선언형 UI) — 예전 방식은 UIKit
- 도구 : **Xcode** (macOS에서만 실행 가능 → **iOS 앱 빌드에는 Mac이 필요** 하다. 크로스 플랫폼도 마찬가지이며, Expo EAS 같은 클라우드 빌드로 대신할 수 있다)
- 배포 : **App Store** (Apple Developer Program 연 $99), 심사가 비교적 엄격하다.

> 💡 Jetpack Compose와 SwiftUI는 React·Flutter처럼 **"상태가 바뀌면 화면이 다시 그려지는" 선언형 UI** 다. 하나를 익히면 나머지도 개념이 비슷하다.

### 6.1 Kotlin Multiplatform

- JetBrains가 만든 기술로, **Kotlin으로 작성한 비즈니스 로직을 Android·iOS가 공유** 한다.
- UI까지 공유하고 싶다면 **Compose Multiplatform** 으로 iOS 화면도 Compose로 만들 수 있다.
- 기존 네이티브 앱에 **조금씩 도입** 할 수 있어, 네이티브 팀이 있는 회사에서 주목받고 있다.

## 7. 데스크톱 앱

| 기술                         | 구조                                              | 장점                                         | 단점                                   | 사용 사례                                  |
| ---------------------------- | ------------------------------------------------- | -------------------------------------------- | -------------------------------------- | ------------------------------------------ |
| **Electron**                 | **Chromium(브라우저) + Node.js** 를 앱에 포함     | 웹 기술 그대로, 가장 성숙한 생태계           | 앱 용량·메모리 사용량이 큼             | VS Code, Slack, Discord, Notion, Figma(데스크톱) |
| **Tauri**                    | 운영체제의 **기본 웹뷰** + **Rust** 백엔드        | 앱 크기가 매우 작고 가벼움, 보안 설계        | Rust 학습, OS별 웹뷰 차이 고려         | 점점 늘어나는 중 (v2부터 모바일도 지원)    |
| **Flutter**                  | 자체 렌더링                                       | 모바일과 코드 공유                           | 데스크톱 생태계는 아직 작음            | 일부 사내 도구                             |
| **React Native Windows/macOS** | 마이크로소프트가 관리하는 RN 확장              | React로 네이티브 데스크톱 UI                 | 자료가 적음                            | 마이크로소프트 일부 앱                     |
| **.NET MAUI / WinUI**        | C#·.NET                                           | 윈도우와 깊은 통합                           | macOS·Linux 지원 제한                  | 기업용 윈도우 앱                           |
| **네이티브**                 | Swift(AppKit/SwiftUI), C++(Qt) 등                 | 최고 성능                                    | 플랫폼마다 따로 개발                   | 전문 소프트웨어                            |

### 7.1 Electron

- 웹 페이지(HTML·CSS·JS)를 **데스크톱 앱 창으로 띄우는** 프레임워크다. GitHub이 Atom 에디터를 만들며 시작했다.
- **Main 프로세스(Node.js)** 가 창 관리·파일 시스템 등 OS 기능을 맡고, **Renderer 프로세스(웹 페이지)** 가 화면을 그린다. 둘은 IPC로 통신한다.
- React, Vue 등 **이미 아는 웹 프레임워크를 그대로** 쓸 수 있다.
- 단점은 앱마다 크롬 브라우저 하나를 통째로 넣기 때문에 **용량(100MB 이상)과 메모리** 를 많이 쓴다는 것이다.
- 보안 : Renderer에서 Node.js 기능을 직접 쓰지 않도록(contextIsolation, preload) 설정하는 것이 중요하다.

### 7.2 Tauri

- Electron처럼 웹 기술로 화면을 만들지만, 브라우저를 포함하지 않고 **OS에 이미 있는 웹뷰** 를 사용한다. 백엔드 로직은 **Rust** 로 작성한다.
- 그래서 **앱 크기가 수 MB 수준** 으로 작고 메모리도 적게 쓴다.
- Tauri 2.0(2024)부터는 **iOS·Android 앱도** 같은 방식으로 만들 수 있다.
- 단점 : OS마다 웹뷰가 달라서(Windows는 WebView2, macOS는 WebKit) 화면이 조금씩 다를 수 있다.

## 8. 무엇을 골라야 할까?

```
웹(React) 개발자이고, 모바일 앱을 빠르게 만들고 싶다
└─ React Native + Expo ✅

디자인을 플랫폼 상관없이 똑같이 맞추고, 모바일·데스크톱을 함께 만들고 싶다
└─ Flutter

최고의 성능, 최신 OS 기능, 플랫폼다운 경험이 꼭 필요하다 (카메라·AR·게임·금융 보안 등)
└─ 네이티브 (Kotlin + Jetpack Compose / Swift + SwiftUI)
   └─ 두 플랫폼의 로직만이라도 공유하고 싶다 → Kotlin Multiplatform

이미 웹 서비스가 있고, 앱 스토어에 빠르게 올리고 싶다
└─ Capacitor (하이브리드) 또는 PWA

데스크톱 앱
├─ 웹 기술로 빠르게, 생태계가 중요 → Electron
├─ 가볍고 작은 앱 → Tauri
└─ 모바일과 코드 공유 → Flutter
```

### 8.1 앱 개발에서 웹과 다른 점

- **스토어 심사** : 배포할 때마다 심사를 거친다. 버그를 고쳐도 즉시 반영되지 않을 수 있다. (Expo 등의 OTA 업데이트로 JS 코드는 심사 없이 갱신 가능한 경우가 있다)
- **버전 파편화** : 사용자가 앱을 업데이트하지 않으면 **옛날 버전이 계속 쓰인다.** 서버 API는 하위 호환을 오래 유지해야 한다.
- **기기 권한** : 카메라, 위치, 알림 등은 사용자에게 권한을 요청해야 한다.
- **푸시 알림** : Android는 FCM, iOS는 APNs를 통해 보낸다.
- **개발 환경** : iOS는 Mac과 Xcode, Android는 Android Studio가 필요하다.

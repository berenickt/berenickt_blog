## 1. 와이어샤크란?

**네트워크에서 오가는 패킷을 실시간으로 포착(capture)하고 분석하는 도구** 다. 무료 오픈소스이며 Windows, macOS, Linux에서 쓸 수 있다.

- 이름은 **wire(통신선) + shark(상어)** 다. 피 한 방울도 감지하는 상어처럼 통신선 위의 데이터를 샅샅이 들여다본다는 뜻으로 이해하면 쉽다.
- 개발·운영에서는 이럴 때 쓴다.
  - API 요청이 실제로 어떤 모양으로 나가는지, 응답이 왜 느린지 확인
  - "연결이 안 돼요", "인증서 오류가 나요" 같은 네트워크·TLS 문제 원인 찾기
  - TCP 연결, 재전송, DNS 조회 등 **눈에 보이지 않던 통신 과정을 직접 보며** 네트워크 공부

> 💡 **패킷(packet)** 이란?
> 네트워크에서 주고받는 데이터를 잘게 나눈 **기본 전송 단위** 다. 큰 파일도 수많은 패킷으로 쪼개져 전달된 뒤 다시 합쳐진다.

설치 방법, 화면 구성, 필터 사용법, TCP·HTTP 분석 실습은 [실습으로 복습하는 네트워크(와이어샤크)](/cs/network/06-wireshark)에 자세히 정리해 두었다. 이 글은 **HTTP와 HTTPS(TLS)를 비교해서 보는 것** 에 집중한다.

> ⚠️ 패킷 캡처는 **내 컴퓨터, 또는 분석 권한이 있는 네트워크에서만** 하자. 다른 사람의 통신을 허락 없이 엿보는 것은 불법이 될 수 있다.

## 2. 기본 용어

| 용어                  | 의미                                                              |
| --------------------- | ----------------------------------------------------------------- |
| `Source (src)`        | 패킷을 보낸 곳 (출발지 IP·포트)                                   |
| `Destination (dst)`   | 패킷을 받는 곳 (목적지 IP·포트)                                   |
| `Protocol`            | 패킷의 프로토콜 (TCP, UDP, DNS, HTTP, TLS, QUIC …)               |
| `Length`              | 패킷 크기 (바이트)                                                |
| `Info`                | 패킷 요약 (e.g. `GET /index.html`, `Client Hello`)               |

### 2.1 포트 번호 : 80과 443

- **포트** 는 한 컴퓨터 안에서 어떤 프로그램(서비스)과 통신할지 구분하는 번호다. `0 ~ 65535` 범위다.
- 잘 알려진 포트
  - `80` : **HTTP**
  - `443` : **HTTPS** (HTTP/3라면 UDP 443)
  - `53` : DNS, `22` : SSH
- 브라우저 주소에서 기본 포트는 **생략** 할 수 있다.
  - `http://example.com` = `http://example.com:80`
  - `https://example.com` = `https://example.com:443`

## 3. HTTP vs HTTPS : 와이어샤크로 보면

### 3.1 HTTP : 내용이 그대로 보인다

`http://`로 시작하는 사이트에 접속하면서 캡처하고, 필터에 `http`를 입력해 보자.

```
GET /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

id=myid&password=mypassword1234     ← 그대로 보인다!
```

- 요청 주소, 헤더, 쿠키, 그리고 **폼에 입력한 아이디·비밀번호까지 평문(plain text)** 으로 보인다.
- 같은 네트워크(공용 와이파이 등)에 있는 누군가가 이 패킷을 가로채면 그대로 읽을 수 있다. → **도청**
- 중간에서 내용을 바꿔치기할 수도 있다. → **변조**

### 3.2 HTTPS : 내용이 암호화되어 보이지 않는다

이번에는 `https://` 사이트에 접속하면서 캡처하고, 필터에 `tls`를 입력해 보자.

```
TLSv1.3   Client Hello (SNI=example.com)
TLSv1.3   Server Hello, Change Cipher Spec, Application Data
TLSv1.3   Application Data          ← 실제 요청·응답 (암호화되어 읽을 수 없음)
TLSv1.3   Application Data
```

- 실제 HTTP 요청·응답은 **`Application Data`** 라는 이름의 **암호화된 데이터** 로만 보인다. 주소 경로, 헤더, 비밀번호 모두 알 수 없다.
- 하지만 **완전히 아무것도 안 보이는 것은 아니다.**
  - 누가 누구와(IP 주소), 언제, 얼마나 많은 데이터를 주고받는지
  - 접속하려는 **도메인 이름** (Client Hello의 **SNI** 필드, DNS 조회)
  - 이 정보를 숨기기 위해 DNS over HTTPS, Encrypted Client Hello(ECH) 같은 기술이 도입되고 있다.

| 구분                | HTTP                       | HTTPS                                          |
| ------------------- | -------------------------- | ---------------------------------------------- |
| 기본 포트           | 80                         | 443                                            |
| 데이터              | 평문 (그대로 보임)         | **TLS로 암호화**                               |
| 도청                | 가능                       | 불가능 (내용을 읽을 수 없음)                   |
| 변조                | 가능                       | 감지됨 (무결성 검증)                           |
| 서버 신원 확인      | 없음                       | **인증서** 로 진짜 서버인지 확인               |
| 와이어샤크 필터     | `http`                     | `tls`                                          |

## 4. SSL과 TLS

- **SSL(Secure Sockets Layer)** : 넷스케이프가 1990년대에 만든 암호화 프로토콜. SSL 2.0, 3.0은 보안 취약점 때문에 **지금은 사용 금지** 다.
- **TLS(Transport Layer Security)** : SSL을 표준화·개선한 후속 프로토콜. 현재는 **TLS 1.2와 TLS 1.3** 을 쓴다. (TLS 1.0, 1.1도 폐기)
- 습관적으로 "SSL 인증서", "SSL/TLS"라고 부르지만, **실제로 쓰이는 것은 TLS** 다.
- **HTTPS = HTTP + TLS** : HTTP 메시지를 TLS로 암호화해서 보낸다.

```
HTTP                HTTPS
─────────           ─────────
HTTP                HTTP
TCP                 TLS      ← 암호화 계층
IP                  TCP
                    IP
```

TLS가 제공하는 세 가지

- **기밀성(암호화)** : 중간에서 엿봐도 내용을 읽을 수 없다.
- **무결성** : 중간에서 내용을 바꾸면 알아챈다.
- **인증** : 인증서로 "내가 접속한 곳이 진짜 `example.com`이 맞다"는 것을 확인한다.

## 5. TLS 핸드셰이크 살펴보기

HTTPS 통신은 데이터를 보내기 전에 **TLS 핸드셰이크** 로 "어떤 암호를 쓸지, 어떤 키로 암호화할지"를 먼저 정한다.
와이어샤크에서 필터 `tls.handshake`를 입력하면 이 과정만 볼 수 있다.

### 5.1 TLS 1.3 흐름

```
클라이언트(브라우저)                                    서버
      │ ── TCP 3-way handshake (SYN, SYN-ACK, ACK) ─────▶ │
      │                                                   │
      │ ── Client Hello ────────────────────────────────▶ │  지원하는 TLS 버전·암호 목록, 키 교환 값, SNI(도메인)
      │ ◀─────────────────────────────────── Server Hello ─│  선택한 암호, 서버의 키 교환 값
      │ ◀──── (암호화) Certificate, Certificate Verify ────│  서버 인증서와 서명
      │ ◀────────────────────────────── (암호화) Finished ─│
      │ ── (암호화) Finished ───────────────────────────▶ │
      │                                                   │
      │ ◀════════ Application Data (암호화된 HTTP) ══════▶ │
```

| 단계                 | 내용                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------ |
| **Client Hello**     | 클라이언트가 지원하는 TLS 버전, 암호 방식(cipher suite) 목록, 키 교환용 값, 접속할 도메인(SNI)을 보냄 |
| **Server Hello**     | 서버가 사용할 TLS 버전과 암호 방식을 고르고, 자신의 키 교환 값을 보냄                      |
| 키 생성              | 양쪽이 주고받은 값으로 **같은 세션 키** 를 각자 계산 (키 자체는 네트워크로 오가지 않음)    |
| **Certificate**      | 서버가 인증서를 보내고, 브라우저는 신뢰하는 인증기관(CA)이 서명했는지, 도메인이 맞는지, 만료되지 않았는지 확인 |
| **Finished**         | 핸드셰이크가 변조 없이 끝났는지 서로 확인                                                  |
| **Application Data** | 이후 모든 HTTP 데이터는 세션 키로 암호화되어 오감                                          |

- **TLS 1.3** 은 핸드셰이크를 **한 번의 왕복(1-RTT)** 으로 줄여, TLS 1.2(2-RTT)보다 연결이 빠르다.
- TLS 1.3에서는 **인증서도 암호화되어** 전송되므로, 와이어샤크에서 인증서 내용이 보이지 않는다. (TLS 1.2에서는 Certificate 메시지가 그대로 보였다)
- 키 교환에는 **(EC)DHE** 방식을 써서, 나중에 서버의 개인 키가 유출되더라도 과거 통신을 풀 수 없다. (**전방향 안전성**, Forward Secrecy)

### 5.2 HTTP/3는 QUIC으로

- 최신 브라우저와 큰 사이트는 **HTTP/3** 를 쓰는 경우가 많다. HTTP/3는 TCP가 아니라 **UDP 기반의 QUIC** 위에서 동작하고, TLS 1.3이 QUIC 안에 들어 있다.
- 그래서 `tls` 필터로 아무것도 안 보인다면 **`quic`** 필터로 확인해 보자.

## 6. 내 HTTPS 통신 복호화해서 보기

개발 중에 **내 브라우저가 보내는 HTTPS 요청 내용** 을 와이어샤크로 보고 싶다면, 브라우저가 사용한 세션 키를 파일로 남기게 해서 복호화할 수 있다.

```bash
# macOS / Linux : 환경 변수를 설정한 터미널에서 브라우저 실행
export SSLKEYLOGFILE=~/tls-keys.log
open -a "Google Chrome"     # macOS (Linux는 google-chrome)
```

1. 와이어샤크 **Preferences → Protocols → TLS → (Pre)-Master-Secret log filename** 에 `~/tls-keys.log` 지정
2. 다시 캡처하면 `Application Data` 대신 **복호화된 HTTP/2·HTTP/3 내용** 이 보인다.

> ⚠️ 이 키 파일이 있으면 그 기간의 HTTPS 통신을 모두 읽을 수 있다. **학습·디버깅이 끝나면 환경 변수를 지우고 파일을 삭제** 하자.

> 💡 사실 내 요청 내용을 보는 것만이 목적이라면 **브라우저 개발자 도구의 Network 탭** 이 훨씬 간단하다.
> 와이어샤크는 TCP·TLS 같은 **더 아래 계층** 에서 무슨 일이 일어나는지 볼 때 쓰자.

## 7. 자주 쓰는 표시 필터

| 필터                                  | 보여 주는 것                                   |
| ------------------------------------- | ---------------------------------------------- |
| `http`                                | 평문 HTTP 요청·응답                            |
| `tls`                                 | TLS(HTTPS) 패킷                                |
| `tls.handshake.type == 1`             | Client Hello만                                 |
| `tls.handshake.extensions_server_name contains "github"` | 특정 도메인(SNI)으로 가는 TLS 연결 |
| `quic`                                | HTTP/3 (QUIC) 패킷                             |
| `tcp.port == 443`                     | 443 포트(HTTPS) 통신                           |
| `ip.addr == 192.168.0.10`             | 특정 IP가 출발지 또는 목적지인 패킷            |
| `dns`                                 | DNS 조회 (도메인 → IP)                         |
| `tcp.analysis.retransmission`         | TCP 재전송 (네트워크가 불안정한지 확인)        |

- 필터는 `&&`(그리고), `||`(또는), `!`(아님)으로 조합할 수 있다. e.g. `tls && ip.addr == 192.168.0.10`

## 8. 와이어샤크 말고도 : TLS 문제를 확인하는 명령어

DevOps 실무에서 인증서·HTTPS 문제를 확인할 때는 터미널 도구도 많이 쓴다.

```bash
# 요청·응답 과정과 TLS 핸드셰이크 정보를 자세히 출력
curl -v https://example.com

# 서버 인증서 정보 (발급자, 유효 기간, 도메인) 확인
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -issuer -subject -dates
```

- 인증서 만료, 도메인 불일치, 중간 인증서(체인) 누락은 HTTPS 장애의 단골 원인이다.
- 웹에서 간단히 점검하려면 [SSL Labs Server Test](https://www.ssllabs.com/ssltest/)를 쓴다.
- 서버에서 직접 패킷을 캡처할 때는 `tcpdump`로 저장한 뒤(`tcpdump -i any -w capture.pcap port 443`) 와이어샤크로 열어 분석한다.

## 9. 정리

- 와이어샤크는 네트워크 패킷을 캡처해서 **통신 과정을 눈으로 확인** 하는 도구다.
- **HTTP는 모든 내용이 평문으로 보이고, HTTPS는 TLS로 암호화되어 `Application Data`로만 보인다.**
- HTTPS의 실체는 **TLS** 이며, 핸드셰이크(Client Hello → Server Hello → 인증서 확인 → 세션 키)로 안전한 통신 채널을 만든다.
- 그래서 지금의 웹은 **모든 사이트에 HTTPS가 기본** 이다.

## 1. 클라우드 제공업체

| 제공업체                      | 특징                                                                  |
| ----------------------------- | --------------------------------------------------------------------- |
| **AWS** (Amazon Web Services) | 시장 점유율 1위(약 30%). 서비스 종류와 자료·커뮤니티가 가장 많음      |
| **Microsoft Azure**           | 2위. 윈도우·오피스·Active Directory 등 마이크로소프트 생태계와 강하게 연동 |
| **Google Cloud (GCP)**        | 3위. 데이터 분석(BigQuery), 쿠버네티스(GKE), AI 분야에 강점           |
| 국내 클라우드                 | 네이버 클라우드, KT 클라우드, NHN 클라우드 등. 공공 분야(CSAP 인증)에서 많이 사용 |

- 세 클라우드 모두 기본 개념(가상 서버, 스토리지, 네트워크, 관리형 DB)은 비슷하다. **하나를 제대로 배우면 다른 곳으로 옮기기 쉽다.**
- 국내 채용 시장에서는 AWS 경험을 요구하는 경우가 가장 많다.
- 비용 감각 : 서버(EC2, RDS)는 **켜져 있는 시간만큼** 요금이 나간다. 쓰든 안 쓰든 켜 두면 돈이 나간다는 점을 기억하자. 정확한 금액은 [AWS 요금 계산기](https://calculator.aws/)로 확인한다.

## 2. 웹 배포에 꼭 필요한 AWS 서비스

| ------------------- | ----------------------------------- | ------------- | ----------------------- |
| **S3**              | 파일 저장소                         | 버킷(Bucket)  | 무제한 외장 하드        |
| **CloudFront**      | CDN (전 세계 캐시 서버)             | 배포(Distribution) | 동네마다 있는 편의점 창고 |
| **Route 53**        | DNS (도메인 → 주소 연결)            | 호스팅 영역   | 전화번호부              |
| **ACM**             | HTTPS 인증서 발급·관리              | 인증서        | 신분증                  |

| **ELB** (ALB)       | 로드 밸런서 (부하 분산)             | 로드 밸런서   | 손님을 빈 창구로 안내하는 직원 |
| **RDS**             | 관리형 데이터베이스                 | DB 인스턴스   | 관리인이 있는 창고      |

### 2.1 S3 (Simple Storage Service)

- **용량 제한 없이 파일(객체)을 저장하는 스토리지 서비스** (단위 : 버킷)
- 이미지, 동영상, 빌드 결과물(HTML·JS·CSS), 백업, 로그 등 무엇이든 저장
- 저장한 용량과 요청 수, 데이터 전송량만큼 과금된다. 표준 스토리지 기준 **GB당 월 몇 센트 수준** 으로 매우 저렴하다.
- **정적 웹사이트 호스팅** 기능이 있어서, 빌드한 프론트엔드 파일을 올리면 바로 웹사이트로 서비스할 수 있다.
- **스토리지 클래스** : 자주 안 읽는 데이터는 더 싼 클래스로 옮겨 비용을 줄인다.
  - `S3 Standard` : 자주 읽는 데이터
  - `S3 Intelligent-Tiering` : 접근 빈도에 따라 자동으로 클래스 이동
  - `S3 Glacier` 계열 : **장기 보관·백업용**(cf. Glacier = 빙하). 저장 비용은 매우 싸지만, 데이터를 꺼낼 때 비용과 시간(몇 분~몇 시간)이 든다.
  - 수명 주기(Lifecycle) 규칙으로 "30일 지나면 Glacier로 이동" 같은 자동화가 가능하다.

---

### 2.2 EC2 (Elastic Compute Cloud)

- **AWS 데이터센터의 컴퓨터를 가상 서버 형태로 빌려 쓰는 서비스** (단위 : 인스턴스)
  - cf. Elastic : "탄력적인" → 필요에 따라 늘리고 줄일 수 있다는 뜻
- 주로 백엔드 API 서버, SSR 프론트엔드 서버(Next.js 등)를 실행하는 데 쓰고, RDS 같은 DB와 연결한다.
- 인스턴스 유형 : `t`(범용·저렴, e.g. t3.micro), `m`(범용), `c`(CPU 중심), `r`(메모리 중심), `g`(GPU) 등
- **요금** : 켜져 있는 시간만큼 과금된다.
  - Linux 인스턴스는 **초 단위**(최소 1분)로 과금된다. (예전처럼 1시간 단위로 올림되지 않는다)
  - 10대를 1시간 돌리는 비용 ≈ 1대를 10시간 돌리는 비용 → 필요할 때 늘리고, 필요 없으면 줄이는 것이 핵심
  - 인스턴스를 **중지(Stop)** 해도 연결된 디스크(EBS)와 고정 IP(Elastic IP) 요금은 계속 나간다. 완전히 안 쓰면 **종료(Terminate)** 하자.
  - 퍼블릭 IPv4 주소에도 시간당 요금이 붙는다.
- 프리 티어 정책이 2025년에 크레딧 방식으로 바뀌는 등 자주 변하므로, 시작 전에 [AWS 프리 티어](https://aws.amazon.com/ko/free/) 페이지를 꼭 확인하자.

### 2.3 ELB (Elastic Load Balancing)

- 들어오는 요청을 **여러 EC2 인스턴스(또는 컨테이너)로 나눠 보내는 부하 분산 서비스** (단위 : 로드 밸런서)
- 여러 가용 영역(AZ)에 서버를 나눠 두면, 한쪽 데이터센터에 문제가 생겨도 서비스가 유지된다.
- 상태 검사(Health Check)로 **고장 난 서버에는 요청을 보내지 않는다.**
- 종류
  - `ALB`(Application Load Balancer) : HTTP/HTTPS 요청을 경로·호스트 기준으로 분배 ✅ 웹 서비스 대부분
  - `NLB`(Network Load Balancer) : TCP/UDP 수준의 초고성능 분배
- 함께 쓰는 **Auto Scaling** : CPU 사용률 등 기준에 따라 EC2 인스턴스 수를 자동으로 늘리고 줄인다.
  - 1차 대비책은 로드 밸런서(분산), 2차 대비책은 오토스케일링(증설)

### 2.4 CloudFront (CDN)

- AWS의 **CDN 서비스** (단위 : 배포)
- 전 세계 수백 곳의 **엣지 로케이션** 에 파일을 캐시해 두고, 사용자와 가장 가까운 곳에서 응답한다.
- 하는 일
  - 정적 파일(S3)을 빠르게 제공
  - 경로에 따라 요청을 다른 곳으로 분기 (e.g. `/api/*`는 로드 밸런서로, 나머지는 S3로)
  - HTTPS 적용(ACM 인증서), HTTP → HTTPS 리다이렉트
  - 원본 서버(EC2)의 부하 감소, DDoS 방어(AWS Shield 기본 포함)
- S3 버킷을 공개하지 않고 **CloudFront를 통해서만 접근** 하게 만들 수 있다. (OAC, Origin Access Control) ✅ 권장
- 캐시 때문에 배포 후 바로 반영되지 않을 수 있다 → 파일명 해시, 캐시 무효화(Invalidation)
- cf. Cloudflare 같은 다른 CDN도 많이 쓰인다. AWS 서비스와 함께 쓴다면 CloudFront가 연동이 편하다.

### 2.5 Route 53 (DNS)

- AWS의 **DNS 서비스** (단위 : 호스팅 영역)
- 구입한 도메인을 S3·CloudFront·ALB 등 AWS 서비스에 연결한다. 도메인 구입도 가능하다.
  - 단, 국내 업체보다 가격이 높을 수 있고, `.kr` 같은 일부 도메인은 구입할 수 없다. → 가비아 등 국내 업체에서 도메인을 사고 **네임서버만 Route 53으로 바꾸는** 방식이 흔하다.
- **Alias 레코드** : CloudFront·ALB·S3 같은 AWS 리소스를 도메인 루트(`example.com`)에 바로 연결할 수 있다. (일반 CNAME은 루트 도메인에 쓸 수 없다)
- 요금 : 호스팅 영역당 월 $0.50 + 쿼리 수에 따른 요금

| 레코드 | 의미                                         |
| ------ | -------------------------------------------- |
| A      | 도메인 → IPv4 주소                           |
| AAAA   | 도메인 → IPv6 주소                           |
| CNAME  | 도메인 → 다른 도메인 (별칭)                  |
| MX     | 메일 서버                                    |
| TXT    | 텍스트 (도메인 소유 확인, 메일 보안 설정 등) |
| NS     | 이 도메인을 관리하는 네임서버                |
| SOA    | 영역(zone)의 기본 정보                       |

### 2.6 ACM (AWS Certificate Manager)

- **HTTPS용 SSL/TLS 인증서를 발급하고 자동 갱신하는 서비스** (단위 : 인증서)
- CloudFront·ALB에 연결하는 **퍼블릭 인증서는 무료** 다.
- 발급 후 **도메인 소유권 검증** 을 해야 활성화된다. Route 53을 쓰면 DNS(CNAME) 검증 레코드를 버튼 하나로 만들 수 있다.
- ⚠️ **CloudFront에 쓸 인증서는 반드시 버지니아 북부(`us-east-1`) 리전** 에서 발급해야 한다. (ALB용은 ALB와 같은 리전)

### 2.7 RDS (Relational Database Service)

- MySQL, PostgreSQL, MariaDB 등을 **AWS가 관리해 주는 데이터베이스 서비스**
- 설치·백업·패치·장애 조치(Multi-AZ)를 AWS가 대신 해 준다.
- DB는 **프라이빗 서브넷** 에 두고, 같은 VPC 안의 서버만 접근하게 하자.
- 더 높은 성능과 자동 확장이 필요하면 **Aurora**, 서버리스가 필요하면 Aurora Serverless를 쓴다.

cf. 각 서비스의 자세한 내용은 [AWS](/devops/aws) 시리즈 참고 : [EC2](/devops/aws/03-ec2), [ELB](/devops/aws/05-elb), [Auto Scaling](/devops/aws/06-auto-scaling), [RDS](/devops/aws/07-rds), [S3](/devops/aws/08-s3), [CloudFront](/devops/aws/09-cloud-front), [Route 53](/devops/aws/10-route53), [IAM](/devops/aws/11-iam)

## 4. 배포 아키텍처 4단계

서비스 규모에 따라 아키텍처는 보통 다음 순서로 커진다. 회사마다 다를 수 있다.

> ⚠️ **처음부터 4단계로 가는 게 아니다.** 1·2단계로 시작해서, 접속량이 늘어 문제가 생기면 다음 단계로 넘어간다.
> 실제로 가장 많이 쓰이는 형태는 2단계다.

### 1단계 : 정적 페이지

```
사용자 → Route 53 → S3 (정적 웹사이트 호스팅)
```

- 회사 소개, 랜딩 페이지, 블로그처럼 **미리 만들어 둔 HTML** 만 보여 주는 경우
- 서버가 없어서 가장 싸고 단순하다.
- 한계 : 요청마다 다른 결과를 만들 수 없다.
  - DB 데이터를 보여 주거나, `/posts/123`처럼 **빌드 시점에 없던 경로(동적 라우팅)** 를 서버에서 처리할 수 없다.
  - 파일과 폴더 이름이 정확히 일치하는 경로만 응답한다. (그래서 Next.js `trailingSlash` 설정이 필요하다 → [Next.js Trailing Slash](/devops/next-trailing-slash))

### 2단계 : 서버 1대

```
사용자 → Route 53 → EC2 1대 (웹 서버 + API) → RDS
```

- 데이터가 필요한 페이지를 위해 결국 **서버** 가 필요하다.
- 한계 : 서버가 1대라서
  - 요청이 몰리면 느려지거나 멈춘다.
  - 서버가 고장 나면 서비스 전체가 멈춘다. (단일 장애점, SPOF)

### 3단계 : 로드 밸런서 + 여러 서버

```
사용자 → Route 53 → ALB ─┬→ EC2
                          ├→ EC2   (Auto Scaling)
                          └→ EC2
                               ↓
                              RDS
```

- 서버를 여러 대 두고 **로드 밸런서** 로 요청을 나눈다.
  - 분배 방식 : 라운드 로빈(순서대로), 최소 연결(가장 한가한 서버로) 등
- **Auto Scaling** : e.g. CPU 사용률이 70%를 넘으면 서버를 자동으로 추가하고, 줄어들면 다시 줄인다.
- 서버들을 여러 가용 영역(AZ)에 나눠 두어 데이터센터 장애에도 버틴다.
- 한계 : 서버가 많아지면서
  - 각 서버에 에러는 없는지, 앱이 잘 실행 중인지, 메모리가 급증하지 않는지 **모니터링** 해야 할 대상이 늘어난다.
  - 정적 파일 요청까지 모두 서버가 처리해서 비용이 커진다.
- 이 단계쯤부터 별도의 DevOps(인프라) 담당이 필요해진다.

### 4단계 : CDN으로 정적·동적 분리

```
사용자 → Route 53 → CloudFront ─┬→ S3          (정적 파일 : JS, CSS, 이미지, 정적 페이지)
                                 └→ ALB → EC2   (동적 요청 : API, SSR 페이지)
```

- 서버를 두는 이유는 **동적인 처리** 때문이다. 그렇다면 정적인 것은 서버에서 빼자.
- **CloudFront** 가 앞에서 요청을 분기한다.
  - 정적 파일 → **S3** (전 세계 엣지에 캐시되어 매우 빠름)
  - 동적 요청 → **ALB → EC2**
- 효과 : 서버 부하와 비용 감소, 응답 속도 향상, 서버가 잠시 멈춰도 정적 페이지는 계속 보임
- 모니터링할 대상을 완전히 없앨 수는 없지만, 서버가 처리할 일을 줄여 관리 부담을 낮춘다.

## 5. 프론트엔드 배포 방식별 요청 흐름

프론트엔드는 렌더링 방식(SSG, SSR, 혼합)에 따라 배포 구조가 달라진다. (cf. [CSR, SSR, SSG](/frontend/nextjs/00-csr-ssr-ssg))

### 5.1 정적 배포 (S3 + CloudFront) ✅

![정적 배포](https://raw.githubusercontent.com/berenickt/image-server/main/img/aws-service-distribution-2.png)

1. 사용자가 **Route 53** 에 도메인을 조회하면, Route 53은 **CloudFront** 주소를 알려 준다.
2. 사용자는 CloudFront에 접속하고, CloudFront는 캐시가 있으면 바로, 없으면 **S3** 에서 가져와 응답한다.

- CDN에 캐시된 파일이 빠르게 제공되므로, **마케팅 페이지·제품 목록처럼 모두에게 같은 화면을 보여 주는 서비스** 에 적합하다.
- HTTPS(ACM 인증서)를 적용할 수 있고, S3를 비공개로 두고 CloudFront로만 접근하게 할 수 있다.
- 단, 캐시된 파일이 보이므로 배포 후 바로 반영되지 않을 수 있다. → 파일명 해시 + `index.html` 캐시 짧게, 필요하면 캐시 무효화

### 5.2 S3 직접 접근 (CDN 없음)

![S3 직접 접근](https://raw.githubusercontent.com/berenickt/image-server/main/img/aws-service-distribution-3.png)

1. Route 53이 **S3 웹사이트 엔드포인트** 주소를 알려 주고, 사용자는 S3에 바로 접속한다.

- 캐시가 없어 S3의 변경 사항이 **즉시** 보이므로, 개발·테스트 단계에서는 편하다.
- 하지만 CDN이 없어 먼 곳의 사용자는 느리고, **S3 웹사이트 엔드포인트는 HTTPS를 지원하지 않는다.** 버킷도 공개해야 한다.
- → **운영 환경에서는 쓰지 않는 것이 좋다.**

### 5.3 정적 + 동적 혼합 (CloudFront 분기) ✅

![정적+동적 배포](https://raw.githubusercontent.com/berenickt/image-server/main/img/aws-service-distribution-1.png)

- SSG와 SSR을 섞어서 배포하는 방법 (4단계 아키텍처)
- S3에 올린 빌드 파일(JS·CSS·이미지, 미리 만든 페이지)은 CloudFront 캐시로 빠르게 보여 주고,
- 요청마다 달라지는 페이지와 API는 **EC2(서버)** 에서 SSR로 처리한다.
- 자주 바뀌지 않는 파일을 S3로 분리해 **서버 부하를 줄이고**, 안정적인 서비스와 비용 절감을 함께 얻는다.

> 💡 직접 구성이 부담된다면 **AWS Amplify Hosting** 이나 Vercel 같은 플랫폼이 이 구조(정적은 CDN, 동적은 서버리스 함수)를 자동으로 만들어 준다. → [프론트엔드 배포](/frontend/front-deploy)

## 6. 실습 : 단계별로 AWS에 프론트엔드 배포하기

> 콘솔 화면의 메뉴 이름과 위치는 자주 바뀐다. 아래 흐름을 이해하고, 화면은 그때그때 맞춰 따라가자.
> 시작 전에 루트 계정 MFA, 작업용 IAM 사용자, **결제 알림(Budget)** 부터 설정하자.

### 6.1 정적 사이트 빌드

Next.js를 정적 파일로 빌드한다.

```js
// next.config.js
module.exports = {
  output: 'export', // `next build` 시 out/ 폴더에 정적 파일 생성 (예전의 `next export` 명령은 제거됨)
  trailingSlash: true, // /about → /about/index.html 로 생성 (S3에서 경로를 찾기 위해)
  images: { unoptimized: true }, // 정적 export에서는 이미지 최적화 서버를 쓸 수 없음
}
```

```bash
npm run build   # → out/ 폴더 생성
```

cf. [Next.js Trailing Slash](/devops/next-trailing-slash)

### 6.2 S3 버킷에 업로드

1. S3 → **버킷 만들기**
   - 리전 : 아시아 태평양(서울) `ap-northeast-2`
   - 버킷 이름 : 아무 이름이나 가능 (S3 웹사이트 호스팅을 쓸 경우에만 도메인 이름과 같아야 함)
   - **퍼블릭 액세스 차단은 켜 둔 채로** 만든다. ✅ (CloudFront OAC로만 접근하게 할 것이므로)
2. `out/` 폴더 안의 파일을 업로드한다.
   - 콘솔에서 드래그 앤 드롭하거나, CLI로 `aws s3 sync ./out s3://버킷이름 --delete`

> 💡 예전 방식은 버킷의 퍼블릭 액세스를 풀고, ACL로 모든 파일을 공개한 뒤, **정적 웹사이트 호스팅** (인덱스 문서 `index.html`, 오류 문서 `404.html`)을 켜서 S3 주소로 접속하는 것이었다.
> 지금도 동작하지만 버킷 전체가 인터넷에 공개되고 HTTPS도 안 되므로, **비공개 버킷 + CloudFront** 방식을 권장한다.

### 6.3 HTTPS 인증서 발급 (ACM)

1. 리전을 **미국 동부(버지니아 북부) `us-east-1`** 로 바꾼다. ⚠️ 매우 중요 (CloudFront는 이 리전의 인증서만 사용)
2. ACM → **인증서 요청** → 퍼블릭 인증서 → 도메인 입력 (e.g. `example.com`, `*.example.com`)
3. 검증 방법 : **DNS 검증**
4. 인증서 상세 화면에서 **Route 53에서 레코드 생성** 버튼 클릭 → 검증용 CNAME 레코드가 자동으로 생성된다.
5. 몇 분 뒤 상태가 `검증 대기 중(Pending validation)` → `발급됨(Issued)`으로 바뀐다.

(도메인을 아직 Route 53에 연결하지 않았다면 6.5를 먼저 진행한다.)

### 6.4 CloudFront 배포 만들기

1. CloudFront → **배포 생성**
2. 원본(Origin) : 6.2에서 만든 **S3 버킷** 선택
   - 원본 액세스 : **OAC(Origin Access Control)** 생성 후 선택
   - 배포 생성 후 안내되는 **버킷 정책을 S3에 붙여 넣는다.** (CloudFront만 버킷을 읽을 수 있게 허용)
3. 뷰어 프로토콜 정책 : **Redirect HTTP to HTTPS**
4. 대체 도메인 이름(CNAME) : 사용할 도메인 입력 (e.g. `example.com`)
5. 사용자 정의 SSL 인증서 : 6.3에서 발급한 인증서 선택
6. 기본 루트 객체 : `index.html`
7. (선택) 오류 페이지 : 403·404 응답을 `/404.html`로 연결
8. 배포가 완료되면 `xxxx.cloudfront.net` 주소가 생긴다.

> 💡 OAC를 쓰면 S3 웹사이트 엔드포인트가 아니라 REST 엔드포인트를 쓰므로, 하위 폴더의 `index.html`(e.g. `/about/` → `/about/index.html`)을 자동으로 찾아 주지 않는다.
> 이 경우 **CloudFront Functions** 로 요청 경로 끝에 `index.html`을 붙여 주는 짧은 함수를 연결한다.

### 6.5 도메인 연결 (Route 53)

1. Route 53 → **호스팅 영역 생성** → 구입한 도메인 입력
   - NS(네임서버)와 SOA 레코드가 자동으로 생긴다.
2. 도메인을 산 업체(e.g. 가비아)에서 **네임서버를 Route 53의 NS 값 4개로 변경** 한다. (끝의 `.`은 빼고 입력)
3. 반영 확인 : `dig example.com NS` → `awsdns`가 들어간 네임서버가 보이면 성공 (몇 분~최대 48시간)
4. **A 레코드 생성** → **별칭(Alias)** 켜기 → 트래픽 라우팅 대상 : **CloudFront 배포** 선택
5. 브라우저에서 `https://example.com` 접속 → 🎉 HTTPS가 적용된 정적 사이트 완성 (1단계)

cf. 도메인 구입과 연결은 [도메인 등록 및 웹 분석 도구](/frontend/deploy/02-domain) 참고

### 6.6 EC2 서버 띄우기 (2단계)

SSR이나 API가 필요하면 서버가 있어야 한다.

1. 리전을 **서울** 로 바꾸고, EC2 → **인스턴스 시작**
   - AMI : **Amazon Linux 2023**
   - 인스턴스 유형 : `t3.micro` 등 작은 유형 (프리 티어 대상 여부 확인)
   - 키 페어 : 새로 만들어 안전하게 보관 (또는 키 없이 **EC2 Instance Connect / Session Manager** 로 접속)
   - 보안 그룹
     - SSH(22) : `0.0.0.0/0`(전체 공개) ❌ → **내 IP만** 허용하거나, Session Manager를 쓰면 아예 열지 않아도 된다.
     - 앱 포트(e.g. 3000) : 3단계부터는 로드 밸런서에서 오는 요청만 허용
2. 인스턴스에 접속해서 Node.js를 설치하고 앱을 실행한다.

```bash
# Amazon Linux 2023
sudo dnf install -y nodejs git
git clone https://github.com/<계정>/<저장소>.git && cd <저장소>
npm ci && npm run build

# 프로세스 매니저로 실행 (서버가 재시작돼도 자동 실행)
sudo npm install -g pm2
pm2 start npm --name web -- start
pm2 startup && pm2 save
```

3. `http://<EC2 퍼블릭 IP>:3000` 으로 접속 확인

> ⚠️ 인스턴스는 켜져 있는 동안 계속 과금된다. 실습이 끝나면 **종료(Terminate)** 하자.

### 6.7 로드 밸런서와 CloudFront 분기 (3·4단계)

1. **대상 그룹(Target Group)** 생성 → EC2 인스턴스 등록, 상태 검사 경로 설정 (e.g. `/api/health`)
2. **ALB 생성** → 퍼블릭 서브넷 2개 이상(서로 다른 AZ) 선택 → 리스너에서 대상 그룹으로 전달
   - HTTPS(443) 리스너를 쓰려면 **서울 리전** ACM 인증서가 필요하다.
3. EC2 보안 그룹을 **ALB 보안 그룹에서 오는 요청만** 허용하도록 수정
4. (선택) **Auto Scaling 그룹** : 시작 템플릿으로 EC2를 자동으로 늘리고 줄이기
5. **CloudFront에 원본 추가** : ALB를 두 번째 원본으로 추가하고, **동작(Behavior)** 으로 분기
   - `/api/*`, SSR 경로 → ALB (캐시 비활성화)
   - `/_next/static/*`, 이미지, 정적 페이지 → S3 (긴 캐시)
6. Route 53의 A 레코드는 그대로 CloudFront를 가리킨다. → 4단계 아키텍처 완성

> 💡 손으로 해 본 이 과정을 다음에는 **GitHub Actions(CI/CD)** 와 **Terraform(IaC)** 으로 자동화해 보자. → [DevOps 로드맵](/devops)

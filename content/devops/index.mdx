## 0. DevOps란?

**DevOps = Development(개발) + Operations(운영)**

예전에는 개발팀이 코드를 만들어 넘기면, 운영팀이 서버에 올리고 관리했다.
두 팀의 목표가 달랐기 때문에(개발팀은 "빨리 새 기능을", 운영팀은 "장애 없이 안정적으로") 배포는 느리고 갈등이 잦았다.

DevOps는 이 벽을 허물고 **"자주, 빠르게, 안전하게 배포하고 운영하자"** 는 문화이자, 그것을 가능하게 하는 도구·방법의 모음이다.

- **자동화** : 빌드·테스트·배포·인프라 구성을 사람이 손으로 하지 않는다. (CI/CD, IaC)
- **측정** : 서비스 상태를 숫자로 보고 판단한다. (모니터링, 로그)
- **공유와 협업** : 개발자도 운영을 이해하고, 운영자도 코드를 다룬다.
- **작고 잦은 변경** : 큰 배포를 가끔 하는 것보다, 작은 배포를 자주 하는 것이 더 안전하다.

> 💡 DevOps 팀이 잘하고 있는지 보는 대표 지표 (**DORA 지표**)
>
> - 배포 빈도 : 얼마나 자주 배포하나?
> - 변경 리드 타임 : 코드 커밋부터 운영 반영까지 얼마나 걸리나?
> - 변경 실패율 : 배포 중 장애로 이어지는 비율은?
> - 복구 시간 : 장애가 나면 얼마 만에 복구하나?

### 0.1 비슷한 직무들

| 직무                       | 초점                                                                  |
| -------------------------- | --------------------------------------------------------------------- |
| **DevOps 엔지니어**        | CI/CD, 인프라 자동화, 배포·운영 환경 구축                             |
| **클라우드 엔지니어**      | AWS·GCP 등 클라우드 인프라 설계·구축·비용 관리                         |
| **SRE** (Site Reliability Engineering) | 구글에서 시작. 소프트웨어 엔지니어링으로 **서비스 안정성** 을 책임 (SLO, 장애 대응) |
| **플랫폼 엔지니어**        | 개발자들이 셀프서비스로 배포·인프라를 쓸 수 있는 **내부 개발자 플랫폼(IDP)** 구축 |

회사마다 이름과 경계가 조금씩 다르지만, 필요한 기본기는 거의 같다.

## 2. 클라우드가 왜 생겼나

- 클라우드 등장 이전에는 어땠을까?
  - 서버를 직접 구매해 데이터센터(IDC)에 설치 → 구매·설치에 몇 주~몇 달
  - 트래픽이 몰릴 걸 대비해 서버를 넉넉히 사 두면, 평소에는 놀고 있는 서버에 돈을 낸다.
  - 하드웨어 고장, 전원, 냉각, 네트워크까지 직접 관리
- 클라우드는 어떤 불편함을 해소했나?
  - **필요할 때 몇 분 만에** 서버를 만들고, 쓴 만큼만 돈을 낸다.
  - 트래픽에 따라 서버를 늘리고 줄일 수 있다. (오토스케일링)
  - DB, 스토리지, CDN 같은 기능을 서비스 형태로 바로 사용
- 서비스 모델 : **IaaS**(가상 서버를 빌림, e.g. EC2) → **PaaS**(실행 환경을 빌림, e.g. Elastic Beanstalk) → **SaaS**(완성된 소프트웨어를 빌림), 그리고 **서버리스**(코드만 올림, e.g. Lambda)

cf. [클라우드 개념](/devops/aws/01-cloud)

## 3. Linux와 네트워크

서버는 대부분 Linux에서 돌고, 모든 장애 분석은 터미널에서 시작한다.

**터미널과 Shell Script**

- 파이프(`|`), 리다이렉션(`>`), 환경 변수, 종료 코드(`$?`)
- 간단한 Shell Script로 반복 작업 자동화 (e.g. 로그 백업 스크립트)
- Vim은 깊게 공부할 필요 없다. 파일 열기·수정·저장·종료(`:wq`)만 할 줄 알면 충분하다.

**Linux**

- 파일·디렉터리 : `ls`, `cd`, `cat`, `less`, `tail -f`, `find`, `grep`
- 권한 : `chmod`, `chown`, 사용자·그룹, `sudo`
- 프로세스·자원 : `ps`, `top`/`htop`, `kill`, `df`, `free`
- 서비스 관리 : `systemctl`, 로그 확인 `journalctl`
- 패키지 설치 : `apt`, `dnf`

**네트워크 기본**

- IP·포트·DNS·HTTP/HTTPS, 방화벽, `curl`, `ping`, `dig`, `ss`
- "도메인을 입력하면 서버까지 어떻게 도착하는가"를 설명할 수 있으면 충분하다.

cf. [네트워크](/cs/network/01-intro), [유닉스 시스템](/cs/unix-system), [와이어샤크(SSL과 HTTPS)](/devops/wireshark)

## 5. 3 Tier 애플리케이션

직접 운영할 앱이 어떻게 동작하는지 알아야, 장애가 났을 때 원인을 찾을 수 있다.

**약간의 백엔드 공부**

- 간단한 API 서버 만들기, DB와 통신하기 (언어는 무엇이든 OK)

**3 Tier 애플리케이션 직접 만들기**

```
[Presentation]  웹 (정적 파일 / 프론트엔드)
      ↓
[Application]   API 서버
      ↓
[Data]          데이터베이스
```

**The Twelve-Factor App**

- [12factor.net](https://12factor.net/ko/)을 읽어 보자. "운영하기 좋은 애플리케이션"의 12가지 원칙이다.
  - e.g. 설정은 코드가 아니라 **환경 변수** 에, 로그는 파일이 아니라 **표준 출력** 으로, 앱은 **상태를 갖지 않게(stateless)**
- 이후 배울 Docker·쿠버네티스가 왜 그렇게 설계되었는지 이해하는 바탕이 된다.

## 6. 클라우드(AWS)

**시작 전에 꼭 할 일**

- AWS 계정 생성, 신용카드 등록
- ⚠️ 루트 계정 MFA 설정, 일상 작업용 IAM 사용자(또는 IAM Identity Center) 만들기, **결제 알림(Budget) 설정**
  - 실수로 켜 둔 리소스나 유출된 키로 큰 요금이 청구되는 사고가 실제로 자주 일어난다.
- 다 쓴 리소스는 반드시 삭제하기

**3 Tier 앱을 AWS에 구성해 보기**

- **EC2** : 가상 서버. 하나 만들고 SSH로 접속해 보기
- **VPC** : 퍼블릭·프라이빗 서브넷, 보안 그룹 (DB는 외부에서 직접 접근할 수 없게)
- **RDS** : 관리형 DB
- **S3 + CloudFront** : 정적 파일과 CDN
- **Route 53** (도메인), **ACM** (HTTPS 인증서)
- **ALB** (로드 밸런서) + Auto Scaling
- 이 단계에서는 손으로 여러 번 배포해 보자. "이걸 매번 손으로 해야 해?"라는 불편함이 8장 CI/CD를 배우는 이유가 된다.

cf. [AWS 로드맵](/devops/aws), [AWS 서비스 종류](/devops/aws-service-type), [클라우드 배포 전략](/devops/distribute), [단계별 AWS Front 배포](/devops/aws-front-distribute)

## 7. 컨테이너(Docker)

"내 컴퓨터에선 되는데 서버에선 안 돼요"를 해결한다. 앱과 실행 환경을 **이미지** 로 묶어 어디서나 똑같이 실행한다.

- 이미지와 컨테이너, `Dockerfile` 작성, 레이어와 캐시, 멀티 스테이지 빌드
- **Docker Compose** 로 API 서버 + DB를 한 번에 띄우기
- 이미지 레지스트리 : Docker Hub, AWS ECR
- 3 Tier 앱을 컨테이너로 바꿔서 다시 배포해 보기 (EC2 위 Docker, 또는 AWS ECS)

cf. [Docker](/devops/docker/01-intro), [Docker Compose](/devops/docker/09-docker-compose)

## 8. CI/CD

손으로 하던 테스트·빌드·배포를 자동화한다.

- **CI(지속적 통합)** : 푸시할 때마다 자동으로 린트·테스트·빌드
- **CD(지속적 배포/전달)** : 테스트를 통과하면 자동으로 운영 환경에 배포
- 도구 : **GitHub Actions** ✅(가장 보편적), Jenkins, GitLab CI/CD
- 실습 : `main`에 푸시 → 테스트 → Docker 이미지 빌드 → ECR 푸시 → 서버 배포
- 보안 팁 : 클라우드 접근 키를 저장소에 넣지 말고, **OIDC** 로 GitHub Actions가 임시 권한을 받아 쓰게 하자.
- 배포 전략 : 롤링, 블루-그린, 카나리, 그리고 **롤백** 방법

cf. [CI/CD](/cs/terms-principles/ci-cd), [Jenkins](/devops/jenkins), [프론트엔드 배포](/frontend/front-deploy)

## 9. IaC (Infrastructure as Code)

AWS 콘솔에서 클릭으로 만든 인프라를 떠올려 보자.
똑같은 환경을 하나 더(스테이징) 만들려면? 누가 언제 무엇을 바꿨는지는? → **클릭은 기록도 재현도 안 된다.**

IaC는 인프라를 코드로 정의하고, Git으로 관리하고, 리뷰하고, 자동으로 적용한다.

```hcl
resource "aws_s3_bucket" "assets" {
  bucket = "my-service-assets"
}
```

- **Terraform** ✅ : 가장 널리 쓰이는 IaC 도구. `plan`(변경 미리 보기) → `apply`(적용)
  - 2023년 라이선스 변경 이후 리눅스 재단 산하의 오픈소스 포크 **OpenTofu** 도 함께 쓰인다.
- 그 밖에 : AWS CDK·Pulumi(일반 프로그래밍 언어로 작성), CloudFormation(AWS 전용)
- 서버 내부 설정 자동화 : Ansible
- 실습 : 6장에서 만든 3 Tier 인프라(VPC, EC2, RDS, S3…)를 Terraform으로 다시 만들어 보기

## 10. Kubernetes

컨테이너가 수십, 수백 개가 되면 새로운 불편함이 생긴다.

- 컨테이너가 죽으면 누가 다시 띄우지? 트래픽이 늘면 누가 늘리지? 무중단 배포는? 서버 여러 대에 어떻게 나눠 배치하지?

**Kubernetes(K8s)** 는 이것을 자동으로 해 주는 컨테이너 오케스트레이션 도구다.

- 기본 개념 : Pod, Deployment, Service, Ingress, ConfigMap·Secret, Namespace
- 패키지 관리 : **Helm**
- 관리형 서비스 : AWS **EKS**, GCP GKE, Azure AKS (직접 설치·운영은 매우 어렵다)
- **GitOps** : Git 저장소의 설정을 쿠버네티스에 자동으로 동기화 → **Argo CD**, Flux
- 로컬 실습 : kind, minikube, k3d

> ⚠️ 쿠버네티스는 강력하지만 **운영 복잡도가 매우 높다.**
> 서비스가 작다면 ECS, Cloud Run, App Runner 같은 더 단순한 컨테이너 서비스로도 충분하다. "우리 규모에 정말 필요한가?"를 항상 먼저 묻자.

cf. [Kubernetes](/devops/kubernetes), [Docker 오케스트레이션](/devops/docker/10-orchestration), [NestJS - Kubernetes & Helm](/backend/nestjs/50-kubernetes-helm)

## 11. 관측성 (Observability)

"서버가 느려요"라는 말을 들었을 때, **어디가 왜 느린지** 바로 찾을 수 있어야 한다.

| 신호        | 질문                          | 도구                                    |
| ----------- | ----------------------------- | --------------------------------------- |
| **메트릭**  | 지금 상태는? (숫자)           | Prometheus, Grafana, CloudWatch         |
| **로그**    | 무슨 일이 있었나? (기록)      | Loki, ELK(Elasticsearch·Logstash·Kibana), CloudWatch Logs |
| **트레이스** | 요청이 어디서 오래 걸렸나?   | Jaeger, Tempo, AWS X-Ray                |

- 표준 수집 도구 : **OpenTelemetry**
- 알림(Alerting) : 에러율·응답 시간이 기준을 넘으면 슬랙·전화 알림 → 알림이 너무 많으면 아무도 안 본다. **정말 조치가 필요한 것만** 알리자.
- 상용 통합 도구 : Datadog, New Relic, Grafana Cloud

## 12. 보안 (DevSecOps)

보안을 마지막에 따로 검사하지 않고, **개발·배포 파이프라인 전체에 녹이는 것** 이다.

- **IAM 최소 권한 원칙** : 필요한 권한만, 필요한 기간만
- **비밀 정보 관리** : 키·비밀번호를 코드나 이미지에 넣지 않기 → AWS Secrets Manager, Parameter Store, Vault
- **이미지·의존성 취약점 스캔** : Trivy, Dependabot, CI에서 자동 검사
- **공급망 보안** : 이미지 서명, SBOM(소프트웨어 구성 목록)
- 네트워크 : 보안 그룹·프라이빗 서브넷, WAF, HTTPS
- 감사 로그 : AWS CloudTrail로 "누가 언제 무엇을 바꿨는지" 기록

---

## 13. 안정성 (SRE)

- **SLI / SLO / SLA**
  - SLI : 측정 지표 (e.g. 성공한 요청 비율)
  - SLO : 내부 목표 (e.g. 한 달 성공률 99.9%)
  - SLA : 고객과의 계약 (지키지 못하면 보상)
- **에러 버짓** : 99.9% 목표라면 0.1%는 실패해도 된다. 이 "허용된 실패"를 다 쓰면 새 기능 배포를 멈추고 안정성 작업에 집중
- **장애 대응** : 온콜(On-call), 런북(대응 매뉴얼), 장애 회고(**비난 없는 Postmortem**)
- 백업과 복구 훈련, 다중 가용 영역(Multi-AZ) 구성, 카오스 엔지니어링

---

## 14. 비용 (FinOps)

클라우드는 편리한 만큼, 관리하지 않으면 **비용이 조용히 새어 나간다.**

- 결제 알림과 예산 설정, 태그로 팀·서비스별 비용 구분
- 쓰지 않는 리소스 정리 (켜 둔 개발 서버, 연결 안 된 EBS 볼륨, 오래된 스냅샷)
- 적정 사양(Right-sizing), 오토스케일링, 예약 인스턴스·Savings Plans, 스팟 인스턴스
- 데이터 전송 비용(특히 인터넷으로 나가는 트래픽) 주의

---

## 15. 플랫폼 엔지니어링

회사가 커지면, 팀마다 인프라를 각자 구성하는 대신 **공통 플랫폼** 을 만든다.

- 개발자가 버튼 하나(또는 템플릿 하나)로 새 서비스 생성 → CI/CD·모니터링·보안 설정이 자동으로 적용
- 도구 : Backstage(내부 개발자 포털), 쿠버네티스 위의 공통 배포 템플릿

---

## 16. AI와 DevOps

- AI 코딩 에이전트가 CI 실패 원인 분석, IaC 코드 작성, 장애 로그 요약을 돕는 일이 많아졌다.
- MCP로 AI 도구를 클라우드·모니터링 도구에 연결해 조회·분석에 활용할 수 있다.
- 단, AI에게 운영 환경 변경 권한을 줄 때는 **읽기 전용부터, 변경은 사람이 검토(plan 확인) 후 적용** 하는 원칙을 지키자.
- AI·LLM 서비스를 운영하는 일(GPU 인프라, 모델 서빙, 비용 관리)도 새로운 DevOps 영역이 되었다.

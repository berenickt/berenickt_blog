## 1. 브랜치(branch)란?

코드를 짜다 보면 갑자기 새로운 기능을 추가해야 할 때가 있다.
원본 코드에 바로 추가하고 커밋해도 되지만, 혹시 잘못해서 **지금까지 잘 돌아가던 프로그램이 망가지면** 어떡할까?

그래서 새 기능은 **원본을 건드리지 않는 별도의 작업 공간** 에서 먼저 개발한다. Git에서는 이것을 **브랜치(branch, 가지)** 라고 한다.

```
main    ●───●───●───────────●   ← 원본 (항상 잘 돌아가는 코드)
                 \         /
coupon            ●───●───●     ← 쿠폰 기능을 따로 개발하는 브랜치
```

- e.g. 쇼핑몰에 **쿠폰 기능** 을 추가하고 싶다 → `coupon` 브랜치를 만들어 거기서 개발하고, 완성되면 `main`에 합친다.
- 브랜치에서 무엇을 하든 `main` 브랜치에는 아무 영향이 없다.
- 여러 기능을 각각의 브랜치에서 **동시에** 개발할 수도 있다.

> 💡 **브랜치는 "프로젝트 복사본"처럼 동작하지만, 실제로 파일을 복사하지는 않는다.**
>
> 브랜치의 실체는 **특정 커밋을 가리키는 이름표(포인터)** 일 뿐이다.
> 그래서 브랜치는 수천 개를 만들어도 거의 공간을 차지하지 않고, 만들고 이동하는 것도 순식간이다.
> 이 가벼움이 Git이 이전 버전 관리 도구(SVN 등)보다 브랜치를 마음껏 쓰게 해 준 핵심이다.

### 1.1 HEAD

- **HEAD** = **"지금 내가 보고 있는 위치"** 를 가리키는 특별한 이름표
- 보통 현재 브랜치를 가리킨다. `git log`에 보이는 `HEAD -> coupon`은 "지금 coupon 브랜치에 있다"는 뜻이다.
- 브랜치를 이동하면 HEAD가 옮겨 가고, 작업 폴더의 파일도 그 브랜치의 상태로 바뀐다.

## 2. 브랜치 만들기와 이동 : git branch, git switch

```bash
# 브랜치 만들기 : git branch 브랜치이름
git branch coupon

# 브랜치 이동 : git switch 브랜치이름
git switch coupon

# 만들면서 바로 이동 (위 두 줄을 한 번에)
git switch -c coupon

# 현재 브랜치 확인
git status          # On branch coupon
git branch          # 브랜치 목록, * 표시가 현재 브랜치
```

- 원래 브랜치로 돌아가려면 `git switch main`
  - 저장소 설정에 따라 기본 브랜치 이름이 `main`이 아니라 `master`일 수도 있다. (`git branch`로 확인)
- 예전에는 `git checkout 브랜치이름`, `git checkout -b 브랜치이름`을 썼다. 지금도 동작하지만, 역할이 분명한 **`git switch`** 를 권장한다.

> ⚠️ 커밋하지 않은 변경이 있는 상태에서 브랜치를 이동하면, 변경 내용이 다른 브랜치로 따라가거나 충돌 때문에 이동이 거부될 수 있다.
> **브랜치를 이동하기 전에는 커밋하거나 잠시 치워 두자.** → [10-작업 임시 보관하기 : stash](/devops/git/10-stash)

---

### 2.1 실습 : 브랜치마다 따로 커밋해 보기

`coupon` 브랜치로 이동해서 새 파일을 만들고 커밋한다.

```bash
git switch -c coupon
```

```txt
# coupon.txt
aaaaaaaaaaa   ← coupon 브랜치에서 작업 중
```

```bash
git add .
git commit -m "쿠폰 파일 추가"
```

이제 `main` 브랜치로 돌아가 보자.

```bash
git switch main
# coupon.txt가 사라진다! → coupon 브랜치에서만 만든 파일이기 때문
```

양쪽 브랜치에서 커밋을 몇 번씩 더 해 보자.

```bash
git switch coupon
# coupon.txt 수정
git add .
git commit -m "쿠폰 할인율 계산"

git switch main
# app.txt 수정
git add .
git commit -m "메인 화면 수정"

# 브랜치와 커밋 내역을 그래프로 보기
git log --oneline --graph --all
```

```
* 7c1d2e9 (HEAD -> main) 메인 화면 수정
| * 4b8a1f3 (coupon) 쿠폰 할인율 계산
| * 2e9c7a0 쿠폰 파일 추가
|/
* 1a2b3c4 첫 파일 만듦
```

→ 하나의 커밋에서 **두 갈래로 갈라져** 각자 따로 이력이 쌓인 것을 볼 수 있다.

---

### 2.2 브랜치 관리 명령어

```bash
git branch                       # 로컬 브랜치 목록
git branch -v                    # 브랜치마다 마지막 커밋까지 표시
git branch -a                    # 원격(GitHub) 브랜치까지 모두 보기
git branch -m 새이름              # 현재 브랜치 이름 바꾸기
git branch -d 브랜치이름           # 브랜치 삭제 (합쳐진 브랜치만 삭제됨)
git branch -D 브랜치이름           # 강제 삭제 (합치지 않은 커밋도 버림 ⚠️)
```

브랜치 이름은 팀에서 규칙을 정해 두면 관리하기 쉽다.

- `feature/coupon` : 새 기능
- `fix/login-error` : 버그 수정
- `refactor/payment` : 리팩터링

## 3. 브랜치 합치기 : git merge

브랜치에서 개발을 마쳤으면, 원본 코드가 있는 `main` 브랜치에 합친다. **브랜치를 합치는 것** 을 **merge(병합)** 라고 한다.

```bash
# 1. 합쳐 받을 브랜치(main)로 이동
git switch main

# 2. 합칠 브랜치 이름으로 merge
git merge coupon
```

- `git merge coupon` = "**지금 있는 브랜치(main)에** coupon 브랜치의 변경을 가져와 합쳐라"
- **어느 브랜치에서 실행하느냐가 중요하다.** 합쳐 받는 쪽(main)으로 먼저 이동해야 한다.
- 양쪽 브랜치에 모두 새 커밋이 있으면, Git은 둘을 합친 **merge 커밋** 을 새로 만든다. (커밋 메시지 입력 창이 뜨면 그대로 저장하고 닫으면 된다)

```
main    ●───●───●───────●───●  ← merge 커밋 (두 갈래를 하나로)
             \             /
coupon        ●───────●───●
```

- 합친 뒤 `git log --oneline --graph --all`로 보면 두 갈래가 합쳐진 것을 확인할 수 있다.
- 다 쓴 브랜치는 `git branch -d coupon`으로 정리한다.

> 💡 merge에는 상황에 따라 **3-way merge, fast-forward, rebase, squash** 같은 여러 방식이 있다. → [04-브랜치를 합치는 4가지 방법](/devops/git/04-merge)

## 4. 충돌(Merge Conflict) 해결하기

두 브랜치에서 **같은 파일의 같은 줄을 서로 다르게 수정** 했다면, Git은 어느 쪽을 남길지 스스로 결정하지 못한다. 이것이 **merge conflict(충돌)** 다.

```bash
git merge coupon
# CONFLICT (content): Merge conflict in app.txt
# Automatic merge failed; fix conflicts and then commit the result.
```

충돌이 난 파일을 열어 보면 Git이 표시를 해 둔다.

```txt
<<<<<<< HEAD
main 브랜치에서 수정한 내용
=======
coupon 브랜치에서 수정한 내용
>>>>>>> coupon
```

| 표시                 | 의미                                         |
| -------------------- | -------------------------------------------- |
| `<<<<<<< HEAD`       | 여기부터 **현재 브랜치(main)** 의 내용        |
| `=======`            | 두 내용의 경계                               |
| `>>>>>>> coupon`     | 여기까지 **합치려는 브랜치(coupon)** 의 내용  |

### 4.1 해결 순서

1. 충돌 난 파일을 열어 **최종적으로 남길 코드만** 남긴다.
   - 한쪽만 남겨도, 둘 다 남겨도, 새로 고쳐 써도 된다.
   - `<<<<<<<`, `=======`, `>>>>>>>` 표시는 **모두 지운다.**
2. 해결한 파일을 스테이징하고 커밋한다.

```bash
git add app.txt
git commit -m "coupon 브랜치 merge, 충돌 해결"
```

→ 새 커밋이 만들어지면서 **충돌 해결 + 브랜치 합치기 완료**

- VS Code는 충돌 부분 위에 **Accept Current Change(현재 것 유지) / Accept Incoming Change(들어오는 것 유지) / Accept Both Changes(둘 다 유지)** 버튼을 보여 준다. 충돌이 복잡하면 **Merge Editor** 로 양쪽을 나란히 보며 해결할 수 있다.
- 해결하다가 꼬였다면 `git merge --abort`로 **merge 시작 전 상태로 되돌릴 수 있다.**

### 4.2 충돌을 줄이는 습관

- 브랜치를 **작게, 짧게** 유지하고 자주 합친다. 오래 떨어져 있을수록 충돌이 커진다.
- 작업 중인 브랜치에 `main`의 최신 변경을 자주 받아 온다.
- 여러 사람이 같은 파일의 같은 부분을 동시에 고치지 않도록 작업을 나눈다.
- 포매터(Prettier 등)를 팀 전체가 같은 설정으로 써서, 코드 모양 차이로 인한 충돌을 막는다.

## 5. 정리

| 하고 싶은 것                    | 명령어                                 |
| ------------------------------- | -------------------------------------- |
| 브랜치 만들기                   | `git branch 브랜치명`                  |
| 브랜치 이동                     | `git switch 브랜치명`                  |
| 만들면서 이동                   | `git switch -c 브랜치명`               |
| 브랜치 목록                     | `git branch`, `git branch -a`          |
| 브랜치 합치기                   | `git switch main` → `git merge 브랜치명` |
| 브랜치 그래프 보기              | `git log --oneline --graph --all`      |
| 충돌 해결 후 마무리             | 파일 수정 → `git add` → `git commit`   |
| merge 취소                      | `git merge --abort`                    |
| 브랜치 삭제                     | `git branch -d 브랜치명`               |

다음 글에서는 브랜치를 합치는 여러 가지 방법(3-way, fast-forward, rebase, squash)을 비교한다. → [04-브랜치를 합치는 4가지 방법](/devops/git/04-merge)

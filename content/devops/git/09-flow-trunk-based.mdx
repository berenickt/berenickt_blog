## 1. 브랜치 전략이 필요한 이유

개발자 10명이 브랜치를 아무렇게나 만들면 개발 과정이 매우 복잡해지고, 무엇이 어디까지 반영됐는지 추적하기 어렵다.
그래서 **브랜치를 언제 만들고, 어디에 합치고, 언제 배포할지** 정한 **방법론(브랜치 전략)** 을 쓴다.

브랜치 전략을 정해 두면

1. 브랜치 관리가 쉬워지고
2. 팀원이 아무리 많아도 개발 → 테스트 → 배포 절차가 매끄러워진다.

그래서 프로젝트를 리드하는 사람이라면 꼭 알아 두면 좋다.

### 1.1 한눈에 비교

| 전략              | 주요 브랜치                                     | 배포 방식                       | 잘 맞는 곳                                     |
| ----------------- | ----------------------------------------------- | ------------------------------- | ---------------------------------------------- |
| **Git Flow**      | main, develop, feature, release, hotfix         | 버전 단위로 정기 출시           | 게임·앱·설치형 소프트웨어, 여러 버전을 동시에 유지 |
| **GitHub Flow**   | main + feature                                  | PR merge할 때마다 수시 배포     | 웹 서비스, 작은~중간 규모 팀 ✅                |
| **GitLab Flow**   | main + 환경 브랜치(staging, production)         | 환경별로 단계적 배포            | 스테이징 검증이 필요한 서비스                  |
| **Trunk-based**   | main(trunk) 하나 + 아주 짧은 브랜치             | 하루에도 여러 번 자동 배포      | CI/CD·테스트 자동화가 잘 된 팀                 |

## 2. Git Flow

**만드는 프로그램이 정해진 버전으로 안정적인 출시(release)를 해야 한다면** (e.g. 게임, 모바일 앱, 설치형 소프트웨어) Git Flow 전략이 잘 맞는다.
2010년 빈센트 드리센(Vincent Driessen)이 블로그 글로 소개하면서 널리 퍼졌다.

Git Flow는 크게 **5가지 브랜치** 를 운영한다.

| 브랜치      | 역할                                                    | 어디서 만들고 → 어디에 합치나       |
| ----------- | ------------------------------------------------------- | ----------------------------------- |
| `main`      | **실제로 출시된 버전** 만 있는 브랜치                  | -                                   |
| `develop`   | 다음 버전을 개발하는 브랜치                             | main에서 생성                       |
| `feature/*` | 기능 하나를 개발                                        | develop → develop                   |
| `release/*` | 출시 전 최종 테스트·버그 수정                           | develop → main + develop            |
| `hotfix/*`  | 이미 출시된 버전의 긴급 버그 수정                       | main → main + develop               |

```
main      ●─────────────────────────●──────────●   (v1.0)     (v1.0.1)
           \                       ↗ \         ↗ ↘
hotfix      \                     /   ●───────●   \
             \                   /                 \
release       \           ●────●                    \
               \         ↗      ↘                    ↘
develop         ●──●────●────────●────────────────────●
                    \   ↗ \    ↗
feature              ●─●   ●──●
                  (guild) (friend)
```

게임 개발로 예를 들어 보자. 이제부터 여러분은 **게임 개발 팀장** 이다.

- 지금까지는 주먹구구식으로 협업해서 0.9 버전까지 만들어 놨다.
- 1.0 버전부터는 신기능도 많아서 제대로 개발을 진행하고 싶다.
- 그래서 Git Flow를 도입해 보자.

### 2.1 develop 브랜치 만들기

신기능을 개발해서 바로 main 브랜치에 합칠 것인가? 절대 안 된다. main은 **유저가 쓰고 있는 버전** 이다.

- main 브랜치를 바탕으로 개발용 **develop 브랜치** 를 만든다.
- 이제 모든 개발은 develop 브랜치를 기준으로 진행하라고 팀원들에게 알린다.

```bash
git switch main
git switch -c develop
git push -u origin develop
```

### 2.2 feature 브랜치에서 신기능 개발

신기능은 develop에서 갈라져 나온 **feature 브랜치** 에서 각각 개발한다.

- `feature/guild` 브랜치에서 길드 기능
- `feature/friend` 브랜치에서 친구 기능
- 브랜치 이름에 여러 단어가 필요하면 보통 `-`나 `/`를 쓴다.

기능이 완성되면 PR을 통해 **develop 브랜치에 merge** 한다. 기능 단위로 이력을 깔끔하게 남기고 싶다면 squash and merge도 괜찮다.

### 2.3 release 브랜치에서 출시 준비

develop에서 만든 기능들이 완성된 것 같다. 이걸 바로 main에 합치기엔 아직 불안하다.
그래서 develop에서 **release 브랜치** 를 만들고 출시 준비를 한다.

- 이름은 보통 `release/1.0`처럼 버전을 붙인다.
- 여기서 **테스트, QA** 를 진행하고, 발견한 버그는 release 브랜치에서 바로 고친다.
- release 브랜치에서는 **새 기능을 추가하지 않는다.** (새 기능은 계속 develop에서)
- 완성되면 **main에 merge** 하고, 버전 **태그** 를 붙여 유저에게 배포한다.
- release에서 고친 버그가 다음 버전에도 반영되도록 **develop에도 merge** 한다.

```bash
git switch main
git merge --no-ff release/1.0
git tag -a v1.0.0 -m "1.0 출시"     # 출시 버전 표시
git push origin main --tags
```

> 💡 **태그(tag)** 는 특정 커밋에 `v1.0.0` 같은 이름을 붙여 두는 기능이다. 나중에 "1.0 출시 당시 코드"를 바로 찾을 수 있다.
> 버전 번호는 보통 **시맨틱 버저닝** (`주.부.수`, e.g. `1.4.2`)을 따른다.

### 2.4 hotfix 브랜치에서 긴급 버그 수정

1.0 버전을 출시했는데 **골드 무한 복사 버그** 가 발견됐다! 다음 버전까지 기다릴 수 없다.

- main 브랜치에서 `hotfix/gold-dupe` 브랜치를 만들어 바로 수정한다.
- 수정이 끝나면 **main에 merge** 하고 `v1.0.1` 태그를 붙여 배포한다.
- 당연히 **develop에도 merge** 해야 다음 버전에서 버그가 다시 살아나지 않는다.

### 2.5 꼭 Git Flow를 써야 할까?

- 장점
  - 출시 버전과 개발 중인 코드가 명확히 분리되어 **안정적으로 버전별 배포** 가 가능하다.
  - 여러 버전을 동시에 유지보수해야 할 때 유리하다.
- 단점
  - 브랜치가 많고 규칙이 복잡하다. 작은 팀에는 과하다.
  - develop과 main 사이가 오래 벌어지면 merge가 어려워진다.
  - **수시로 배포하는 CI/CD 방식과는 잘 맞지 않는다.**

> 💡 Git Flow를 소개한 드리센도 2020년에 덧붙인 글에서 **"지속적으로 배포하는 웹 앱이라면 GitHub Flow 같은 더 단순한 방식을 권한다"** 고 했다.

그래서 남들이 하는 걸 그대로 따라 하지 말고 **팀 상황에 맞게 변형해서 쓰면 된다.**
예를 들어 release 브랜치 없이 develop에서 바로 main으로 merge해서 배포해도 된다. 그 선택에 **합당한 이유와 근거** 가 있으면 된다. (물론 책임도 져야 한다)

## 3. GitHub Flow

**main 브랜치 + 기능 브랜치** 만 쓰는 단순한 전략이다. GitHub가 자기 팀의 방식으로 소개했다.

```
main      ●────●────────●────────●──────   ← 항상 배포 가능한 상태
           \  ↗ \      ↗ \      ↗
feature     ●●   ●●●●●    ●●●●●
         (PR 리뷰 후 merge → 바로 배포)
```

1. main에서 **이름이 분명한 브랜치** 를 만든다. (`feature/coupon`, `fix/login-error`)
2. 커밋하고 push한다.
3. **Pull Request** 를 열어 코드 리뷰와 자동 테스트(CI)를 거친다. → [08-Pull Request](/devops/git/08-pull-request)
4. 승인되면 **main에 merge하고, 바로 배포** 한다.
5. 다 쓴 브랜치는 삭제한다.

- 규칙은 하나 : **main은 언제나 배포할 수 있는 상태여야 한다.**
- 대부분의 웹 서비스와 오픈소스 프로젝트가 이 방식(또는 변형)을 쓴다.

## 4. GitLab Flow

GitHub Flow에 **환경(배포 단계)별 브랜치** 를 더한 방식이다.

```
feature → main → staging → production
                (검증 서버)  (실제 서비스)
```

- main에 merge된 코드를 바로 운영에 내보내지 않고, `staging` 브랜치로 옮겨 **검증 서버에서 확인한 뒤** `production`으로 옮긴다.
- 배포 시점을 조절해야 하거나(앱 스토어 심사 등), 여러 환경을 운영할 때 유용하다.
- 버전별 출시가 필요하면 `release/1.0` 같은 **릴리스 브랜치** 를 함께 쓰기도 한다.

## 5. Trunk-based Development

**코드를 짜는 대로 바로 유저에게 배포해도 되는 프로그램** 이고, 테스트·배포가 자동화되어 있다면,
굳이 많은 브랜치를 만들 필요가 없다. 모두가 **하나의 main 브랜치(trunk, 나무의 몸통)** 에 **작은 단위로 자주** 합친다.

```
main(trunk)  ●─●─●─●─●─●─●─●─●─●─●   ← 하루에도 여러 번 merge, 자동 테스트 후 자동 배포
              ↖↗  ↖↗    ↖↗
          (몇 시간~하루짜리 아주 짧은 브랜치)
```

### 5.1 운영 방법

1. 기능 추가나 버그 수정이 필요하면 main에서 브랜치를 만든다. **브랜치는 길어야 하루~이틀** 만 유지한다.
2. 작업이 끝나면 바로 main에 합치고, 브랜치는 삭제한다.
3. main에 합쳐진 코드는 **자동 테스트를 통과하면 자동으로 배포** 된다.
4. 아직 완성되지 않은 기능은 **피처 플래그(Feature Flag)** 로 숨겨 둔다.

> 💡 **피처 플래그** : 코드는 main에 합치고 배포까지 하되, 설정값으로 기능을 켜고 끄는 기법이다.
> 미완성 기능을 오래된 브랜치에 묵혀 두지 않아도 되고, 일부 사용자에게만 먼저 공개(점진적 출시)할 수도 있다.
>
> ```ts
> if (flags.newCheckout) {
>   return <NewCheckout />
> }
> return <OldCheckout />
> ```

### 5.2 GitHub Flow와 무엇이 다를까?

둘 다 main 중심이라 비슷하지만, Trunk-based는 **브랜치 수명이 훨씬 짧고(또는 main에 직접 커밋), 배포가 더 잦고 자동화** 되어 있다는 점을 강조한다.
GitHub Flow를 아주 짧은 주기로 돌리면 Trunk-based에 가까워진다.

### 5.3 장단점

- 장점
  - 코드를 **한 브랜치에서만 관리** 하니 편하다.
  - 크게 개발해서 한 번에 merge하는 것보다 **작은 단위로 자주 merge하는 것이 더 안전** 하다. (충돌이 작고, 문제를 빨리 발견)
  - 기능이 유저에게 전달되는 속도가 빠르다.
- 단점
  - main이 망가지면 바로 서비스에 영향을 준다. 그래서 **테스트와 코드 리뷰를 자주, 자동으로** 해야 한다.
  - 테스트 자동화, CI/CD, 피처 플래그, 모니터링이 갖춰진 팀이어야 제대로 쓸 수 있다.

## 6. 어떤 전략을 골라야 할까?

```
정해진 버전으로 출시하고, 여러 버전을 동시에 유지보수해야 하나? (게임, 앱, 설치형 SW)
├─ YES → Git Flow (또는 release 브랜치를 쓰는 GitLab Flow)
└─ NO (웹 서비스처럼 수시 배포)
   ├─ 테스트 자동화·CI/CD·피처 플래그가 잘 갖춰져 있다 → Trunk-based
   ├─ 스테이징 검증 후 배포 시점을 조절하고 싶다 → GitLab Flow
   └─ 그 외 대부분 → GitHub Flow ✅
```

- 이미 어느 정도 개발이 진척되었거나 **숙련된 팀** 이라면 GitHub Flow나 Trunk-based가 훨씬 편하다.
- **CI/CD로 수시 배포하는 곳** 은 대부분 Trunk-based에 가까운 방식을 쓴다.
- 출시 버전의 안정성이 중요한 프로그램, **여러 버전을 동시에 지원** 해야 하는 프로그램은 Git Flow가 적절하다.
- 어떤 전략이든 **팀이 함께 합의하고 문서로 남기는 것** 이 가장 중요하다.

## 7. Q&A

**Q. merge할 때는 어떤 방법이 좋을까?**

- 브랜치가 합쳐진 **기록을 남겨야 하는 중요한 브랜치** (release, hotfix → main) : **3-way merge** (`--no-ff`, Create a merge commit)
- **기록을 남길 필요가 없는 작은 기능 브랜치** (feature → develop/main) : **squash** 또는 **rebase**
- 결국 팀의 취향과 규칙이다. → [04-브랜치를 합치는 4가지 방법](/devops/git/04-merge)

**Q. 브랜치 이름은 어떻게 짓나?**

- `feature/기능명`, `fix/버그명`, `hotfix/버그명`, `release/버전`, `chore/작업명`
- 이슈 번호를 붙이면 추적이 쉽다 : `feature/123-coupon`

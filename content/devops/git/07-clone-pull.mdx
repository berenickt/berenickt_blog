## 1. 원격 저장소로 협업하기

원격 저장소의 가장 큰 장점은 **다른 사람과 함께 작업할 수 있다** 는 것이다.

```
          GitHub (원격 저장소)
        ↗ push    ↘ pull
   나 (로컬)        팀원 (로컬)
        ↖ pull    ↙ push
```

- 각자 자기 컴퓨터에서 코드를 짜고 커밋한 뒤 `git push`로 올린다.
- 다른 사람이 올린 최신 코드는 `git pull`로 받아 온다.
- 이 글에서는 팀원이 처음 저장소를 받는 **clone**, 최신 코드를 받아오는 **pull**, 그 내부 동작인 **fetch** 를 다룬다.

---

## 2. 팀원 초대하기

다른 사람이 내 저장소에 **push하려면 권한** 이 있어야 한다.

- 개인 저장소 : GitHub 저장소 **Settings → Collaborators → Add people** 에서 팀원의 GitHub 아이디를 등록한다. 팀원이 초대 메일을 수락하면 push할 수 있다.
- 회사·팀 단위 : **Organization** 을 만들고 팀(Team)별로 저장소 권한(읽기·쓰기·관리자)을 준다.
- 권한이 없는 오픈소스 프로젝트에 기여할 때는 저장소를 내 계정으로 복사(**Fork**)한 뒤 Pull Request를 보낸다. → [08-Pull Request로 협업하기](/devops/git/08-pull-request)

## 3. git clone : 원격 저장소 내려받기

팀원은 원격 저장소를 통째로 자기 컴퓨터에 복제해서 시작한다.

```bash
git clone https://github.com/아이디/my-project.git
cd my-project
```

- 저장소 이름과 같은 폴더가 생기고, 그 안에 **모든 파일 + 전체 커밋 이력 + `.git` 폴더** 가 내려받아진다.
- `origin`이라는 이름으로 원격 저장소가 **자동 등록** 되고, `main` 브랜치도 원격과 연결(upstream)되어 있다. 그래서 바로 `git pull`, `git push`를 쓸 수 있다.
- `git init`이나 `git remote add`를 따로 할 필요가 없다.

```bash
git clone 주소 폴더이름          # 원하는 폴더 이름으로 받기
git clone -b develop 주소       # 특정 브랜치를 기본으로 받기
git clone --depth 1 주소        # 최신 커밋 하나만 받기 (이력이 큰 저장소를 빠르게 받을 때)
```

이제 팀원도 폴더를 열어서 코드를 짜고, 커밋하고, `git push`하면 된다.

## 4. push가 거부되는 상황

`git push`는 아무 때나 되는 게 아니다. **원격 저장소에 내 로컬에 없는 커밋이 있으면 push할 수 없다.**

실습해 보자. 같은 저장소를 두 폴더에 받아서 **나** 와 **팀원** 역할을 번갈아 하면 된다.

```bash
# [팀원] b.txt를 만들어 먼저 push
git add .
git commit -m "b 파일 생성"
git push                          # 성공 → 원격 저장소가 업데이트됨

# [나] 그 사실을 모른 채 c.txt를 만들어 push
git add .
git commit -m "c 파일 생성"
git push
```

```
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/아이디/my-project.git'
hint: Updates were rejected because the remote contains work that you do
hint: not have locally. This is usually caused by another repository pushing
hint: to the same ref. You may want to first integrate the remote changes
hint: (e.g., 'git pull ...') before pushing again.
```

```
원격 (GitHub)   A───B───(팀원) b 파일 생성
나 (로컬)       A───B───(나) c 파일 생성      ← 서로 다른 커밋을 갖고 있음
```

- 원격과 내 로컬의 이력이 **서로 갈라진** 상태다.
- 이대로 push를 허락하면 팀원의 `b 파일 생성` 커밋이 사라지므로, Git이 **미리 막아 주는 것** 이다.
- 해결 : **원격의 최신 커밋을 먼저 받아서 내 커밋과 합친 다음 push** 한다. → `git pull`

---

## 5. git pull : 최신 코드 받아서 합치기

```bash
git pull      # 원격의 최신 커밋을 받아 현재 브랜치에 합침
git push      # 이제 원격의 내용을 다 갖고 있으므로 push 성공
```

- `git pull`은 **현재 브랜치와 연결된 원격 브랜치** (e.g. `main` ↔ `origin/main`)의 새 커밋을 받아서 **현재 브랜치에 합친다.**
- `clone`으로 받았거나 `push -u`로 연결해 두었다면 `git pull`만 입력하면 된다.
- 원격 이름과 브랜치를 직접 지정할 수도 있다 : `git pull origin main`

> 💡 **협업할 때 습관 : 작업을 시작하기 전에 `git pull`, push하기 전에도 `git pull`**
>
> 오래 pull하지 않을수록 받아올 변경이 쌓여 충돌이 커진다.

### 5.1 pull할 때 충돌이 나면

나와 팀원이 **같은 파일의 같은 줄** 을 고쳤다면, pull할 때 merge conflict가 날 수 있다.
해결 방법은 브랜치를 merge할 때와 똑같다.

1. 충돌 난 파일을 열어 `<<<<<<<`, `=======`, `>>>>>>>` 표시를 정리하고 남길 코드만 남긴다.
2. `git add 파일` → `git commit`
3. `git push`

자세한 방법은 [03-충돌 해결하기](/devops/git/03-branch-merge) 참고

## 6. git pull = git fetch + git merge

`git pull`은 사실 두 명령을 한 번에 실행한다.

| 명령어          | 하는 일                                                             |
| --------------- | ------------------------------------------------------------------- |
| **git fetch**   | 원격 저장소의 새 커밋을 **받아 오기만** 한다. (내 브랜치는 그대로)  |
| **git merge**   | 받아 온 커밋을 **내 브랜치에 합친다.**                              |

### 6.1 원격 추적 브랜치 : origin/main

`git fetch`로 받아 온 커밋은 내 `main`이 아니라 **`origin/main`** 이라는 **원격 추적 브랜치** 에 저장된다.
"마지막으로 확인했을 때 GitHub의 main은 여기까지였다"는 표시다.

```
fetch 후

origin/main   A───B───D───E      ← 팀원이 올린 커밋을 받아 옴
main          A───B───C          ← 내 브랜치는 아직 그대로
```

### 6.2 fetch를 따로 쓰면 좋은 경우

pull은 받아 오자마자 합치기 때문에, **합치기 전에 무엇이 바뀌었는지 먼저 보고 싶을 때** 는 fetch를 따로 쓴다.

```bash
git fetch                         # 원격의 새 커밋 받아 오기 (내 코드는 그대로)
git log main..origin/main --oneline   # 원격에만 있는 새 커밋 목록 보기
git diff main origin/main         # 무엇이 바뀌었는지 비교
git merge origin/main             # 확인했으면 합치기 (= pull 한 것과 같은 결과)
```

- `git fetch`는 내 작업 파일을 전혀 건드리지 않으므로, **아무 때나 안전하게** 실행할 수 있다.
- VS Code 등 에디터의 자동 fetch 기능을 켜 두면, 원격에 새 커밋이 생겼을 때 알려 준다.

## 7. pull할 때 합치는 방식 설정하기

최근 Git에서는 내 로컬과 원격 모두에 새 커밋이 있는 상태로 `git pull`을 하면 다음과 같은 안내가 나온다.

```
hint: You have divergent branches and need to specify how to reconcile them.
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
```

**갈라진 이력을 어떻게 합칠지** 정하라는 뜻이다. 한 번 설정해 두면 된다.

| 설정                                     | 동작                                                                 | 이력                       |
| ---------------------------------------- | -------------------------------------------------------------------- | -------------------------- |
| `git config --global pull.rebase false`  | **merge** : 원격 커밋과 내 커밋을 merge 커밋으로 합침 (전통적인 방식) | merge 커밋이 생김          |
| `git config --global pull.rebase true`   | **rebase** : 원격 커밋 뒤에 내 커밋을 다시 쌓음                       | 한 줄로 깔끔 ✅ 많이 씀     |
| `git config --global pull.ff only`       | fast-forward가 가능할 때만 pull, 아니면 거부                         | 직접 판단해서 합쳐야 함    |

- `pull.rebase true`를 쓰면 `Merge branch 'main' of github.com/...` 같은 의미 없는 merge 커밋이 생기지 않아 이력이 깔끔해진다.
- 단, rebase 중에 충돌이 나면 해결 후 `git add` → `git rebase --continue`로 진행한다. (→ [04-rebase](/devops/git/04-merge))

## 8. 원격의 다른 브랜치에서 작업하기

팀원이 GitHub에 올린 `feature/login` 브랜치를 내 컴퓨터에서 이어서 작업하고 싶다면

```bash
git fetch                    # 원격의 새 브랜치 정보 받아 오기
git branch -a                # remotes/origin/feature/login 이 보이는지 확인
git switch feature/login     # 같은 이름의 로컬 브랜치를 만들고 원격과 자동 연결
```

- 이후 이 브랜치에서도 `git pull`, `git push`를 그대로 쓸 수 있다.
- 원격에서 삭제된 브랜치를 내 목록에서도 정리하려면 `git fetch --prune`

## 9. 정리

| 하고 싶은 것                               | 명령어                                  |
| ------------------------------------------ | --------------------------------------- |
| 원격 저장소 처음 받기                      | `git clone 주소`                        |
| 최신 코드 받아서 합치기                    | `git pull`                              |
| 받아 오기만 하고 합치지는 않기             | `git fetch`                             |
| 원격에만 있는 새 커밋 보기                 | `git log main..origin/main --oneline`   |
| push가 거부될 때                           | `git pull` → (충돌 해결) → `git push`   |
| pull 방식을 rebase로 설정                  | `git config --global pull.rebase true`  |
| 원격 브랜치 가져와서 작업                  | `git fetch` → `git switch 브랜치이름`   |

결론적으로, **협업할 때 push가 거부되면 당황하지 말고 `git pull` 먼저!**

다음 글에서는 main에 바로 push하지 않고, 브랜치와 **Pull Request** 로 코드 리뷰를 받으며 협업하는 방법을 배운다. → [08-Pull Request로 협업하기](/devops/git/08-pull-request)

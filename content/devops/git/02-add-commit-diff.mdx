## 1. 저장소 만들기 : git init

프로젝트 폴더에서 다음 명령어를 입력하면, Git이 이 폴더의 **파일 생성·수정을 추적하기 시작** 한다.

```bash
cd my-project
git init   # 현재 폴더를 Git 저장소로 만든다
```

- 폴더 안에 숨김 폴더 **`.git`** 이 생긴다. 이 폴더가 바로 **저장소(repository)** 이고, 모든 버전 기록이 여기에 저장된다.
- `.git` 폴더를 지우면 Git 기록도 모두 사라지므로 직접 건드리지 말자.
- 이미 GitHub에 있는 프로젝트를 받아올 때는 `git init` 대신 `git clone`을 쓴다. → [07-팀원과 함께 작업하기 : clone, pull, fetch](/devops/git/07-clone-pull)

## 2. 버전 만들기 : git add, git commit

Git의 **commit** 기능을 쓰면 파일의 현재 상태를 기록해 둘 수 있다.
정확히 말하면 그 순간 프로젝트의 **스냅샷(사진)** 을 저장하는 것이고, 보통 "기록"보다는 **"버전을 만든다"** 고 부른다.

VS Code에서 `app.txt` 파일을 만들고 내용을 적어 보자.

```txt
aaaaaaaaaaaaa
```

이 상태를 버전으로 남기려면 두 단계를 거친다.

```bash
git add app.txt                 # 1. 커밋할 파일을 고른다 (스테이징)
git commit -m "첫 파일 만듦"     # 2. 메시지와 함께 버전을 만든다 (커밋)
```

이제부터 이 상태로 언제든 되돌아갈 수 있고, 나중에 파일 변경 이력이 궁금하면 열어 볼 수 있다.

---

### 2.1 작업 폴더, 스테이징 영역, 저장소

![git_2_1](https://raw.githubusercontent.com/berenickt/image-server/main/img/git_2_1.png)

```
작업 폴더 (Working Directory)  ──git add──▶  스테이징 영역 (Staging Area)  ──git commit──▶  저장소 (Repository)
   파일을 실제로 수정하는 곳                  커밋할 변경을 골라 담는 곳                    버전(커밋)이 쌓이는 곳
```

- **작업 폴더** : 지금 내가 파일을 만들고 고치는 폴더
- **스테이징 영역(staging area)**
  - 커밋하기 전에 **이번 커밋에 넣을 변경만 골라 담아 두는 곳**
  - 스테이징 영역에 파일을 넣는 것을 **스테이징(staging)** 이라고 하고, `git add`로 한다.
- **저장소(repository)**
  - 커밋된 **버전들이 모여 있는 곳** (실체는 `.git` 폴더)

> 💡 왜 굳이 스테이징이라는 단계가 있을까?
>
> 파일 10개를 고쳤어도, 그중 "로그인 기능" 관련 3개만 먼저 커밋하고 나머지는 다음 커밋으로 나누고 싶을 때가 있다.
> 스테이징은 **커밋을 의미 있는 단위로 나누기 위한 장바구니** 다.

### 2.2 파일의 상태

Git이 보는 파일은 다음 상태 중 하나다. `git status`가 이 상태를 알려 준다.

| 상태                    | 의미                                      | 다음 단계                     |
| ----------------------- | ----------------------------------------- | ----------------------------- |
| **Untracked**           | 새로 만들어서 Git이 아직 추적하지 않는 파일 | `git add`                     |
| **Modified**            | 추적 중인 파일을 수정했지만 아직 스테이징 안 함 | `git add`                 |
| **Staged**              | 다음 커밋에 들어가도록 스테이징됨         | `git commit`                  |
| **Committed (Unmodified)** | 마지막 커밋과 내용이 같음              | 수정하면 다시 Modified        |

---

### 2.3 자주 쓰는 명령어

```bash
# 스테이징
git add 파일명1 파일명2     # 여러 파일을 한 번에 스테이징
git add .                  # 현재 폴더 아래의 모든 변경을 스테이징
git add -p                 # 변경 내용을 조각(hunk)별로 보면서 골라 스테이징

# 상태 확인 — 지금 뭘 하고 있었는지 까먹었을 때 "상태창!!"
git status                 # 변경된 파일, 스테이징된 파일을 보여 줌
git status -s              # 짧게 보기

# 스테이징 취소 (작업 폴더의 수정 내용은 그대로 남음)
git restore --staged 파일명

# 커밋
git commit -m "메시지"      # -m 뒤에 이번 변경을 설명하는 메시지
git commit                 # 메시지를 에디터(VS Code 등)에서 길게 작성

# 커밋 기록 보기
git log                    # 자세히
git log --oneline          # 한 줄씩 짧게
git log --oneline --graph --all   # 모든 브랜치를 그래프로
git show 커밋ID             # 특정 커밋에서 무엇이 바뀌었는지
```

- `git log` 결과가 길면 화면이 멈춘 것처럼 보이는데, **페이저(less)** 화면이다. `j`/`k` 또는 방향키로 스크롤하고 **`q`로 나간다.**
- `git log --oneline`에 보이는 `a1b2c3d` 같은 문자열이 **커밋 ID(해시)** 다. 되돌리기·비교할 때 이 값을 쓴다.

---

### 2.4 커밋은 얼마나 자주, 어떻게?

> ❓ 얼마나 자주 커밋하는 게 좋을까?
>
> `Ctrl + S` 누르듯 습관적으로 할 필요는 없고, **작은 기능 하나를 마칠 때마다** 커밋하면 된다.
>
> 예를 들어 회원가입 기능을 만든다면
>
> - 회원가입 폼 레이아웃을 만들었으면 커밋
> - 이메일 형식 검증 기능을 만들었으면 커밋
> - 서버로 전송하는 기능을 만들었으면 커밋

좋은 커밋의 기준

- **하나의 커밋 = 하나의 목적** : 버그 수정과 새 기능을 한 커밋에 섞지 않기
- **메시지는 "무엇을, 왜"** : `수정`, `ㅇㅇ` 대신 `회원가입 폼 이메일 형식 검증 추가`
- 커밋하기 전에 `git status`와 `git diff`로 **의도한 변경만 들어갔는지 확인** 하기
- 팀에서는 `feat:`, `fix:` 같은 접두사 규칙(Conventional Commits)을 쓰기도 한다. → [11-커밋 메시지 규칙](/devops/git/11-github-profile)

### 2.5 커밋하지 않을 파일 : .gitignore

`node_modules`, 빌드 결과물, 비밀 키가 들어 있는 `.env` 같은 파일은 저장소에 올리면 안 된다.
프로젝트 최상위에 **`.gitignore`** 파일을 만들어 Git이 무시할 파일을 적어 둔다.

```gitignore
# 의존성
node_modules/

# 빌드 결과물
dist/
.next/

# 환경 변수 (비밀 키) ⚠️
.env
.env.local

# OS·에디터 파일
.DS_Store
.vscode/
```

- 이미 커밋된 파일은 `.gitignore`에 적어도 계속 추적된다. 추적을 멈추려면 `git rm --cached 파일명` 후 커밋한다.
- 언어·프레임워크별 템플릿은 [github/gitignore](https://github.com/github/gitignore)에서 가져다 쓸 수 있다.
- ⚠️ 비밀 키를 실수로 커밋해서 GitHub에 올렸다면, 커밋을 지우는 것만으로는 부족하다. **키를 즉시 폐기하고 새로 발급** 하자.

### 2.6 에디터로 add, commit 하기

VS Code 같은 대부분의 에디터에는 Git 기능이 들어 있어서, 터미널 없이도 add·commit을 할 수 있다.

![git_2_2](https://raw.githubusercontent.com/berenickt/image-server/main/img/git_2_2.png)

VS Code 왼쪽의 **소스 제어(Source Control)** 메뉴를 열면 어떤 파일이 변경·추가되었는지 보여 준다.

- 파일 옆 **`+`** 버튼 = `git add`
- 위쪽 메시지 입력 후 **커밋(체크) 버튼** = `git commit`
- 파일을 클릭하면 변경 전후를 나란히 비교해서 보여 준다.

파일이 많고 복잡할 때는 이쪽이 더 편할 수 있다. 다만 **명령어로 무슨 일이 일어나는지 먼저 이해** 해 두면, 문제가 생겼을 때 훨씬 빨리 해결할 수 있다.

## 3. 변경 내용 비교 : git diff

커밋하기 전에 **무엇이 바뀌었는지** 확인하고 싶을 때 `git diff`를 쓴다.

```bash
git diff                   # 작업 폴더 vs 스테이징 영역 (아직 add 안 한 변경)
git diff --staged          # 스테이징 영역 vs 마지막 커밋 (add 해서 곧 커밋될 변경)
git diff HEAD              # 작업 폴더 vs 마지막 커밋 (add 여부와 상관없이 전부)
git diff 커밋ID             # 작업 폴더 vs 특정 커밋
git diff 커밋ID1 커밋ID2    # 두 커밋끼리 비교
git diff --stat            # 파일별로 몇 줄 바뀌었는지만 요약
```

> ⚠️ 헷갈리기 쉬운 점 : 아무 옵션 없는 `git diff`는 "마지막 커밋과의 차이"가 아니라 **"아직 스테이징하지 않은 변경"** 만 보여 준다.
> 그래서 `git add` 하고 나면 `git diff`에 아무것도 안 나온다. 이때는 `git diff --staged`로 확인하자.

결과 읽는 법

```diff
--- a/app.txt        ← 변경 전
+++ b/app.txt        ← 변경 후
@@ -1 +1,2 @@
 aaaaaaaaaaaaa
+bbbbbbbbbbbbb       ← + 로 시작하면 추가된 줄, - 로 시작하면 삭제된 줄
```

- 커밋 ID는 `git log --oneline`으로 확인한다.
- 터미널에서 보는 diff는 파일이 많으면 읽기 힘들어서, 실무에서는 아래의 도구들을 함께 쓰는 경우가 많다.

---

### 3.1 git difftool

`git difftool`을 쓰면 별도 화면에서 **변경 전후를 나란히** 보여 준다.

```bash
git difftool                   # 작업 폴더와 스테이징 영역 비교 (git diff와 같은 기준)
git difftool 커밋ID             # 작업 폴더와 특정 커밋 비교
git difftool 커밋ID1 커밋ID2    # 두 커밋 비교
```

![git_2_3](https://raw.githubusercontent.com/berenickt/image-server/main/img/git_2_3.png)

- 따로 설정하지 않으면 **Vim(vimdiff)** 으로 열린다. `hjkl`로 이동하고, `:qa`로 한 번에 나갈 수 있다. (`:q`는 창 수만큼 여러 번 입력해야 함)
- Vim이 불편하다면 **VS Code로 열리게** 설정하자.

```bash
git config --global diff.tool vscode
git config --global difftool.vscode.cmd 'code --wait --diff $LOCAL $REMOTE'
git config --global difftool.prompt false   # 파일마다 "열까요?" 묻지 않기
```

### 3.2 에디터 확장 프로그램

VS Code의 기본 소스 제어 기능만으로도 파일별 diff를 볼 수 있고, 확장 프로그램을 설치하면 더 편해진다.

- **[Git Graph](https://marketplace.visualstudio.com/items?itemName=mhutchie.git-graph)** : 커밋 기록을 그래프로 한눈에 보고, 커밋을 클릭하면 바뀐 파일과 diff를 바로 확인
  - Extensions 메뉴에서 `git graph` 검색 → 설치 → 소스 제어 메뉴의 **Git Graph 버튼**
- **GitLens** : 코드 한 줄마다 누가 언제 바꿨는지(blame) 표시, 파일·줄 단위 이력 조회

과거 내역을 살펴볼 때는 이런 GUI 도구를 활용하면 훨씬 편하다.

## 4. 정리

| 하고 싶은 것                          | 명령어                               |
| ------------------------------------- | ------------------------------------ |
| 이 폴더를 Git 저장소로 만들기         | `git init`                           |
| 커밋할 파일 고르기                    | `git add 파일명`, `git add .`        |
| 스테이징 취소                         | `git restore --staged 파일명`        |
| 버전 만들기                           | `git commit -m "메시지"`             |
| 현재 상태 확인                        | `git status`                         |
| 커밋 기록 보기                        | `git log --oneline --graph --all`    |
| 아직 add 안 한 변경 보기              | `git diff`                           |
| 곧 커밋될 변경 보기                   | `git diff --staged`                  |
| 커밋하지 않을 파일 지정               | `.gitignore`                         |

다음 글에서는 원본을 건드리지 않고 새 기능을 따로 개발하는 **브랜치** 를 배운다. → [03-브랜치 만들고 합치기 : branch, switch, merge](/devops/git/03-branch-merge)

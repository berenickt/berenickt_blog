## 1. Jenkins란?

**빌드·테스트·배포를 자동화하는 오픈소스 CI/CD 서버** 다.

- `CI(지속적 통합)` : 코드를 push할 때마다 자동으로 빌드·테스트해서, 문제를 빨리 발견한다.
- `CD(지속적 배포/전달)` : 검증된 코드를 자동으로 서버에 배포한다.

```
개발자 push ──▶ GitHub ──webhook──▶ Jenkins ──▶ 빌드 ──▶ 테스트 ──▶ 이미지 생성 ──▶ 배포
                                        │
                                        └──▶ 결과 알림 (Slack, GitHub PR 상태 표시)
```

- Java로 만들어졌고, 2011년 Hudson 프로젝트에서 갈라져 나왔다. 오래된 만큼 자료와 사용 사례가 매우 많다.
- **직접 서버에 설치해서 운영(Self-hosted)** 하는 방식이다.
  - 반대로 GitHub Actions처럼 서비스가 실행 환경을 제공하는 방식도 있다.

cf. CI/CD 개념은 [CI/CD](/cs/terms-principles/ci-cd), DevOps 전체 흐름은 [DevOps 로드맵](/devops) 참고

## 2. 특징

- **플러그인** : 1,800개가 넘는 플러그인으로 Git, Docker, Kubernetes, Slack, AWS 등과 연동
- **Pipeline as Code** : 빌드 과정을 `Jenkinsfile`로 작성해 **코드처럼 저장소에서 관리**
- **분산 빌드** : Controller(관리 서버)가 여러 Agent(작업 서버)에 빌드를 나눠서 실행
- **자유도** : 사내망(폐쇄망), 온프레미스 서버, 특수한 빌드 환경(게임 엔진, 임베디드 등)도 자유롭게 구성 가능
- **단점** : 서버를 직접 운영·업데이트해야 하고, 플러그인이 많아질수록 **버전 호환성과 보안 관리가 번거롭다.**

### 2.1 다른 CI/CD 도구와 비교

| 구분        | Jenkins                          | GitHub Actions                       | GitLab CI/CD                    |
| ----------- | -------------------------------- | ------------------------------------ | ------------------------------- |
| 실행 환경   | 직접 운영하는 서버               | GitHub 제공 Runner (자체 Runner도 가능) | GitLab 제공 Runner (자체도 가능) |
| 설정 파일   | `Jenkinsfile` (Groovy)           | `.github/workflows/*.yml`            | `.gitlab-ci.yml`                |
| 설치·운영   | 직접 설치, 업데이트, 백업 필요   | 설치 불필요                          | GitLab과 함께 제공              |
| 장점        | 자유도·확장성, 사내망 배포, 오래된 레퍼런스 | GitHub와 밀착, 마켓플레이스 액션 | GitLab에 모든 기능 통합         |
| 잘 맞는 곳  | 사내 인프라·보안 규정이 있는 기업, 복잡한 빌드 | GitHub를 쓰는 대부분의 프로젝트 ✅ | GitLab을 쓰는 조직              |

> 💡 새 프로젝트라면 GitHub Actions로 시작하는 경우가 많다. 하지만 **이미 Jenkins를 쓰는 회사가 많고**, 사내망·온프레미스 환경에서는 여전히 Jenkins가 주력인 곳이 많아 알아 두면 좋다.

## 3. 구조 : Controller와 Agent

```
            ┌─────────────────────────┐
            │  Controller (관리 서버)  │  웹 UI, Job 설정, 스케줄링, 플러그인, 결과 저장
            └───────┬───────┬─────────┘
                    │       │   빌드 작업을 나눠 줌
           ┌────────┘       └────────┐
     ┌─────▼─────┐             ┌─────▼─────┐
     │  Agent 1  │             │  Agent 2  │   실제로 빌드·테스트를 실행 (Linux, Windows, Docker, K8s Pod 등)
     └───────────┘             └───────────┘
```

- **Controller** (예전 이름 Master) : 웹 화면, 설정, 스케줄 관리. **빌드를 직접 실행하지 않도록** 하는 것이 권장된다. (보안·안정성)
- **Agent** (예전 이름 Slave) : 실제 빌드를 실행하는 서버. 필요할 때만 Docker 컨테이너나 쿠버네티스 Pod로 띄워 쓰기도 한다.
- **Executor** : Agent 하나가 동시에 실행할 수 있는 빌드 수

## 4. Docker로 실행하기

```bash
docker run -d --name jenkins \
  -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home \
  jenkins/jenkins:lts
```

- `8080` : 웹 화면, `50000` : Agent 연결용 포트
- `jenkins_home` 볼륨에 **모든 설정과 빌드 기록이 저장** 된다. 컨테이너를 지워도 볼륨이 남아 있으면 그대로 복구된다. (이 볼륨을 백업하자)
- 버전은 안정판인 **LTS** 를 쓰자. (Jenkins는 Java 17 이상에서 동작하며, 공식 이미지에는 Java가 포함되어 있다)

`http://localhost:8080`에 접속하면 처음 화면에서 관리자 비밀번호를 묻는다.

```bash
# 초기 관리자 비밀번호 확인
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword
```

1. 비밀번호 입력
2. **Install suggested plugins** (추천 플러그인 설치)
3. 관리자 계정 생성
4. Jenkins URL 확인 → 시작

> ⚠️ 위 컨테이너 안에는 Docker CLI가 없어서, 파이프라인에서 `docker build`를 실행하면 실패한다.
> Docker를 쓰는 빌드는 **Docker가 설치된 Agent** 를 따로 두거나, Docker 플러그인으로 컨테이너 Agent를 띄우는 방식을 쓰자. (Controller에 호스트의 Docker 소켓을 연결하는 방법도 있지만 보안상 권장되지 않는다)

## 5. 주요 용어

| 용어            | 설명                                                                  |
| --------------- | --------------------------------------------------------------------- |
| **Job (Item)**  | Jenkins가 실행하는 작업 단위                                          |
| **Build**       | Job을 한 번 실행한 것 (`#1`, `#2` … 번호가 붙음)                      |
| **Pipeline**    | 여러 단계(Stage)로 이루어진 Job. `Jenkinsfile`로 정의                 |
| **Stage / Step** | 파이프라인의 단계(e.g. Test) / 단계 안의 실제 명령(e.g. `sh 'npm test'`) |
| **Workspace**   | 빌드할 때 소스 코드를 받아 두는 작업 폴더                             |
| **Credentials** | Git 토큰, 서버 SSH 키, 클라우드 키 등 **비밀 정보를 안전하게 보관** 하는 곳 |
| **Artifact**    | 빌드 결과물 (jar, zip, 리포트 등). Jenkins에 보관하거나 다운로드 가능 |

### 5.1 Job의 종류

- **Freestyle project** : 웹 화면에서 클릭으로 설정하는 예전 방식. 간단하지만 설정이 코드로 남지 않는다.
- **Pipeline** : `Jenkinsfile`로 단계를 정의한다. ✅
- **Multibranch Pipeline** : 저장소의 **브랜치와 PR마다 자동으로 파이프라인을 만들어** 실행한다. ✅ 팀 프로젝트에 추천

## 6. Jenkinsfile 작성하기

Jenkinsfile 문법은 **Declarative(선언형)** 와 **Scripted(스크립트형)** 두 가지가 있다. 읽기 쉽고 구조가 정해진 **Declarative** 를 권장한다.

```groovy
pipeline {
  // 이 파이프라인을 실행할 환경 : Node.js 공식 이미지 컨테이너 안에서 실행 (Docker Pipeline 플러그인 필요)
  agent {
    docker { image 'node:22' }
  }

  environment {
    NODE_ENV = 'production'
  }

  options {
    timeout(time: 20, unit: 'MINUTES')   // 너무 오래 걸리면 중단
    disableConcurrentBuilds()            // 같은 Job이 동시에 여러 번 돌지 않게
  }

  stages {
    stage('Install') {
      steps {
        sh 'npm ci'
      }
    }

    stage('Lint & Test') {
      steps {
        sh 'npm run lint'
        sh 'npm test'
      }
    }

    stage('Build') {
      steps {
        sh 'npm run build'
      }
    }

    stage('Deploy') {
      when { branch 'main' }   // main 브랜치일 때만 배포 (Multibranch Pipeline에서 동작)
      steps {
        // Credentials에 저장한 SSH 키로 서버에 배포 (SSH Agent 플러그인)
        sshagent(credentials: ['deploy-server-key']) {
          sh 'rsync -avz --delete dist/ ubuntu@서버주소:/var/www/app/'
        }
      }
    }
  }

  post {
    success { echo '배포 성공' }
    failure { echo '빌드 실패' }
    always  { cleanWs() }       // 작업 폴더 정리 (Workspace Cleanup 플러그인)
  }
}
```

- 저장소 루트에 `Jenkinsfile`을 두고, Jenkins에서 Pipeline(또는 Multibranch Pipeline) Job을 만든 뒤 **Pipeline script from SCM** 을 선택해 저장소를 연결한다.
  - 이렇게 하면 Jenkins가 소스 코드를 **자동으로 checkout** 하므로, Jenkinsfile 안에서 `git` 단계를 따로 쓸 필요가 없다.
- `when { branch 'main' }`은 **Multibranch Pipeline** 에서만 브랜치 정보를 알 수 있어서 동작한다. 일반 Pipeline Job이라면 Job 자체를 main 브랜치용으로 따로 만든다.

### 6.1 비밀 정보 다루기

비밀번호나 토큰을 Jenkinsfile에 **직접 쓰지 말고**, **Manage Jenkins → Credentials** 에 저장한 뒤 ID로 불러온다.

```groovy
stage('Push Image') {
  steps {
    withCredentials([usernamePassword(
      credentialsId: 'dockerhub',
      usernameVariable: 'DOCKER_USER',
      passwordVariable: 'DOCKER_PASS'
    )]) {
      sh 'echo "$DOCKER_PASS" | docker login -u "$DOCKER_USER" --password-stdin'
      sh 'docker push my-org/my-app:${BUILD_NUMBER}'
    }
  }
}
```

- `withCredentials` 안에서 쓴 비밀 값은 빌드 로그에 `****`로 가려져 출력된다.
- `${BUILD_NUMBER}`처럼 Jenkins가 제공하는 환경 변수(빌드 번호, 브랜치 이름 등)를 이미지 태그 등에 쓸 수 있다.

## 7. 빌드를 자동으로 실행하는 방법

| 방법                    | 동작                                                          | 비고                                           |
| ----------------------- | ------------------------------------------------------------- | ---------------------------------------------- |
| **GitHub Webhook** ✅   | push·PR이 생기면 GitHub가 Jenkins에 알림 → 즉시 빌드          | 저장소 Settings → Webhooks → `http://젠킨스주소/github-webhook/` |
| Poll SCM                | 정해진 주기마다 저장소에 변경이 있는지 확인                   | Jenkins가 외부에서 접근 불가능한 사내망일 때   |
| Build periodically      | cron 문법으로 정해진 시간에 빌드                              | e.g. `H 2 * * *` 매일 새벽 2시경 (야간 테스트) |

- cron 문법의 `H`는 "해시(hash)"로, 여러 Job이 정확히 같은 시각에 몰리지 않도록 Jenkins가 시각을 조금씩 분산한다.
- Webhook을 쓰려면 GitHub에서 Jenkins 주소로 접속할 수 있어야 한다. (사내망이라면 Poll SCM이나 별도 중계 설정 필요)
- **GitHub Branch Source** 플러그인 + Multibranch Pipeline을 쓰면 PR마다 빌드하고, 결과(✅/❌)를 **GitHub PR 화면에 표시** 할 수 있다.

## 8. 운영할 때 주의할 점

- **보안**
  - Jenkins는 서버·클라우드 접근 권한을 가진 경우가 많아 **공격 대상이 되기 쉽다.** 관리자 계정·권한을 최소화하고, 인터넷에 그대로 노출하지 말자. (VPN, 방화벽, HTTPS 리버스 프록시)
  - **Jenkins와 플러그인을 꾸준히 업데이트** 하자. 오래된 플러그인의 보안 취약점이 자주 발표된다.
  - Controller의 Executor 수를 0으로 두고, 빌드는 Agent에서만 실행한다.
- **백업** : `jenkins_home`을 정기적으로 백업한다.
- **설정도 코드로** : Jenkins 자체 설정은 **Configuration as Code(JCasC)** 플러그인으로 YAML 파일에 저장해 두면 서버를 새로 만들어도 똑같이 복구할 수 있다.
- **공통 파이프라인 재사용** : 여러 저장소에서 같은 단계를 쓴다면 **Shared Library** 로 묶어 관리한다.
- 파이프라인 시각화 : 예전의 Blue Ocean UI는 더 이상 활발히 개발되지 않으므로, **Pipeline Graph View** 플러그인 등을 쓰는 것이 좋다.

---

## 9. 정리

- Jenkins는 **직접 운영하는 CI/CD 서버** 로, 자유도와 확장성이 가장 큰 장점이다.
- 빌드 과정은 **`Jenkinsfile`(Declarative Pipeline)** 로 저장소에서 코드로 관리하자.
- 비밀 정보는 **Credentials** 에, 빌드는 **Agent** 에서, 실행은 **Webhook** 으로.
- 서버 운영(업데이트, 백업, 보안)이 부담된다면 GitHub Actions 같은 서비스형 CI/CD도 함께 고려하자.

## 0. Git & GitHub란?

| 구분           | 정체                                   | 하는 일                                                       |
| -------------- | -------------------------------------- | ------------------------------------------------------------- |
| **Git**        | 내 컴퓨터에 설치하는 **프로그램**      | 파일 변경 이력 기록, 되돌리기, 브랜치, 병합                   |
| **GitHub**     | Git 저장소를 올려 두는 **웹 서비스**   | 저장소 공유·백업, Pull Request로 코드 리뷰, 협업, 자동화      |
| GitLab, Bitbucket | GitHub와 같은 종류의 서비스         | GitLab은 회사 서버에 직접 설치 가능, Bitbucket은 Jira와 연동  |

- Git은 GitHub 없이도 쓸 수 있다. 하지만 **다른 사람과 함께 작업하거나, 코드를 안전하게 보관하려면** GitHub 같은 원격 저장소가 필요하다.
- 비유하면 Git은 **사진을 찍고 앨범으로 정리하는 카메라**, GitHub는 **그 앨범을 올려 친구들과 함께 보고 댓글을 다는 클라우드 앨범** 이다.

### 0.1 GitHub의 주요 기능

| 기능                    | 설명                                                                 |
| ----------------------- | -------------------------------------------------------------------- |
| **Repository**          | 프로젝트 저장소. 공개(Public) 또는 비공개(Private)                   |
| **Pull Request**        | "내 브랜치의 변경을 합쳐 주세요" 요청 + 코드 리뷰                    |
| **Issues · Projects**   | 할 일, 버그, 기능 요청 관리와 칸반 보드                              |
| **Actions**             | 푸시·PR마다 테스트, 빌드, 배포를 자동으로 실행하는 CI/CD             |
| **Pages**               | 저장소의 정적 파일로 웹사이트 무료 호스팅                            |
| **Codespaces**          | 브라우저에서 바로 쓰는 클라우드 개발 환경                            |
| **Copilot**             | AI 코딩 도우미, PR 요약·리뷰                                         |
| **Dependabot · 보안 스캔** | 의존성 취약점 알림, 비밀 키 유출 탐지                             |

이 글에서는 Git이 왜, 어떻게 지금의 모습이 되었는지 **버전 관리 도구의 역사** 를 따라가 본다.
Git 명령어 실습은 이 시리즈의 다음 글부터 시작한다. (10장)

## 1. 버전 관리란?

**버전 관리(Version Control)** 는 파일의 변경 이력을 기록해 두고, 필요할 때 **이전 상태로 되돌리거나, 누가 언제 무엇을 왜 바꿨는지 확인하고, 여러 사람의 작업을 합치는** 것이다.

버전 관리 도구가 없던 시절의 모습은 이랬다.

```
보고서_최종.docx
보고서_최종_수정.docx
보고서_최종_진짜최종.docx
보고서_최종_진짜최종_팀장님피드백반영.docx
```

- 어떤 파일이 최신인지, 무엇이 바뀌었는지 알 수 없다.
- 두 사람이 같은 파일을 고치면 한 사람의 작업이 덮어써진다.
- 실수로 지운 코드를 되살릴 방법이 없다.

버전 관리 도구는 이 문제를 풀기 위해 **로컬 → 중앙 집중형 → 분산형** 으로 발전해 왔다.

## 2. 한눈에 보는 역사

| ------------- | ------------------------------ | ----------- | ------------------------------------------------------------ |
| 1972          | **SCCS**                       | 1세대(로컬) | 벨 연구소. 최초의 버전 관리 시스템 중 하나                   |
| 1982          | **RCS**                        | 1세대(로컬) | 파일 단위 이력 관리, 변경분(delta)만 저장                    |
| 1986~1990     | **CVS**                        | 2세대(중앙) | 서버 하나에 여러 사람이 접속, 여러 파일·동시 작업 지원       |
| 1990년대      | ClearCase, Visual SourceSafe, Perforce | 2세대 | 기업용 상용 도구들                                         |
| 2000~2004     | **Subversion(SVN)**            | 2세대(중앙) | "더 나은 CVS". 원자적 커밋, 폴더 이력 관리                   |
| 2000~2005     | BitKeeper                      | 3세대(분산) | 상용 분산 버전 관리. 리눅스 커널 개발에 사용                 |
| **2005**      | **Git**, Mercurial             | 3세대(분산) | 리눅스 커널 사태를 계기로 등장한 오픈소스 분산 버전 관리     |
| **2008**      | **GitHub**                     | 협업 플랫폼 | 웹에서 저장소 공유 + **Pull Request** 협업 문화              |
| 2011          | GitLab                         | 협업 플랫폼 | 오픈소스·자체 설치형 Git 플랫폼, CI/CD 통합                  |
| 2018          | 마이크로소프트의 GitHub 인수   |             | Git과 GitHub가 사실상 업계 표준으로 자리 잡음                |
| 2020~         | 기본 브랜치 `main`, SHA-256    |             | Git 자체의 현대화                                            |
| 2020년대      | 초대형 모노레포 도구, Jujutsu, AI | 진행 중  | 대규모 저장소 성능, 더 쉬운 사용성, AI와 협업                |

## 3. 1세대 : 로컬 버전 관리 (1970~80년대)

**내 컴퓨터 안에서만** 파일의 변경 이력을 관리하던 시기다.

### SCCS (Source Code Control System, 1972)

- 벨 연구소의 마크 로크킨드(Marc Rochkind)가 만들었다.
- 파일마다 변경 이력을 저장하는 최초의 버전 관리 시스템 중 하나다.

### RCS (Revision Control System, 1982)

- 월터 티히(Walter Tichy)가 만들었다.
- 파일 전체를 매번 저장하지 않고 **바뀐 부분(delta, 차이)만 저장** 해서 공간을 아꼈다.
- **잠금(Lock) 방식** : 누군가 파일을 수정 중이면 다른 사람은 그 파일을 고칠 수 없다.

**한계**

- 파일 **하나하나** 를 따로 관리해서, "이 기능을 위해 함께 바꾼 파일들"을 묶어서 볼 수 없다.
- 같은 컴퓨터를 쓰는 사람끼리만 공유할 수 있다. 다른 컴퓨터의 동료와 협업하기 어렵다.

## 4. 2세대 : 중앙 집중형 버전 관리 (1990~2000년대)

**중앙 서버 하나에 모든 이력을 저장** 하고, 개발자들은 서버에서 파일을 받아(checkout) 작업한 뒤 다시 올리는(commit) 방식이다.

```
          ┌────────────────┐
          │  중앙 서버      │  ← 모든 이력은 여기에만
          │ (저장소 원본)   │
          └───┬───┬───┬────┘
      checkout│   │   │commit
          ┌───┘   │   └───┐
       개발자A  개발자B  개발자C   ← 각자는 최신 파일만 가짐
```

### CVS (Concurrent Versions System, 1986~1990)

- 1986년 딕 그루너(Dick Grune)가 RCS를 감싸는 셸 스크립트로 시작했고, 1990년 C 언어로 다시 만들어지며 널리 퍼졌다.
- **여러 사람이 같은 파일을 동시에 고칠 수 있게** 했다. (복사 → 수정 → 병합 방식)
  - 잠금 방식처럼 기다릴 필요 없이 각자 고치고, 커밋할 때 충돌이 나면 병합한다.
- 1990년대 오픈소스 프로젝트의 표준이었다. (SourceForge 같은 호스팅 사이트도 CVS를 제공)
- 한계
  - 커밋이 **원자적이지 않다** : 여러 파일을 커밋하다 중간에 실패하면 일부만 반영될 수 있다.
  - 파일 이름 변경·이동, 폴더의 이력을 제대로 관리하지 못한다.
  - 브랜치를 만들고 합치기가 매우 어렵다.

### Subversion (SVN, 2000~2004)

- CollabNet이 "CVS를 제대로 다시 만들자(CVS done right)"는 목표로 2000년에 시작했고, 2004년 1.0이 나왔다. 2010년 아파치 재단 프로젝트가 되었다.
- 개선점
  - **원자적 커밋** : 여러 파일의 변경이 전부 반영되거나, 전부 반영되지 않는다.
  - 폴더 단위 이력, 파일 이름 변경·이동 추적
  - 저장소 전체에 `r1, r2, r3…` 처럼 **하나의 증가하는 리비전 번호** 를 매긴다. → 이해하기 쉽다.
- 2000년대 중후반 기업과 오픈소스에서 가장 많이 쓰였고, 지금도 일부 기업·게임 회사에서 쓰인다.

### 상용 도구들

- **Perforce(Helix Core)** : 대용량 바이너리 파일(그래픽, 영상)을 잘 다뤄서 **게임 업계** 에서 지금도 많이 쓴다.
- ClearCase(IBM), Visual SourceSafe(마이크로소프트) 등

### 중앙 집중형의 한계

- **서버가 죽으면 아무도 일할 수 없다.** 커밋도, 이력 조회도 서버가 있어야 한다.
- 서버 디스크가 고장 나고 백업이 없으면 **모든 이력이 사라진다.** (단일 장애점)
- 인터넷이 없으면 커밋할 수 없다. 모든 명령이 네트워크를 거쳐서 느리다.
- 브랜치 병합이 어려워서 **브랜치를 잘 만들지 않게** 된다. → 기능을 실험하거나 나눠 작업하기 어렵다.

## 5. 3세대 : 분산형 버전 관리 (2000년대 중반~)

**모든 개발자가 저장소의 전체 이력을 통째로 복제(clone)** 해서 갖고 있는 방식이다.

```
     개발자A (전체 이력)  ⇄  원격 저장소 (전체 이력)  ⇄  개발자B (전체 이력)
            ⇅                                              ⇅
     내 컴퓨터에서 커밋·브랜치·이력 조회가 모두 가능
```

- 커밋, 브랜치, 이력 조회를 **내 컴퓨터에서** 한다. → 빠르고, 인터넷이 없어도 된다.
- 모든 개발자의 컴퓨터가 **완전한 백업** 이다. 서버가 사라져도 누구의 저장소로든 복구할 수 있다.
- "중앙 서버"는 기술적으로 필수가 아니라, **팀이 약속한 공유 장소** 일 뿐이다.

### 5.1 BitKeeper와 리눅스 커널 사태 (2002~2005)

- 리눅스 커널은 수천 명이 참여하는 거대 프로젝트라, 1990년대에는 버전 관리 도구 없이 **이메일로 패치(diff)를 주고받으며** 개발했다.
- 2002년부터 상용 분산 버전 관리 도구인 **BitKeeper** 를 무료 라이선스로 쓰기 시작했다.
- 2005년, 커뮤니티의 한 개발자가 BitKeeper의 프로토콜을 분석한 일을 계기로 BitMover사가 **무료 라이선스를 철회** 했다.
- 리눅스 커널 개발팀은 하루아침에 버전 관리 도구를 잃었다.

### 5.2 Git의 탄생 (2005)

- 리눅스를 만든 **리누스 토르발스(Linus Torvalds)** 가 직접 새 도구를 만들기로 했다.
- **2005년 4월** 개발을 시작해 며칠 만에 Git 자신의 코드를 Git으로 관리할 수 있게 되었고, 몇 달 뒤 리눅스 커널 개발에 쓰이기 시작했다.
- 같은 해 7월부터는 **하마노 준오(Junio Hamano)** 가 메인테이너를 맡아 지금까지 관리하고 있다.
- 설계 목표
  - **속도** : 수만 개 파일, 수천 명의 기여자를 감당
  - **분산** : 모두가 전체 이력을 가짐
  - **강력한 브랜치·병합** : 수많은 병렬 작업을 쉽게 합침
  - **데이터 무결성** : 모든 커밋과 파일을 **해시(SHA-1)** 로 식별해서, 이력이 몰래 바뀌면 바로 알 수 있음
- 차이(delta)가 아니라 매 커밋마다 프로젝트 전체의 **스냅샷** 을 저장하는 방식이다. (바뀌지 않은 파일은 이전 것을 가리키기만 해서 효율적)
- 이름의 유래 : 리누스는 농담처럼 "나는 모든 프로젝트에 내 이름을 붙인다. 처음엔 Linux, 이번엔 Git"이라고 말했다. (git은 영국 속어로 "얼간이")

### 5.3 같은 시기의 경쟁자들

| 도구          | 특징                                                                                |
| ------------- | ----------------------------------------------------------------------------------- |
| **Mercurial** | Git과 같은 2005년 4월, 같은 이유로 탄생. 명령어가 쉽고 일관적. 한때 Git과 양강 구도 |
| Bazaar        | 우분투를 만든 캐노니컬(Canonical)이 후원                                            |
| Darcs, Monotone | 독특한 이론(패치 이론 등)을 가진 초기 분산 도구들                                 |

Mercurial은 사용성이 좋아 페이스북(메타), 모질라 등이 오래 사용했지만, 결국 **Git이 압도적인 표준** 이 되었다.

## 6. GitHub와 협업 플랫폼의 시대 (2008~)

Git이 이긴 가장 큰 이유는 Git 자체보다 **GitHub** 였다는 평가가 많다.

- **2008년 GitHub 출시** : Git 저장소를 웹에서 쉽게 만들고 공유하는 서비스
  - **Fork + Pull Request** : 누구나 남의 저장소를 복사(fork)해서 고친 뒤, "이 변경을 반영해 주세요"라고 요청하는 협업 방식
  - 코드 리뷰, 이슈 관리, 위키를 한곳에서
  - 개발자의 저장소·기여 기록이 **포트폴리오** 가 되는 "소셜 코딩"
- 오픈소스가 GitHub로 모이면서 Git이 사실상 표준이 되었다.
  - Bitbucket은 2020년 Mercurial 지원을 종료했고, Google Code(2016 종료) 같은 서비스도 사라졌다.
- **GitLab(2011)** : 회사 서버에 직접 설치할 수 있는 오픈소스 플랫폼, CI/CD를 통합해 DevOps 플랫폼으로 성장
- **Bitbucket** : Atlassian(Jira) 제품과 통합
- **2018년 마이크로소프트가 GitHub를 인수** 했다. 이후 GitHub Actions(CI/CD), Codespaces(클라우드 개발 환경), Copilot(AI 코딩) 등으로 영역을 넓혔다.
- 지금은 개발자 설문에서 응답자 대부분(90% 이상)이 Git을 사용한다.

> 💡 리눅스 커널은 지금도 GitHub의 Pull Request가 아니라 **메일링 리스트로 패치를 주고받는** 전통적인 방식으로 개발한다. Git은 원래 이 방식을 위해 만들어졌다.

## 7. Git의 현재와 발전 (2020년대)

### 7.1 Git 자체의 변화

- **기본 브랜치 이름 `main`** : Git 2.28(2020)에서 기본 브랜치 이름을 설정할 수 있게 되었고, GitHub·GitLab은 새 저장소의 기본값을 `master`에서 `main`으로 바꿨다.
- **SHA-1 → SHA-256** : SHA-1 해시 충돌이 실제로 만들어지면서(2017), 더 안전한 SHA-256 저장소 형식 지원이 추가되었다. 기본값 전환은 앞으로의 Git 3.0과 함께 준비되고 있다.
- **사용성 개선** : 하나의 명령이 너무 많은 일을 하던 `git checkout`을 `git switch`(브랜치 이동)와 `git restore`(파일 되돌리기)로 나눴다. (Git 2.23, 2019)
- **대용량 저장소 성능** : 부분 클론(partial clone), sparse-checkout, 파일 시스템 모니터, 커밋 그래프 등으로 거대한 저장소도 빠르게 다룰 수 있게 되었다.
- **Git LFS(2015)** : 이미지·영상·모델 파일 같은 큰 바이너리를 저장소 밖에 두고 포인터만 관리

### 7.2 초대형 모노레포를 위한 도구

빅테크는 회사 전체 코드를 하나의 저장소(모노레포)에 두기도 하는데, 그 규모가 일반 Git의 한계를 넘는다.

- **Google Piper** : 구글 내부의 거대한 중앙 집중형 버전 관리 시스템
- **Meta Sapling** : 메타가 Mercurial을 기반으로 만들어 2022년 공개한 도구 (Git 저장소와도 연동)
- **Microsoft Scalar** : 윈도우 개발을 위해 만든 대용량 Git 기술이 **Git 본체에 포함** 되었다.

### 7.3 새로운 시도 : Jujutsu (jj)

- 구글 엔지니어가 시작한 오픈소스 버전 관리 도구로, **Git 저장소를 그대로 사용** 하면서 더 쉬운 사용법을 제공한다.
- 작업 중인 변경도 자동으로 커밋으로 다루고, 모든 작업을 되돌릴 수 있는(undo) 등 Git의 어려운 부분을 개선하려는 시도로 주목받고 있다.

### 7.4 협업 방식의 변화

```
이메일 패치 → 중앙 서버 커밋 → Pull Request + 코드 리뷰 → CI 자동 검사 → AI 리뷰·AI가 만든 PR
```

- **브랜치 전략** 의 변화 : 복잡한 Git Flow → 단순한 GitHub Flow, **트렁크 기반 개발**(짧은 브랜치, 자주 병합) → [브랜치 전략](/devops/git/09-flow-trunk-based)
- **스택 PR(Stacked Diffs)** : 큰 변경을 작은 PR 여러 개로 쌓아서 리뷰
- **AI와 버전 관리** : AI 코딩 에이전트가 브랜치를 만들고, 커밋하고, Pull Request를 연다. AI가 PR을 리뷰하기도 한다.
  - 그만큼 **작은 단위의 커밋, 명확한 커밋 메시지, 꼼꼼한 리뷰** 가 더 중요해졌다. 버전 관리는 사람과 AI의 작업을 추적하고 되돌리는 **안전망** 이다.

## 8. 세대별 비교

| 구분              | 로컬 (RCS)          | 중앙 집중형 (SVN)                 | 분산형 (Git)                            |
| ----------------- | ------------------- | --------------------------------- | --------------------------------------- |
| 이력 저장 위치    | 내 컴퓨터           | 중앙 서버에만                     | **모든 개발자 컴퓨터** + 원격 저장소    |
| 협업              | 어려움              | 서버를 통해 가능                  | 자유로움 (원격 저장소 여러 개도 가능)   |
| 오프라인 작업     | 가능 (혼자)         | ❌ 커밋·이력 조회 불가            | ✅ 대부분 가능                          |
| 서버 장애 시      | -                   | 모두 작업 중단, 데이터 유실 위험  | 계속 작업 가능, 누구의 저장소로든 복구  |
| 브랜치·병합       | 거의 없음           | 무겁고 어려움                     | **가볍고 빠름** (브랜치를 마음껏 만듦)  |
| 버전 식별         | 파일별 번호         | 저장소 전체 리비전 번호 (r123)    | 커밋 해시 (`a1b2c3d`)                   |
| 대용량 바이너리   | -                   | 비교적 유리 (잠금 기능)           | 불리 → Git LFS로 보완                   |
| 대표 도구         | SCCS, RCS           | CVS, SVN, Perforce                | **Git**, Mercurial                      |

## 9. 정리

- 버전 관리 도구는 **"혼자 이력 관리" → "서버 하나로 함께 작업" → "모두가 전체 이력을 가진 분산 협업"** 으로 발전했다.
- Git은 리눅스 커널이라는 거대한 프로젝트의 필요에서 태어나, **속도·분산·브랜치·무결성** 이라는 장점과 **GitHub라는 협업 플랫폼** 덕분에 표준이 되었다.
- 지금은 Git을 아는 것이 개발자의 기본기이고, 그 위에서 Pull Request, CI/CD, AI 협업까지 모든 개발 흐름이 돌아간다.

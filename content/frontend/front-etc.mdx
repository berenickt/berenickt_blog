## 1. SEO (검색 엔진 최적화)

검색 엔진이 내 페이지를 **찾고(크롤링), 이해하고(인덱싱), 좋은 순위로 보여 주도록(랭킹)** 만드는 작업이다.

- **렌더링 방식이 가장 중요하다.** 빈 HTML에 JS로 내용을 채우는 CSR은 크롤러가 내용을 늦게 보거나 못 볼 수 있다. → SSR·SSG 사용
- 기본 체크리스트
  - 페이지마다 고유한 `<title>`과 `<meta name="description">`
  - Open Graph(`og:title`, `og:image`) : SNS·메신저 공유 미리보기
  - 시맨틱 HTML과 제목 구조(`h1` → `h2` → `h3`)
  - `robots.txt`, `sitemap.xml`, canonical URL(중복 페이지 정리)
  - **구조화 데이터(JSON-LD)** : 글, 상품, FAQ 정보를 검색 결과에 풍부하게 표시
  - Core Web Vitals(성능)도 순위에 반영된다.
- Next.js는 `metadata` 객체·`generateMetadata`, `sitemap.ts`, `robots.ts`로 이 작업을 지원한다.
- 요즘은 검색 엔진뿐 아니라 **AI 검색·AI 에이전트** 도 페이지를 읽는다. 명확한 구조와 텍스트 콘텐츠가 그 어느 때보다 중요하다.
- 등록 : Google Search Console, 네이버 서치어드바이저 → [도메인 등록 및 웹 분석 도구](/frontend/deploy/02-domain)

## 2. 국제화 (i18n)

**i18n** = internationalization (i와 n 사이에 18글자). 앱을 여러 언어·지역에 맞게 만드는 것이다.

- 번역만이 아니다.
  - 날짜·숫자·통화 형식 : `2026. 11. 20.` vs `11/20/2026`, `₩1,000` vs `$1,000.00`
  - 복수형 : "1 item" / "2 items"
  - 오른쪽에서 왼쪽으로 쓰는 언어(RTL, 아랍어·히브리어) → CSS 논리 속성(`margin-inline-start`) 사용
- **`Intl` API** (브라우저 내장)로 대부분의 형식 처리가 가능하다.

```ts
new Intl.NumberFormat('ko-KR', { style: 'currency', currency: 'KRW' }).format(15000) // '₩15,000'
new Intl.DateTimeFormat('en-US', { dateStyle: 'long' }).format(new Date()) // 'November 20, 2026'
new Intl.RelativeTimeFormat('ko', { numeric: 'auto' }).format(-1, 'day') // '어제'
```

- 라이브러리 : **next-intl**(Next.js), react-i18next, FormatJS(react-intl), Lingui, Paraglide
- URL 전략 : `/ko/about`, `/en/about`처럼 언어별 경로를 두는 것이 SEO에 유리하다. (`hreflang` 태그로 언어 버전 연결)

## 3. 폼(Form)

거의 모든 서비스에 있지만 의외로 까다로운 영역이다. 입력 상태, 유효성 검사, 에러 표시, 제출 중 상태, 서버 에러 처리가 모두 필요하다.

- **React Hook Form** : 입력마다 리렌더링하지 않아 빠르고, 코드가 짧다. 사실상 표준
- **Zod** : 스키마로 유효성 검사 규칙을 정의하고, **같은 스키마를 클라이언트와 서버에서 재사용**
- React 19 + 서버 컴포넌트 : `<form action={serverAction}>`, `useActionState`, `useFormStatus`로 JS가 로드되기 전에도 동작하는 폼
- TanStack Form : 타입 안정성이 강한 대안

```tsx
const schema = z.object({
  email: z.string().email('올바른 이메일을 입력하세요'),
  password: z.string().min(8, '8자 이상 입력하세요'),
})

const { register, handleSubmit, formState: { errors } } = useForm({
  resolver: zodResolver(schema),
})
```

- 기억할 것 : **클라이언트 검증은 사용자 편의, 서버 검증은 보안** 이다. 서버에서도 반드시 다시 검증하자.

## 4. PWA (Progressive Web App)

웹사이트를 **앱처럼 홈 화면에 설치하고, 오프라인에서도 쓰고, 푸시 알림을 받게** 만드는 기술 모음이다.

- **Web App Manifest** (`manifest.json`) : 앱 이름, 아이콘, 테마 색, 시작 URL → 설치 가능해짐
- **Service Worker** : 브라우저와 네트워크 사이에서 요청을 가로채는 스크립트 → 캐싱, 오프라인 지원, 백그라운드 동기화
- **푸시 알림** : iOS도 홈 화면에 설치한 웹 앱에서는 웹 푸시를 지원한다.
- 도구 : Workbox(서비스 워커 캐싱 전략), `vite-plugin-pwa`, Serwist(Next.js)
- 앱 스토어 없이 배포·업데이트할 수 있다는 것이 가장 큰 장점이다.

## 5. 모노레포 (Monorepo)

여러 프로젝트(웹, 어드민, 디자인 시스템, 공통 유틸)를 **하나의 저장소** 에서 관리하는 방식이다.

- 장점 : 공통 코드 공유가 쉽고, 여러 패키지를 한 번에 수정·리뷰할 수 있고, 도구 설정을 통일할 수 있다.
- 단점 : 저장소가 커지면 빌드·CI가 느려진다. → 변경된 패키지만 빌드하고, 결과를 캐싱하는 도구가 필요
- 도구
  - **pnpm workspace** : 패키지 연결의 기본
  - **Turborepo** : 작업 실행 순서 관리 + 빌드 캐싱(원격 캐시)
  - **Nx** : 더 많은 기능(코드 생성, 의존성 그래프, 영향 분석)을 가진 풀 패키지
- 구조 예시

```
apps/
  web/          # 서비스
  admin/        # 어드민
packages/
  ui/           # 디자인 시스템 컴포넌트
  utils/        # 공통 함수
  tsconfig/     # 공통 TS 설정
```

## 6. 마이크로 프론트엔드 (Micro Frontends)

백엔드의 마이크로서비스처럼, **하나의 큰 웹 앱을 여러 팀이 독립적으로 개발·배포하는 작은 앱들로 나누는** 아키텍처다.

- e.g. 쇼핑몰의 검색, 장바구니, 결제를 각 팀이 따로 만들고 따로 배포
- 구현 방법 : **Module Federation**(런타임에 다른 앱의 모듈을 불러옴, Webpack·Rspack·Vite 지원), iframe, 웹 컴포넌트, 서버 측 조합
- 장점 : 팀 독립성, 부분 배포, 점진적인 기술 교체(레거시 → 새 프레임워크)
- 단점 : 공통 의존성 버전 관리, 일관된 디자인 유지, 성능(중복 로드), 운영 복잡도
- **조직이 크고 팀이 많을 때만** 고려하자. 작은 팀에는 모노레포가 훨씬 단순하다.

## 7. 웹 컴포넌트 (Web Components)

브라우저 표준만으로 **어떤 프레임워크에서도 쓸 수 있는 재사용 컴포넌트** 를 만드는 기술이다.

- **Custom Elements** : `<my-button>` 같은 나만의 태그 정의
- **Shadow DOM** : 컴포넌트 내부 스타일·구조를 바깥과 격리
- **HTML Template / Slot** : 재사용할 마크업 틀
- 라이브러리 : **Lit**(구글), Stencil
- 잘 맞는 곳 : 여러 프레임워크를 쓰는 회사의 공통 디자인 시스템, 외부 사이트에 삽입하는 위젯
- React 19부터 Custom Elements를 정식 지원해 속성·이벤트 전달이 자연스러워졌다.

## 8. 크로스 플랫폼 앱

웹 프론트엔드 기술로 모바일·데스크톱 앱을 만드는 방법이다.

| 대상       | 도구                               | 특징                                                          |
| ---------- | ---------------------------------- | ------------------------------------------------------------- |
| 모바일     | **React Native + Expo** ✅         | React 문법으로 네이티브 UI. Expo가 빌드·배포·업데이트를 쉽게 해 줌 |
| 모바일     | Capacitor, Ionic                   | 웹 앱을 그대로 감싸 네이티브 앱으로                           |

| 데스크톱   | **Tauri**                          | Rust 기반, 시스템 웹뷰를 사용해 **앱 크기가 작고 가벼움**     |
| 데스크톱   | Electron                           | Chromium을 포함해 무겁지만 가장 성숙함 (VS Code, Slack, Discord) |

## 9. 에러 처리와 모니터링

- **Error Boundary** : 컴포넌트 렌더링 중 에러가 나도 앱 전체가 하얗게 죽지 않고, 대체 화면을 보여 준다.
  - Next.js는 `error.tsx`, `not-found.tsx`, `global-error.tsx`로 라우트 단위 에러 화면을 제공
  - 이벤트 핸들러·비동기 코드의 에러는 Error Boundary가 잡지 못하므로 `try/catch`로 따로 처리
- **사용자에게 보여 주는 에러** : 무엇이 잘못됐는지, 무엇을 하면 되는지(다시 시도 버튼) 알려 주기
- **모니터링** : Sentry로 사용자 환경의 에러, 발생 브라우저, 재현 경로(세션 리플레이)를 수집 → [프론트엔드 배포 - 모니터링](/frontend/front-deploy)

## 10. 인증 (로그인)

- 방식 : 세션(쿠키) vs 토큰(JWT), 소셜 로그인(OAuth 2.0 / OpenID Connect), **패스키(Passkey)** 로 비밀번호 없는 로그인 확산 중
- 프론트엔드 원칙
  - 토큰은 `localStorage`보다 **HttpOnly 쿠키** 에 저장 (XSS 대비)
  - **화면에서 버튼을 숨기는 것은 보안이 아니다.** 권한 검사는 반드시 서버에서
  - Next.js 미들웨어(Proxy)는 리다이렉트용 1차 확인으로만 쓰고, 데이터 접근 시점에 다시 인증·권한 확인
- 도구 : Auth.js(NextAuth), Better Auth, Clerk, Supabase Auth, Firebase Auth

cf. [로그인의 역사(feat. JWT)](/backend/login)

## 11. 날짜와 시간

시간대(타임존), 서머타임, 서버(UTC)와 사용자(로컬) 시간 차이 때문에 버그가 잘 생기는 영역이다.

- 원칙 : **저장·전송은 UTC(ISO 8601 문자열), 표시할 때만 사용자 시간대로 변환**
- SSR 주의 : 서버와 브라우저의 시간대가 달라 **하이드레이션 불일치** 가 생길 수 있다. 시간 표시는 시간대를 명시하거나 클라이언트에서 렌더링
- 도구
  - `Intl.DateTimeFormat`, `Intl.RelativeTimeFormat` : 형식 표시는 대부분 내장 API로 충분
  - **Temporal** : `Date`를 대체할 새 표준 날짜 API. 시간대·달력 계산을 정확하게 처리하며, 브라우저 지원이 늘어나는 중
  - date-fns, Day.js : 날짜 계산 유틸 (Moment.js는 유지보수 모드라 신규 사용 비추천)

## 12. 프론트엔드에서 AI 기능 붙이기

- **스트리밍 응답** : AI 답변은 한 글자씩 생성되므로, SSE(Server-Sent Events)나 스트리밍 `fetch`로 받아 점점 화면에 그린다.
- **API 키는 서버에** : AI API 키를 프론트엔드 코드에 넣으면 누구나 가져다 쓸 수 있다. 반드시 서버(API 라우트, Server Action)를 거친다.
- 도구 : **Vercel AI SDK**(스트리밍 채팅 UI 훅, 여러 AI 제공사 통합), 각 AI 제공사의 공식 SDK
- 브라우저 안에서 직접 실행 : WebGPU 기반 Transformers.js, WebLLM 등으로 작은 모델을 서버 없이 실행 (개인정보 보호, 비용 절감)
- UX 고려 : 로딩·중단 버튼, 마크다운·코드 블록 렌더링, 응답이 틀릴 수 있다는 안내, 피드백 수집

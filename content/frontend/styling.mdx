## 0. 한눈에 보기

| 방식                         | 대표 도구                                 | 스타일이 만들어지는 시점 | 2026년 현재                       |
| ---------------------------- | ----------------------------------------- | ------------------------ | --------------------------------- |
| Inline Style                 | `style={{ }}`                             | 런타임                   | 동적인 값 한두 개에만             |
| 일반 CSS                     | `.css` 파일                               | 빌드                     | 전역 스타일, 리셋                 |
| CSS Modules                  | `*.module.css`                            | 빌드                     | 안정적인 기본 선택지 ✅            |
| CSS 전처리기                 | Sass(SCSS)                                | 빌드                     | 기존 프로젝트에서 많이 사용       |
| **유틸리티 퍼스트**          | **Tailwind CSS**                          | 빌드                     | 가장 많이 쓰이는 방식 ✅           |
| 런타임 CSS-in-JS             | styled-components, Emotion                | 런타임                   | 신규 채택 감소 (서버 컴포넌트와 충돌) |
| 제로 런타임 CSS-in-JS        | vanilla-extract, Panda CSS, StyleX        | 빌드                     | 타입 안정성이 필요할 때            |

큰 흐름은 **"런타임에 JS로 스타일을 만드는 방식 → 빌드 타임에 CSS 파일로 뽑아내는 방식"** 으로 옮겨 가고 있다.
이유는 성능(JS 실행 비용 감소)과 React 서버 컴포넌트 호환성이다.

## 1. 기본적인 스타일링 방법

### 1.1 Inline Style

```tsx
const style: React.CSSProperties = {
  backgroundColor: 'black',
  color: 'white',
}

const BlackBg = ({ children }: { children: React.ReactNode }) => {
  return <div style={style}>{children}</div>
}
```

- 장점
  - 별도 파일이나 도구 없이 바로 쓸 수 있다.
  - **JS 값에 따라 바뀌는 동적인 스타일** (e.g. 드래그 위치, 진행률 `width: ${percent}%`)에 적합하다.
- 단점
  - `:hover` 같은 가상 클래스, 미디어 쿼리, 애니메이션(`@keyframes`)을 쓸 수 없다.
  - 명시도가 가장 높아서 다른 곳에서 덮어쓰기 어렵고, 컴포넌트 코드가 길어진다.

> 실무에서는 **동적인 값은 CSS 변수로 넘기고, 나머지는 클래스로** 처리하는 방식을 많이 쓴다.
>
> ```tsx
> <div className="progress" style={{ '--percent': `${percent}%` } as React.CSSProperties} />
> ```

---

### 1.2 일반 CSS

```tsx
// App.tsx
import './style.css'

const App = () => {
  return <div className="some-class">내용</div>
}
```

```css
/* style.css */
.some-class {
  background-color: black;
  color: white;
}
```

- 장점
  - 별도 학습 없이 CSS 그대로 사용, 스타일과 컴포넌트 파일을 분리할 수 있다.
- 단점
  - 클래스 이름이 **전역** 이라, 다른 파일의 같은 이름과 충돌할 수 있다.
  - 그래서 BEM 같은 이름 규칙을 팀이 지켜야 한다.
- 지금은 주로 **전역 스타일(리셋, 폰트, CSS 변수 정의)** 에 사용한다.

---

### 1.3 CSS Modules

```tsx
import styles from './Button.module.css'

const Button = () => {
  return <button className={styles.button}>버튼</button>
}
```

```css
/* Button.module.css */
.button {
  border-radius: 5px;
  padding: 5px;
}
```

- 빌드할 때 클래스 이름을 `Button_button__a1b2c` 처럼 **자동으로 고유하게** 바꿔 준다.
- 장점
  - 클래스 이름 충돌이 없다.
  - 순수 CSS라서 런타임 비용이 없고, **서버 컴포넌트에서도 문제없이** 동작한다.
  - Vite, Next.js에 기본 내장되어 설정이 필요 없다.
- 단점
  - 파일이 컴포넌트마다 하나씩 늘어난다.
  - 컴포넌트 props에 따른 스타일 분기는 클래스 조합으로 직접 처리해야 한다. → 2장의 `clsx`

cf. [Next.js - CSS Modules](/frontend/nextjs/05-styling/01-css-modules)

---

### 1.4 모던 CSS로 줄어든 도구의 필요성

예전에 Sass나 CSS-in-JS를 쓰던 이유 상당수가 이제 CSS 자체로 가능하다.

| 예전에 도구가 필요했던 이유 | 지금 CSS로 하는 방법                        |
| -------------------------- | ------------------------------------------- |
| 변수                       | CSS 변수 `--main-color` (런타임에 바꿀 수도 있음) |
| 중첩(nesting)              | 네이티브 CSS 중첩 `.card { & .title { } }`  |
| props에 따른 테마 변경     | CSS 변수 + `data-theme` 속성                |
| 부모 상태에 따른 스타일    | `:has()`                                    |
| 컴포넌트 크기에 따른 반응형 | 컨테이너 쿼리 `@container`                  |
| 스타일 우선순위 관리       | `@layer`                                    |
| 색 조합 계산               | `color-mix()`, 상대 색상 문법               |

> 그래서 **CSS Modules + 모던 CSS** 만으로도 충분한 프로젝트가 많아졌다.

## 2. 클래스 이름 조합 : clsx, classnames

조건에 따라 클래스를 붙였다 뗐다 할 때 문자열을 직접 이어 붙이면 지저분해진다.

```tsx
// 😵 직접 조합
<button className={'button' + (active ? ' active' : '') + (disabled ? ' disabled' : '')} />
```

### 2.1 classnames / clsx

```tsx
import clsx from 'clsx' // 또는 import classNames from 'classnames'

const Button = ({ active, disabled, children }: Props) => {
  // active가 true면 'active' 클래스가 붙는다
  return <button className={clsx('button', { active, disabled })}>{children}</button>
}
```

- 문자열, 객체, 배열을 받아 **truthy인 클래스만** 공백으로 이어 준다.
- `clsx`는 `classnames`와 사용법이 같으면서 더 작고 빨라서, 요즘은 `clsx`를 더 많이 쓴다.

### 2.2 CSS Modules + classnames/bind

```tsx
import classNames from 'classnames/bind'
import styles from './Button.module.css'

const cx = classNames.bind(styles) // styles 객체와 연결

const Button = ({ active, children }: Props) => {
  // 'button' → styles.button 으로 자동 변환
  return <button className={cx('button', { active })}>{children}</button>
}
```

- `styles.button`, `styles.active`를 일일이 쓰지 않고 문자열로 쓸 수 있다.

### 2.3 Tailwind와 함께 쓰는 `cn` 함수

Tailwind에서는 `p-2`와 `p-4`처럼 **충돌하는 클래스** 가 함께 붙으면 의도와 다르게 적용될 수 있다.
그래서 `clsx` + `tailwind-merge`를 합친 `cn` 유틸을 만들어 쓰는 것이 사실상 표준이다. (shadcn/ui 방식)

```ts
import { clsx, type ClassValue } from 'clsx'
import { twMerge } from 'tailwind-merge'

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs))
}

// 뒤에 오는 p-4가 앞의 p-2를 이긴다 → 'p-4 text-white'
cn('p-2 text-white', isLarge && 'p-4')
```

cf. [Tailwind CSS - classNames](/frontend/tailwindcss/02-classNames)

## 3. CSS 전처리기 · 후처리기

### 3.1 Sass (SCSS)

- CSS에 변수, 중첩, 믹스인(`@mixin`), 함수, 반복문, 파일 분할(`@use`)을 추가한 언어
- `.scss` 파일로 작성하면 빌드할 때 CSS로 변환된다. Vite, Next.js 모두 `sass` 패키지만 설치하면 바로 사용 가능
- CSS Modules와 함께 `*.module.scss`로 쓰는 경우가 많다.
- 지금은
  - `@import`가 deprecated 되어 `@use` / `@forward`를 써야 한다.
  - 변수·중첩이 CSS 표준이 되면서 **새 프로젝트에서 꼭 필요한 이유는 줄었지만**, 믹스인과 반복문이 필요한 대규모 스타일 시스템이나 기존 프로젝트에서는 여전히 많이 쓴다.

cf. [Sass](/frontend/sass/01-intro-example)

### 3.2 PostCSS

- CSS를 **JS 플러그인으로 변환** 하는 도구. 그 자체로 문법을 추가하지 않고, 어떤 플러그인을 쓰느냐에 따라 기능이 정해진다.
  - e.g. `autoprefixer` : `-webkit-` 같은 벤더 접두사 자동 추가
  - e.g. `postcss-preset-env` : 최신 CSS 문법을 구형 브라우저용으로 변환
- 직접 설정할 일은 줄었지만, Vite·Next.js·Tailwind 내부에서 여전히 쓰인다.
- 최근에는 Rust 기반 **Lightning CSS** 가 접두사 추가·문법 변환·압축을 더 빠르게 처리하며, Tailwind v4와 Vite에서 사용된다.

cf. [PostCSS](/frontend/postcss)

## 4. 유틸리티 퍼스트 : Tailwind CSS

```tsx
<button className="rounded-lg bg-blue-500 px-4 py-2 text-white hover:bg-blue-600 md:px-6">
  저장
</button>
```

- `p-4`, `text-white`, `md:flex`처럼 **속성 하나에 대응하는 작은 클래스** 를 조합해서 스타일링한다.
- 장점
  - 클래스 이름을 짓지 않아도 되고, HTML과 스타일을 오가지 않아도 된다.
  - 간격·색상·글자 크기가 **정해진 디자인 토큰** 안에서만 쓰여서 디자인이 일관된다.
  - 실제 사용한 클래스만 CSS로 만들어서 **최종 CSS 파일이 작다.**
  - 순수 CSS 결과물이라 서버 컴포넌트와 잘 맞는다.
  - AI 코딩 도구가 가장 잘 다루는 스타일링 방식이기도 하다.
- 단점
  - 클래스가 길어져 마크업이 지저분해 보일 수 있다. → 컴포넌트로 추출해서 해결
  - 처음에는 클래스 이름을 외워야 한다. (에디터 확장 프로그램이 자동 완성 제공)

**Tailwind CSS v4 (2025년 1월)** 에서 바뀐 점

- Rust 기반 새 엔진(Oxide)으로 빌드가 크게 빨라짐
- `tailwind.config.js` 대신 **CSS 파일에서 설정** (CSS-first)

```css
/* app.css */
@import 'tailwindcss';

@theme {
  --color-brand: oklch(0.62 0.19 260);
  --font-display: 'Pretendard', sans-serif;
}
```

- 설정한 토큰이 그대로 **CSS 변수** 로 노출되어, 다른 CSS에서도 `var(--color-brand)`로 쓸 수 있음
- 컨테이너 쿼리(`@container`), 3D 변환, `@starting-style` 등 모던 CSS 기능 기본 지원
- Vite 전용 플러그인(`@tailwindcss/vite`) 제공, 콘텐츠 경로를 자동 감지

**Tailwind와 함께 쓰는 도구**

- `cva`(class-variance-authority) / `tailwind-variants` : `variant="primary" size="lg"` 같은 컴포넌트 변형을 정리
- `prettier-plugin-tailwindcss` : 클래스 순서를 자동 정렬
- **shadcn/ui** : Radix UI(또는 Base UI) + Tailwind로 만든 컴포넌트 코드를 내 프로젝트에 **복사해서** 쓰는 방식. 현재 React 진영에서 가장 많이 쓰는 UI 구성 방법

cf. [Tailwind CSS](/frontend/tailwindcss/01-tailwindcss), [Next.js - Tailwind CSS](/frontend/nextjs/05-styling/02-tailwind-css)

## 5. CSS-in-JS

JS 파일 안에서 CSS를 작성하는 방식이다. 컴포넌트와 스타일이 한 파일에 있고, props로 스타일을 바꾸기 쉽다.

### 5.1 런타임 CSS-in-JS : styled-components, Emotion

```tsx
import styled from 'styled-components' // 또는 '@emotion/styled'

const Button = styled.button<{ $primary?: boolean }>`
  padding: 8px 16px;
  border-radius: 8px;
  background: ${props => (props.$primary ? 'royalblue' : 'white')};
  &:hover {
    opacity: 0.8;
  }
`

<Button $primary>저장</Button>
```

- 장점
  - 스타일이 컴포넌트에 묶여 있어서 함께 옮기고 지우기 쉽다.
  - props에 따라 스타일을 바꾸는 코드가 직관적이다.
  - 클래스 이름 충돌이 없고, `ThemeProvider`로 테마를 쉽게 적용한다.
- 단점
  - 브라우저에서 **JS가 실행되면서 스타일을 만들기 때문에** 런타임 비용이 있고 번들이 커진다.
  - React Context에 의존해서 **React 서버 컴포넌트에서 쓸 수 없다.** (`'use client'` 컴포넌트에서만 가능)
  - SSR을 하려면 스타일을 수집하는 별도 설정이 필요하다.

**2026년 현재 상황**

- React 서버 컴포넌트가 확산되면서 런타임 CSS-in-JS는 **새 프로젝트에서 선택하는 경우가 크게 줄었다.**
- styled-components는 2025년 메인테이너가 **유지보수 모드** 를 선언해, 새 기능 개발보다는 버그·보안 수정 위주로 관리된다.
- Emotion도 계속 쓰이지만(MUI 등 기존 라이브러리 기반), 신규 프로젝트에서는 아래 제로 런타임 방식이나 Tailwind로 옮겨 가는 추세다.
- 기존 프로젝트를 당장 바꿀 필요는 없지만, **새로 시작한다면 다른 방식을 먼저 고려** 하자.

cf. [styled-components](/frontend/styled-components), [Emotion](/frontend/emotion), [Next.js - CSS-in-JS](/frontend/nextjs/05-styling/03-css-in-js)

---

### 5.2 제로 런타임 CSS-in-JS

CSS-in-JS처럼 JS/TS로 작성하지만, **빌드할 때 정적인 CSS 파일로 뽑아내서** 런타임 비용이 없다.

| 도구              | 특징                                                                    |
| ----------------- | ----------------------------------------------------------------------- |
| vanilla-extract   | `.css.ts` 파일에 TS로 스타일 작성. 타입 안전한 테마와 변형(recipes)    |
| Panda CSS         | Chakra UI 팀 제작. 객체 문법 + 유틸리티 클래스 생성, 디자인 토큰 시스템 |
| StyleX            | 메타 제작. Facebook·Instagram 등에서 사용하는 원자적(atomic) CSS 생성   |
| Linaria           | styled-components와 비슷한 문법을 빌드 타임에 CSS로 변환                |

```ts
// button.css.ts (vanilla-extract)
import { style } from '@vanilla-extract/css'

export const button = style({
  padding: '8px 16px',
  borderRadius: 8,
  ':hover': { opacity: 0.8 },
})
```

- 장점 : TS 자동 완성·타입 체크 + 서버 컴포넌트 호환 + 런타임 비용 없음
- 단점 : 빌드 설정이 필요하고, props에 따라 **임의의 값** 으로 스타일을 바꾸기는 런타임 방식보다 불편하다. (미리 정의한 변형이나 CSS 변수로 처리)

## 6. UI 컴포넌트 라이브러리와의 관계

스타일링 방식은 어떤 UI 라이브러리를 쓰느냐와도 연결된다.

| 유형                     | 예시                                   | 스타일링                      |
| ------------------------ | -------------------------------------- | ----------------------------- |
| 완성형(스타일 포함)      | MUI, Ant Design, Mantine, Chakra UI    | 라이브러리의 스타일 시스템 사용 |
| Headless(동작만 제공)    | Radix UI, React Aria, Base UI, Ark UI  | 원하는 방식으로 직접 스타일링  |
| 코드 복사형              | shadcn/ui                              | Tailwind (코드를 직접 수정)    |

- 디자인 시스템이 이미 있다면 → Headless + 우리 스타일
- 빠르게 관리자 화면을 만들어야 한다면 → 완성형
- 커스터마이즈 자유도와 속도를 둘 다 원하면 → shadcn/ui

cf. [UI 라이브러리 종류](/frontend/ui-lib-kind)

## 7. 무엇을 골라야 할까?

```
새 프로젝트인가?
├─ YES
│  ├─ 빠른 개발, 일관된 디자인 토큰, 서버 컴포넌트 사용 → Tailwind CSS (+ shadcn/ui) ✅
│  ├─ CSS 작성 방식이 익숙하고 도구 의존을 줄이고 싶다 → CSS Modules + 모던 CSS ✅
│  └─ 대규모 디자인 시스템, TS 타입 안전성이 중요 → vanilla-extract / Panda CSS / StyleX
└─ NO (기존 프로젝트)
   ├─ Sass, styled-components, Emotion을 쓰고 있다 → 그대로 유지해도 OK
   └─ 서버 컴포넌트로 옮기는 중이다 → 새 컴포넌트부터 CSS Modules나 Tailwind로 점진적 전환
```

정답은 없다. 중요한 것은

- **팀이 합의한 하나의 방식을 일관되게** 쓰는 것
- 렌더링 방식(서버 컴포넌트 여부)과 **성능** 에 맞는지 확인하는 것
- 어떤 도구를 쓰든 결국 **CSS 자체(박스 모델, Flex, Grid, 캐스케이드)를 잘 아는 것** 이 기본이라는 것

## 1. 프론트엔드 테스트란?

- `소프트웨어 테스트` : 소프트웨어가 **기대한 대로 동작하는지 확인하고, 잠재적인 버그를 찾아내는** 과정
- `프론트엔드 테스트` : 그중에서도 **사용자가 보고 조작하는 화면(UI)과 그 동작** 을 검증하는 것
  - e.g. 버튼을 누르면 모달이 열리는가? 잘못된 이메일을 입력하면 에러 메시지가 뜨는가? 로그인하면 대시보드로 이동하는가?

수동으로 브라우저를 열어 확인할 수도 있지만, 기능이 늘어날수록 매번 전부 다시 확인하는 건 불가능하다.
그래서 **코드로 테스트를 작성해 자동으로 반복 실행** 한다.

---

### 1.1 왜 테스트를 해야 할까?

- `신뢰성 확보` : 배포 전에 버그를 찾아, 사용자가 먼저 발견하는 일을 줄인다.
- `안전한 변경` : 리팩터링이나 라이브러리 업데이트 후에도 **기존 기능이 깨지지 않았다는 것** 을 바로 확인할 수 있다.
  - 테스트가 없으면 코드를 고치는 게 무서워지고, 결국 아무도 손대지 못하는 코드가 된다.
- `개발 속도 향상` : 버그는 늦게 발견할수록 고치는 비용이 커진다. 개발 중에 바로 잡으면 디버깅 시간이 줄어든다.
- `살아 있는 문서` : 테스트 코드는 "이 컴포넌트는 이렇게 동작해야 한다"는 명세 역할을 한다.
- `협업` : 다른 사람이 내 코드를 고쳐도 테스트가 지켜 준다. CI에서 자동으로 돌리면 리뷰 부담도 줄어든다.
- `AI 시대에 더 중요` : AI 코딩 도구가 만든 변경이 맞는지 **빠르게 검증하는 안전망** 이 테스트다.

## 2. 테스트 종류

| 종류                   | 무엇을 검증하나                          | 속도  | 비용  | 대표 도구                         |
| ---------------------- | ---------------------------------------- | ----- | ----- | --------------------------------- |
| 정적 분석              | 오타, 타입 오류, 잘못된 패턴             | ⚡⚡⚡ | 낮음  | TypeScript, ESLint                |
| 유닛 테스트            | 함수·훅 하나                             | ⚡⚡⚡ | 낮음  | Vitest, Jest                      |
| 컴포넌트·통합 테스트   | 컴포넌트가 사용자 조작에 맞게 동작하는가 | ⚡⚡   | 중간  | Testing Library, Vitest Browser Mode |
| E2E 테스트             | 실제 브라우저에서 사용자 시나리오 전체   | ⚡     | 높음  | Playwright, Cypress               |
| 시각적 회귀 테스트     | 화면 모양이 의도치 않게 바뀌었는가       | ⚡     | 중간  | Chromatic, Playwright 스크린샷    |
| 접근성 테스트          | 키보드·스크린 리더로 사용 가능한가       | ⚡⚡   | 낮음  | axe-core                          |
| 성능 테스트            | 로딩·반응 속도가 기준을 만족하는가       | ⚡     | 중간  | Lighthouse CI                     |

### 2.1 테스트 피라미드와 테스트 트로피

어떤 테스트를 얼마나 쓸지에 대한 두 가지 관점이 있다.

```
   테스트 피라미드                 테스트 트로피 (Kent C. Dodds)

        /\                            ___
       /E2E\                         |E2E|
      /------\                   ____|___|____
     / 통합   \                 |    통합      |  ← 가장 많이
    /----------\                 \____________/
   /   유닛     \  ← 가장 많이        | 유닛 |
  /--------------\                  |______|
                                  [ 정적 분석 ]
```

- **테스트 피라미드** : 빠르고 싼 유닛 테스트를 가장 많이, 느린 E2E는 적게
- **테스트 트로피** : 프론트엔드에서는 **통합(컴포넌트) 테스트에 가장 많이 투자** 하자는 관점
  - 이유 : UI 버그는 대부분 "함수 하나"보다 **컴포넌트와 상태, API가 맞물리는 곳** 에서 생기기 때문
  - 그리고 TypeScript와 ESLint 같은 정적 분석이 바닥에서 많은 버그를 미리 막아 준다.

> "테스트가 소프트웨어가 사용되는 방식과 닮을수록, 더 큰 확신을 줄 수 있다." — Kent C. Dodds (Testing Library 제작자)

---

### 2.2 유닛 테스트

소프트웨어의 가장 작은 단위(함수, 훅, 유틸)를 **다른 것과 격리해서** 테스트한다.

```ts
// math.ts
export function add(a: number, b: number) {
  return a + b
}

// math.test.ts
import { describe, expect, test } from 'vitest'
import { add } from './math'

describe('add', () => {
  test('1 + 2 = 3', () => {
    expect(add(1, 2)).toBe(3)
  })
})
```

- 잘 맞는 대상 : 가격 계산, 날짜 포맷, 유효성 검사, 데이터 변환처럼 **입력과 출력이 분명한 순수 함수**, 커스텀 훅
- 도구 : **Vitest**(현재 주류), Jest

유닛 테스트는 **FIRST 원칙** 을 따른다.

- `Fast` : 빠르게 실행되어야 한다. 느린 테스트는 피드백을 늦추고 결국 안 돌리게 된다.
- `Isolated/Independent` : 각 테스트는 독립적이어야 하고, 실행 순서에 영향을 받지 않아야 한다.
- `Repeatable` : 어떤 환경에서 몇 번을 돌려도 같은 결과가 나와야 한다. (현재 시간, 랜덤 값, 네트워크에 의존하지 않기)
- `Self-validating` : 사람이 결과를 눈으로 해석할 필요 없이 성공/실패가 명확해야 한다.
- `Timely` : 기능 코드와 같은 시점에 작성하고, 계속 유지보수해야 한다.

### 2.3 컴포넌트·통합 테스트

컴포넌트를 렌더링하고, **사용자처럼 클릭·입력한 뒤, 화면에 보이는 결과를 검증** 한다.
여러 컴포넌트, 상태, (모킹한) API가 함께 동작하는 걸 확인하므로 통합 테스트라고도 부른다.

```tsx
// LoginForm.test.tsx
import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import { expect, test } from 'vitest'
import { LoginForm } from './LoginForm'

test('이메일 형식이 틀리면 에러 메시지를 보여 준다', async () => {
  const user = userEvent.setup()
  render(<LoginForm />)

  // Arrange → Act → Assert
  await user.type(screen.getByLabelText('이메일'), 'wrong-email')
  await user.click(screen.getByRole('button', { name: '로그인' }))

  expect(screen.getByText('올바른 이메일을 입력하세요')).toBeInTheDocument()
})
```

**Testing Library의 핵심 철학 : 구현이 아니라 동작을 테스트한다**

- ❌ 내부 state 값, 클래스 이름, 컴포넌트 구조를 검사 → 리팩터링만 해도 테스트가 깨진다.
- ✅ 사용자가 보고 하는 것(텍스트, 버튼, 레이블)으로 찾고 검증 → 내부를 바꿔도 동작이 같으면 통과한다.

요소를 찾는 쿼리 우선순위

1. `getByRole` : 역할 + 접근 가능한 이름 (`button`, `heading`, `textbox`...) ✅ 가장 권장
2. `getByLabelText` : 폼 요소
3. `getByPlaceholderText`, `getByText`, `getByDisplayValue`
4. `getByAltText`, `getByTitle`
5. `getByTestId` : 위 방법이 모두 안 될 때 최후의 수단

> `getByRole`로 찾을 수 없는 요소는 스크린 리더 사용자도 찾기 어렵다는 뜻이다. **테스트를 쓰다 보면 접근성도 좋아진다.**

쿼리 종류

- `getBy...` : 없으면 바로 에러 (지금 있어야 하는 요소)
- `queryBy...` : 없으면 `null` (없는 것을 확인할 때)
- `findBy...` : 나타날 때까지 기다림 (비동기로 나타나는 요소)

**API 모킹 : MSW(Mock Service Worker)**

컴포넌트가 실제 서버를 호출하면 테스트가 느려지고 불안정해진다.
MSW는 **네트워크 레벨에서 요청을 가로채 가짜 응답** 을 준다. `fetch`든 Axios든 TanStack Query든 코드 수정 없이 그대로 동작한다.

```ts
import { http, HttpResponse } from 'msw'
import { setupServer } from 'msw/node'

const server = setupServer(
  http.get('/api/user', () => HttpResponse.json({ name: '홍길동' })),
)

beforeAll(() => server.listen())
afterEach(() => server.resetHandlers())
afterAll(() => server.close())
```

- 같은 핸들러를 개발 중 브라우저, Storybook, 테스트에서 모두 재사용할 수 있다.

**jsdom vs 실제 브라우저**

- 기본적으로 Vitest·Jest는 **jsdom**(Node에서 흉내 낸 가짜 DOM)에서 컴포넌트를 렌더링한다. 빠르지만 레이아웃, CSS, 일부 브라우저 API는 동작하지 않는다.
- **Vitest Browser Mode** 나 Storybook의 Vitest 연동을 쓰면 **실제 브라우저(Playwright 기반)** 에서 컴포넌트 테스트를 돌릴 수 있어, 점점 이 방식이 늘고 있다.

cf. [React Testing Library](/frontend/react-testing-library)

### 2.4 E2E 테스트

**실제 브라우저를 띄워** 사용자 시나리오를 처음부터 끝까지 실행한다. 프론트엔드·백엔드·DB가 모두 맞물려 동작하는지 확인할 수 있다.

```ts
// e2e/login.spec.ts (Playwright)
import { expect, test } from '@playwright/test'

test('로그인하면 대시보드로 이동한다', async ({ page }) => {
  await page.goto('/login')

  await page.getByLabel('이메일').fill('test@example.com')
  await page.getByLabel('비밀번호').fill('password123')
  await page.getByRole('button', { name: '로그인' }).click()

  await expect(page).toHaveURL(/\/dashboard/)
  await expect(page.getByRole('heading', { name: '환영합니다' })).toBeVisible()
})
```

| 도구           | 특징                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------- |
| **Playwright** ✅ | 마이크로소프트 제작. Chromium·Firefox·WebKit(Safari) 모두 지원, 병렬 실행이 빠르고 무료. 자동 대기, 코드 생성기(`codegen`), 실행 과정을 되돌려 보는 Trace Viewer. 현재 가장 많이 선택됨 |
| Cypress        | 브라우저 안에서 실행되어 테스트 과정을 눈으로 보며 디버깅하기 좋음. 시간 여행 디버거. 기존 프로젝트에서 여전히 많이 사용 |

- E2E 테스트는 느리고 깨지기 쉬우므로, **로그인, 결제, 회원가입처럼 비즈니스에 치명적인 핵심 흐름** 위주로 작성한다.
- React 서버 컴포넌트(async 컴포넌트)는 jsdom 기반 컴포넌트 테스트로 다루기 어려워서, **서버 컴포넌트가 포함된 페이지는 E2E로 검증** 하는 것이 권장된다.

cf. [Cypress](/frontend/cypress), [Next.js - Playwright](/frontend/nextjs/08-testing/03-playwright)

### 2.5 스냅샷 테스트

렌더링 결과를 파일로 저장해 두고, 다음 실행 때 **달라진 부분이 있는지** 비교한다.

```tsx
import { render } from '@testing-library/react'
import { expect, test } from 'vitest'
import { MyComponent } from './MyComponent'

test('렌더링 결과가 바뀌지 않았다', () => {
  const { asFragment } = render(<MyComponent />)
  expect(asFragment()).toMatchSnapshot()
})
```

- 장점 : 작성이 매우 쉽다.
- 단점 : 무엇이 "맞는" 결과인지 검증하지 않고 **"바뀌었는지"만** 본다.
  - 스냅샷이 커지면 리뷰어가 diff를 제대로 보지 않고 `-u`(업데이트)로 덮어쓰기 쉽다.
- 그래서 지금은 큰 컴포넌트 전체 스냅샷보다는
  - 작은 데이터 구조·에러 메시지에 **인라인 스냅샷**(`toMatchInlineSnapshot`)을 쓰거나,
  - 화면 모양 확인은 아래 **시각적 회귀 테스트** 로 대체하는 경우가 많다.

### 2.6 시각적 회귀 테스트

DOM 구조가 아니라 **실제 화면 스크린샷** 을 비교해, CSS 변경으로 인한 의도치 않은 UI 깨짐을 잡는다.

- 도구 : Chromatic(Storybook 제작사), Percy, Playwright의 `toHaveScreenshot()`
- **Storybook** 과 함께 쓰면 좋다.
  - 컴포넌트를 상태별(기본, 로딩, 에러, 비활성화...)로 **스토리** 로 만들어 두면
  - 문서 + 디자이너 리뷰 + 시각적 테스트 + 상호작용 테스트를 한 곳에서 할 수 있다.

cf. [Storybook](/frontend/storybook)

### 2.7 접근성 테스트

- **axe-core** 로 자동 검사 : `vitest-axe`, `@axe-core/playwright`, Storybook a11y 애드온
  - 대체 텍스트 누락, 명도 대비 부족, 레이블 없는 입력 등을 자동으로 찾아 준다.
- 단, 자동 검사로 찾을 수 있는 건 일부다. **키보드만으로 직접 써 보고, 스크린 리더로 들어 보는** 수동 확인이 함께 필요하다.

### 2.8 성능 테스트

- 응답 시간, 로딩 속도, 자원 사용량을 측정해 성능 문제를 찾는다.
- 도구
  - **Lighthouse** / PageSpeed Insights : 성능, 접근성, SEO 점수와 개선 방법
  - **Lighthouse CI** : PR마다 성능 점수를 측정해, 기준보다 떨어지면 실패 처리
  - 개발자 도구 Performance 탭 : 느린 렌더링, 긴 작업(Long Task) 분석
  - `web-vitals` 라이브러리 : 실제 사용자의 LCP, INP, CLS 수집
- 번들 크기 제한 도구(`size-limit` 등)로 "번들이 갑자기 커지는 것"도 테스트처럼 막을 수 있다.

## 3. 2026년 테스트 도구 정리

| 용도                 | 추천                           | 대안 / 참고                         |
| -------------------- | ------------------------------ | ----------------------------------- |
| 테스트 러너          | **Vitest**                     | Jest (기존 프로젝트, React Native)  |
| 컴포넌트 테스트      | **Testing Library** + `user-event` | Vitest Browser Mode             |
| API 모킹             | **MSW**                        |                                     |
| E2E                  | **Playwright**                 | Cypress                             |
| 컴포넌트 문서·시각 테스트 | **Storybook** + Chromatic  | Playwright 스크린샷                 |
| 접근성               | axe-core                       |                                     |
| 성능                 | Lighthouse CI                  |                                     |

**Vitest vs Jest**

- Jest는 오랫동안 JS 테스트의 표준이었지만, ESM·TypeScript 설정이 번거롭다.
- Vitest는 **Vite 설정을 그대로 재사용** 하고, ESM·TS를 기본 지원하며, Jest와 거의 같은 API(`describe`, `test`, `expect`)를 쓴다.
- 그래서 Vite 기반 프로젝트는 물론, 새 프로젝트 대부분이 Vitest를 선택한다. Jest에서 옮기는 것도 어렵지 않다.

cf. [Jest](/frontend/jest), [Next.js - Vitest](/frontend/nextjs/08-testing/01-vitest)

## 4. 좋은 테스트를 쓰는 법

- **AAA 패턴** : `Arrange(준비) → Act(실행) → Assert(검증)` 순서로 구분해서 쓴다.
- **테스트 이름은 동작을 설명하는 문장** 으로 : `'이메일 형식이 틀리면 에러 메시지를 보여 준다'`
- **테스트 하나에 시나리오 하나** : 실패했을 때 무엇이 깨졌는지 바로 알 수 있게
- **구현 세부 사항을 테스트하지 않는다** : 내부 함수 호출 횟수, state 값보다 사용자가 보는 결과를 검증
- **모킹은 최소한으로** : 너무 많이 모킹하면 "모킹이 잘 동작하는지"를 테스트하게 된다. 네트워크 경계(MSW)에서만 모킹하는 것이 좋다.
- **시간·랜덤에 의존하지 않기** : `vi.useFakeTimers()`, 고정된 시드 사용
- **불안정한 테스트(Flaky Test)는 바로 고친다** : 가끔 실패하는 테스트를 방치하면 팀이 테스트 결과를 믿지 않게 된다.
  - 원인 대부분은 비동기 대기 부족 → `findBy...`, Playwright의 자동 대기(`expect(...).toBeVisible()`) 활용
- **커버리지는 지표일 뿐 목표가 아니다** : 100%를 채우려고 의미 없는 테스트를 쓰기보다, 중요한 흐름을 확실히 지키는 게 낫다.
- **CI에서 자동 실행** : PR마다 린트 → 타입 체크 → 유닛·컴포넌트 테스트 → E2E 순으로 돌린다. → [CI/CD](/cs/terms-principles/ci-cd)

## 5. 소프트웨어 테스트 7가지 원칙

ISTQB(International Software Testing Qualifications Board)의 기본 원칙이다.

1. **테스팅은 결함이 있음을 보여 줄 뿐이다** (Testing shows presence of defects)
   - 테스트를 통과해도 "버그가 없다"는 증명은 아니다.
2. **완벽한 테스팅은 불가능하다** (Exhaustive testing is impossible)
   - 모든 입력 조합을 테스트할 수 없으니, 위험도에 따라 우선순위를 정한다.
3. **조기 테스팅** (Early testing)
   - 일찍 테스트할수록 버그를 고치는 비용이 싸다.
4. **결함 집중** (Defect clustering)
   - 버그는 소수의 복잡한 모듈에 몰려 있는 경우가 많다. 그곳을 더 촘촘히 테스트한다.
5. **살충제 역설** (Pesticide paradox)
   - 같은 테스트만 반복하면 새로운 버그를 찾지 못한다. 테스트도 계속 보완해야 한다.
6. **테스팅은 정황에 의존한다** (Testing is context dependent)
   - 결제 시스템과 개인 블로그의 테스트 수준은 달라야 한다.
7. **오류 부재의 궤변** (Absence-of-errors fallacy)
   - 버그가 없어도 **사용자가 원하는 기능이 아니면** 소용없다.

## 6. 테스트 주도 개발(TDD)

`Test Driven Development(TDD)` : **실제 코드보다 테스트 코드를 먼저 작성** 하는 개발 방법

### 6.1 Red → Green → Refactor

1. 🔴 **Red** : 아직 없는 기능에 대한 테스트를 먼저 작성한다. → 당연히 실패
2. 🟢 **Green** : 테스트를 통과하는 **최소한의 코드** 를 작성한다.
3. 🔵 **Refactor** : 테스트가 통과하는 상태를 유지하면서 코드를 깔끔하게 다듬는다.
4. 다시 1번으로 반복

### 6.2 TDD 장점

- 코드에 안정감이 생긴다. 모든 기능에 처음부터 테스트가 붙어 있기 때문이다.
- 개발 시간의 많은 부분을 차지하는 디버깅 시간이 줄어든다.
- 테스트하기 쉬운 코드 = 의존성이 적고 역할이 분명한 코드라서, 자연스럽게 **설계가 좋아진다.**
- "무엇을 만들어야 하는지"를 먼저 정리하게 되어 요구사항이 명확해진다.

### 6.3 TDD의 한계와 현실적인 사용법

- UI는 디자인이 자주 바뀌고, 결과를 눈으로 봐야 하는 부분이 많아서 **모든 화면을 TDD로 만들기는 어렵다.**
- 그래서 프론트엔드에서는 보통
  - **비즈니스 로직, 유틸 함수, 커스텀 훅, 폼 유효성 검사** 처럼 입력과 출력이 분명한 부분에 TDD를 적용하고,
  - 화면은 만든 뒤 핵심 동작에 대한 컴포넌트·E2E 테스트를 추가하는 방식을 많이 쓴다.
- AI 코딩 도구와 함께 쓸 때도 **테스트를 먼저 작성하고 AI에게 통과하는 구현을 맡기는** 방식이 결과물을 검증하기 좋아 다시 주목받고 있다.

## 1. 배포란?

**배포(Deploy)** = 내 컴퓨터에서 만든 앱을 **사용자가 인터넷으로 접속할 수 있는 곳에 올리는 것** 이다.

```
코드 작성 → 빌드(npm run build) → 결과물 업로드 → 서버/CDN에서 서비스 → 도메인 연결 → 사용자 접속
```

프론트엔드 배포에서 가장 먼저 알아야 할 것은 **"빌드 결과물이 무엇인가"** 다. 이에 따라 배포 방식이 완전히 달라진다.

---

### 1.1 빌드 결과물의 3가지 형태

| 형태                 | 결과물                                 | 예시                                          | 필요한 것                     |
| -------------------- | -------------------------------------- | --------------------------------------------- | ----------------------------- |
| **정적 파일**        | HTML, CSS, JS, 이미지 파일 묶음        | Vite + React(SPA), Astro, Next.js `output: 'export'` | 파일 서버(CDN)만 있으면 됨    |
| **Node.js 서버**     | 요청마다 HTML을 만드는 서버 프로그램   | Next.js(SSR, 서버 컴포넌트), Nuxt, SvelteKit, React Router | 서버를 계속 실행할 곳         |
| **서버리스 / 엣지 함수** | 요청이 올 때만 실행되는 함수        | Vercel·Netlify·Cloudflare에 올린 Next.js, Nuxt 등 | 플랫폼이 알아서 실행          |

- **정적 파일** 은 가장 싸고 빠르고 단순하다. 전 세계 CDN에 복사해 두기만 하면 된다.
- **SSR이나 서버 컴포넌트를 쓰면 서버가 필요** 하다. 직접 서버를 띄우거나, 서버리스 플랫폼에 맡긴다.
- 메타 프레임워크는 한 앱 안에서 이 셋을 섞는다. (정적 페이지는 CDN, 동적 페이지는 서버 함수)

cf. 렌더링 방식 차이는 [CSR, SSR, SSG](/frontend/nextjs/00-csr-ssr-ssg) 참고

---

### 1.2 꼭 알아야 할 용어

- **빌드(Build)** : 소스 코드를 브라우저·서버가 실행할 수 있는 최적화된 결과물로 바꾸는 과정 (번들링, 압축, 트랜스파일)
- **호스팅(Hosting)** : 결과물을 올려 두고 요청에 응답해 주는 서비스
- **CDN(Content Delivery Network)** : 전 세계 여러 서버에 파일을 복사해 두고, **사용자와 가장 가까운 서버** 에서 응답하는 네트워크
- **서버리스(Serverless)** : 서버를 직접 관리하지 않고, 요청이 올 때만 코드가 실행되며 사용한 만큼만 비용을 내는 방식
- **엣지(Edge)** : CDN 서버(사용자 가까운 곳)에서 직접 코드를 실행하는 것. 응답이 빠르지만 사용할 수 있는 Node.js API에 제한이 있다.
- **DNS** : `example.com` 같은 도메인을 실제 서버 IP 주소로 바꿔 주는 시스템 → [도메인 등록](/frontend/deploy/02-domain)
- **CI/CD** : 코드를 푸시하면 테스트·빌드·배포가 자동으로 실행되는 파이프라인 → [CI/CD](/cs/terms-principles/ci-cd)

## 2. 배포 플랫폼 비교

### 2.1 프론트엔드 특화 플랫폼 (PaaS)

Git 저장소만 연결하면 **푸시할 때마다 자동으로 빌드·배포** 해 준다. 처음 배포한다면 여기서 시작하자.

| 플랫폼                                           | 특징                                                                                 | 잘 맞는 경우                         |
| ------------------------------------------------ | ------------------------------------------------------------------------------------ | ------------------------------------ |
| [Vercel](https://vercel.com/) ✅                 | Next.js 제작사. Next.js의 모든 기능(서버 컴포넌트, ISR, 이미지 최적화)이 설정 없이 동작 | Next.js 프로젝트                     |
| [Netlify](https://www.netlify.com/)              | 정적 사이트·Jamstack의 원조. 폼 처리, 서버리스 함수 내장                             | 정적 사이트, Astro, 다양한 프레임워크 |
| [Cloudflare Pages / Workers](https://pages.cloudflare.com/) | 전 세계 엣지 네트워크, **대역폭 요금이 없어** 트래픽이 많아도 저렴             | 트래픽이 많은 사이트, 비용 민감      |
| [GitHub Pages](https://pages.github.com/)        | GitHub 저장소에서 정적 사이트 무료 호스팅                                            | 개인 블로그, 문서, 포트폴리오        |
| [Firebase Hosting](https://firebase.google.com/products/hosting) | 구글 제공, Firebase 인증·DB와 함께 쓰기 편함                          | Firebase 백엔드를 쓰는 앱            |

### 2.2 클라우드 / 직접 운영

| 방식                                         | 특징                                                                       |
| -------------------------------------------- | -------------------------------------------------------------------------- |
| AWS S3 + CloudFront                          | 정적 파일을 S3에 올리고 CloudFront(CDN)로 서비스. 저렴하고 안정적          |
| AWS Amplify                                  | AWS의 Vercel 같은 서비스. Git 연동 자동 배포, Next.js SSR 지원             |
| Render, Railway, Fly.io                      | Docker나 Node 서버를 간단히 올릴 수 있는 PaaS                              |
| Docker + 서버(EC2, ECS, Kubernetes 등)       | 자유도가 가장 높지만 서버·보안·확장을 직접 관리해야 함                     |

- Next.js를 Vercel이 아닌 곳에 올릴 때는
  - `next.config`의 `output: 'standalone'`으로 Node 서버를 만들어 **Docker** 로 배포하거나,
  - **OpenNext** 같은 어댑터로 AWS Lambda, Cloudflare Workers용으로 변환한다.

cf. [Vercel 배포, GitHub Actions + EC2, Elastic Beanstalk + Docker 실습](/frontend/deploy/01-deploy), [Next.js 배포](/frontend/nextjs/10-deploying)

---

### 2.3 무엇을 골라야 할까?

```
빌드 결과물이 정적 파일뿐인가? (SPA, SSG)
├─ YES
│  ├─ 개인 블로그·포트폴리오 → GitHub Pages, Cloudflare Pages (무료)
│  ├─ 회사 서비스 → Cloudflare Pages, Netlify, S3 + CloudFront
│  └─ 이미 AWS를 쓰고 있다 → S3 + CloudFront
└─ NO (SSR, 서버 컴포넌트, API 라우트 사용)
   ├─ Next.js + 빠르게 배포하고 싶다 → Vercel ✅
   ├─ 트래픽이 많고 비용이 걱정된다 → Cloudflare(OpenNext), 직접 운영(Docker)
   ├─ 회사 인프라(AWS, 사내 서버) 규정이 있다 → Docker + ECS/EKS, Amplify
   └─ 백엔드와 함께 한 서버에 올리고 싶다 → Docker + Render·Railway·Fly.io·EC2
```

> 💡 비용 주의 : 서버리스 플랫폼은 **사용량에 따라 요금이 붙는다.** 갑자기 트래픽이 몰리거나 봇 공격을 받으면 예상보다 큰 청구서가 올 수 있다.
> 사용량 알림과 지출 한도(Spend Limit)를 꼭 설정해 두자.

## 3. 배포 파이프라인 (CI/CD)

### 3.1 일반적인 흐름

```
PR 생성
 ├─ 린트 · 타입 체크 · 테스트 (CI)
 ├─ 미리보기(Preview) 배포 → PR마다 고유 URL 생성, 리뷰어·디자이너가 직접 확인
 └─ 코드 리뷰 승인
main 브랜치에 merge
 ├─ 프로덕션 빌드
 ├─ 배포 (CD)
 └─ 배포 후 확인 (스모크 테스트, 모니터링)
```

- **미리보기 배포** 는 Vercel, Netlify, Cloudflare Pages가 기본으로 제공한다. 코드 리뷰와 QA 효율이 크게 올라간다.
- 직접 구성할 때는 **GitHub Actions** 를 가장 많이 쓴다.

---

### 3.2 예시 : GitHub Actions로 Vite 앱을 GitHub Pages에 배포

```yaml
# .github/workflows/deploy.yml
name: Deploy

on:
  push:
    branches: [main] # main에 푸시하면 실행

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      - run: pnpm install --frozen-lockfile # lock 파일과 정확히 같은 버전 설치
      - run: pnpm lint && pnpm test
      - run: pnpm build
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist # 빌드 결과물 폴더

  deploy:
    needs: build # build가 성공해야 실행
    runs-on: ubuntu-latest
    environment:
      name: github-pages
    steps:
      - uses: actions/deploy-pages@v4
```

- `workflow` : `.github/workflows/*.yml`에 정의한 자동화 과정
- `on` : 언제 실행할지 (push, pull_request, 스케줄 등)
- `jobs` / `steps` : 실행할 작업과 단계. `needs`로 순서를 정한다.
- 비밀 값(API 키, 클라우드 인증 정보)은 저장소 **Settings → Secrets** 에 넣고 `${{ secrets.NAME }}`으로 쓴다.

## 4. 배포할 때 자주 겪는 문제

### 4.1 SPA 새로고침 시 404

- SPA는 `index.html` 하나만 있고, `/about` 같은 경로는 **브라우저의 JS 라우터** 가 처리한다.
- 그런데 `/about`에서 새로고침하면 서버는 `about.html` 파일을 찾다가 없어서 **404** 를 응답한다.
- 해결 : **모든 경로를 `index.html`로 보내는 설정(fallback / rewrite)** 을 추가한다.
  - Netlify : `public/_redirects`에 `/*  /index.html  200`
  - Vercel : `vercel.json`의 `rewrites`
  - Nginx : `try_files $uri $uri/ /index.html;`
  - GitHub Pages : `404.html`을 `index.html`과 같게 복사하는 우회 방법 사용

### 4.2 환경 변수

- 개발·스테이징·프로덕션마다 API 주소, 키가 다르므로 **환경 변수** 로 분리한다.
- 프론트엔드 환경 변수는 **빌드할 때 코드에 박힌다.** 환경 변수를 바꾸면 **다시 빌드** 해야 반영된다.
- ⚠️ 브라우저로 나가는 환경 변수는 **누구나 볼 수 있다.**
  - Vite의 `VITE_`, Next.js의 `NEXT_PUBLIC_` 접두사가 붙은 값은 클라이언트 번들에 그대로 포함된다.
  - 비밀 키(DB 비밀번호, 결제 시크릿 키)는 절대 이 접두사를 붙이지 말고, 서버 코드에서만 사용한다.
- `.env` 파일은 `.gitignore`에 넣고, 배포 플랫폼의 환경 변수 설정 화면이나 Secrets로 관리한다.

### 4.3 캐싱과 "배포했는데 안 바뀌어요"

- 빌드 도구는 JS·CSS 파일 이름에 **해시** 를 붙인다. (e.g. `index-3f9a1c.js`)
  - 내용이 바뀌면 파일 이름도 바뀌므로, 이런 파일은 **1년 캐시**(`Cache-Control: public, max-age=31536000, immutable`)해도 안전하다.
- 반면 `index.html`은 이름이 바뀌지 않으므로 **캐시하지 않거나 짧게**(`no-cache`) 설정해야 새 버전의 JS를 불러온다.
- CDN을 직접 운영한다면 배포 후 **캐시 무효화(invalidation)** 가 필요할 수 있다.

### 4.4 버전 불일치 (Version Skew)

- 사용자가 페이지를 열어 둔 사이에 새 버전이 배포되면, 브라우저의 **옛날 JS** 가 **새 서버** 와 통신하면서 에러가 날 수 있다.
  - e.g. 이미 삭제된 JS 청크를 불러오려다 실패, 서버 액션 ID가 바뀌어 호출 실패
- 대응 : 이전 버전 파일을 일정 기간 유지, 청크 로드 실패 시 새로고침 유도, Vercel의 Skew Protection 같은 플랫폼 기능 사용

## 5. 안전하게 배포하는 전략

| 전략                     | 방법                                                                 | 장점                         |
| ------------------------ | -------------------------------------------------------------------- | ---------------------------- |
| 즉시 교체                | 새 버전으로 한 번에 바꿈                                             | 가장 단순                    |
| 블루-그린(Blue-Green)    | 새 환경(그린)을 미리 띄워 두고, 확인 후 트래픽을 한 번에 전환        | 문제 시 즉시 원래 환경으로   |
| 카나리(Canary)           | 새 버전을 일부 사용자(e.g. 5%)에게만 먼저 공개하고 점차 늘림          | 문제의 영향 범위가 작음      |
| 피처 플래그(Feature Flag) | 코드는 배포하되, 기능은 설정으로 켜고 끔                            | 배포와 기능 공개를 분리      |

- **롤백** : 문제가 생기면 이전 버전으로 **즉시** 되돌릴 수 있어야 한다.
  - Vercel·Netlify·Cloudflare는 이전 배포를 클릭 한 번으로 다시 프로덕션으로 올릴 수 있다.
  - 직접 운영한다면 이전 Docker 이미지 태그를 남겨 두자.
- 금요일 오후 배포는 피하자. 문제가 생겼을 때 대응할 사람이 없다.

## 6. 배포 후 : 모니터링

배포는 끝이 아니라 시작이다. 사용자 환경에서 무슨 일이 일어나는지 알아야 한다.

- **에러 추적** : [Sentry](https://sentry.io/) 등으로 사용자 브라우저에서 난 에러를 수집
  - 빌드 시 **소스맵** 을 업로드해야 압축된 코드가 아니라 원래 코드 위치로 에러를 볼 수 있다. (소스맵 자체는 공개 서버에 올리지 않는 것이 안전)
- **성능 모니터링** : 실제 사용자의 Core Web Vitals(LCP, INP, CLS) 수집 → Vercel Speed Insights, `web-vitals` 라이브러리
- **사용자 분석** : Google Analytics, 검색 노출 관리(Google Search Console, 네이버 서치어드바이저) → [웹 분석 도구](/frontend/deploy/02-domain)
- **가용성 모니터링** : 사이트가 다운되면 알림 (UptimeRobot, Better Stack 등)
- **로그** : 서버 함수·SSR 로그는 플랫폼 대시보드나 로그 수집 도구에서 확인

## 7. 배포 전 체크리스트

- [ ] `npm run build`가 로컬에서 에러 없이 성공하는가?
- [ ] 린트, 타입 체크, 테스트가 CI에서 통과하는가?
- [ ] 프로덕션 환경 변수를 모두 설정했는가? 비밀 값이 클라이언트에 노출되지 않는가?
- [ ] HTTPS가 적용되어 있는가? (대부분의 플랫폼이 무료 인증서 자동 발급)
- [ ] 커스텀 도메인과 DNS 설정이 완료되었는가?
- [ ] SPA라면 새로고침 시 404가 나지 않는가?
- [ ] `<title>`, `description`, Open Graph 이미지, `robots.txt`, `sitemap.xml`을 준비했는가?
- [ ] 파비콘과 404 페이지가 있는가?
- [ ] 보안 헤더(CSP, HSTS 등)를 설정했는가?
- [ ] 에러 추적과 분석 도구를 연결했는가?
- [ ] 문제가 생기면 어떻게 롤백할지 알고 있는가?
- [ ] 사용량 알림·지출 한도를 설정했는가?

# Front 로드맵

## 0. 한눈에 보기

| 단계 | 주제                          | 핵심 질문                                        |
| ---- | ----------------------------- | ------------------------------------------------ |
| 1    | 인터넷과 웹의 역사            | 프론트엔드는 왜 생겼나?                          |
| 2    | HTML, CSS                     | 문서 구조를 어떻게 짜고, 어떻게 꾸미나?          |
| 3    | JavaScript, TypeScript        | 화면을 어떻게 움직이고, 코드를 어떻게 안전하게 쓰나? |
| 4    | 브라우저 동작 원리            | 코드가 어떻게 화면이 되나?                       |
| 5    | 프레임워크와 렌더링 전략      | 화면을 어디서(서버/브라우저), 언제 만드나?       |
| 6    | 개발 도구                     | 협업하고 빌드하려면 무엇이 필요한가?             |
| 7    | 네트워크 통신                 | 브라우저와 서버는 어떻게 대화하나?               |
| 8    | API                           | 데이터를 어떤 약속으로 주고받나?                 |
| 9    | 상태 관리와 데이터 페칭       | 화면의 데이터를 어디에 두고 어떻게 동기화하나?   |
| 10   | 웹 성능                       | 사용자가 느끼는 속도를 어떻게 재고 줄이나?       |
| 11   | 웹 보안                       | 사용자와 서비스를 어떻게 지키나?                 |
| 12   | 웹 접근성                     | 누구나 쓸 수 있게 만들었나?                      |
| 13   | 테스트                        | 고쳐도 안 깨진다는 걸 어떻게 확신하나?           |
| 14   | 배포와 운영                   | 만든 걸 어떻게 사용자에게 안정적으로 전달하나?   |
| 15   | AI와 함께 개발하기            | 도구가 코드를 쓰는 시대에 무엇을 잘해야 하나?    |

공부 순서 팁

- **1~4 → 5 → 6** 까지가 "혼자 화면을 만들 수 있는" 최소 단계다.
- 7~9는 서버와 협업하기 시작하면 바로 필요하다.
- 10~14는 실무에서 "잘 만든다"의 기준이 되는 부분이라, 프로젝트를 하나 완성한 뒤 다시 보면 훨씬 잘 들어온다.
- 모든 걸 다 알고 시작할 필요는 없다. **작은 프로젝트를 만들면서 막히는 부분을 이 표에서 찾아 채우는 방식** 이 가장 효율적이다.

## 1. 네트워크와 인터넷

## 2. HTML, CSS

### 2.1 HTML

HTML은 **문서의 구조와 의미** 를 정의한다. 어떻게 보이는지는 CSS의 일이다.

- 일반 태그와 **시맨틱 태그**
  - `<div>`만으로도 화면은 만들 수 있지만, `<header>`, `<nav>`, `<main>`, `<article>`, `<button>`처럼 의미에 맞는 태그를 써야
  - 스크린 리더, 검색 엔진, AI 에이전트가 페이지를 제대로 이해한다. (→ 12장 접근성, SEO와 직결)
- `<form>`과 입력 요소 : `<input>`의 type, `<label>` 연결, 기본 유효성 검사(`required`, `pattern`)
- 메타 태그 : `<title>`, `description`, Open Graph(SNS 공유 미리보기), `viewport`(모바일 대응)
- 최근 HTML 기능 : `<dialog>`, Popover API(`popover` 속성), `<details>`/`<summary>` → JS 없이도 모달·토글 구현 가능
- `HTML 전처리기` : 변수, 반복문, 조건문 같은 문법을 HTML에 추가해 HTML로 변환하는 도구
  - e.g. Pug, Haml, Slim
  - 요즘은 JSX나 각 프레임워크의 템플릿 문법이 이 역할을 대신해서 **새로 배울 필요는 거의 없다.**

cf. [HTML 시작](/languages/html/HTML-Start), [WAI-ARIA](/languages/html/HTML-WAI-ARIA)

### 2.2 CSS

- **기본 개념**
  - 캐스케이딩 : 중요도(`!important`) → 명시도(선택자 우선순위) → 작성 순서로 최종 스타일 결정
  - 상속 : 글꼴, 색 같은 일부 속성은 부모에서 자식으로 상속됨
  - **박스 모델** : content → padding → border → margin, `box-sizing: border-box`
- **레이아웃**
  - `Flexbox` : 1차원(가로 또는 세로 한 줄) 정렬 → [Flexible Layout](/languages/css/07-Flexible-Layout)
  - `Grid` : 2차원(행과 열) 배치 → [Grid Layout](/languages/css/08-Grid-Layout)
  - `position`(relative, absolute, fixed, sticky)과 `z-index`
- **반응형 웹**
  - 미디어 쿼리 : 화면 크기에 따라 스타일 변경 → [MediaQuery](/languages/css/09-MediaQuery)
  - **컨테이너 쿼리** : 화면이 아니라 "부모 요소 크기"에 따라 스타일 변경 → 컴포넌트 단위 반응형에 적합
  - 상대 단위 : `rem`, `%`, `vw`/`vh`, `dvh`(모바일 주소창을 고려한 높이), `clamp()`
- **모던 CSS** (지금은 대부분 모든 주요 브라우저에서 사용 가능)
  - CSS 변수(Custom Properties) : `--main-color: blue;` → 다크 모드, 테마에 필수
  - 네이티브 중첩(nesting) : Sass 없이도 `.card { .title { } }` 형태 작성 가능
  - `:has()` : 자식 상태에 따라 부모 스타일 변경 ("부모 선택자")
  - `@layer` : 캐스케이드 우선순위를 레이어 단위로 관리
  - 애니메이션 : `transition`, `@keyframes`, View Transitions, 스크롤 기반 애니메이션
- `CSS 전처리기` : CSS에 변수, 중첩, 믹스인, 반복문 등을 추가해 CSS로 변환하는 도구
  - e.g. Sass(SCSS 문법) → [Sass 가이드라인](https://sass-guidelin.es/ko/), LESS
  - 변수와 중첩이 CSS 표준에 들어오면서 **새 프로젝트에서 전처리기를 쓰는 이유는 많이 줄었다.**
- `CSS 후처리기` : CSS 문법 그대로 쓰고, JS 플러그인으로 변환하는 도구
  - e.g. PostCSS : CSS를 추상 구문 트리(AST)로 바꾼 뒤 플러그인으로 변환 (e.g. Autoprefixer로 벤더 접두사 자동 추가)
  - cf. 추상 구문 트리 : 코드에서 계층 구조 정보를 추출해 트리 형태로 만든 것
- `CSS 방법론` : 도구 없이 이름 규칙으로 유지보수성을 높이는 방법
  - OOCSS : 구조와 외형의 분리, 컨테이너와 콘텐츠의 분리
  - SMACSS : 규칙을 Base, Layout, Module, State, Theme로 분류
  - BEM : 클래스 이름을 `Block__Element--Modifier`로 짓는 규칙 → [BEM](/languages/css/02-BEM-attribute)

## 3. JavaScript & TypeScript

### 3.1 JavaScript

프레임워크보다 **JS 자체를 먼저 탄탄히** 하는 게 결국 가장 빠른 길이다.
React에서 막히는 대부분은 사실 JS(클로저, 비동기, 참조) 문제다.

- **기본** : 변수(`let`, `const`), 자료형, 연산자, 조건문, 반복문, 함수
- **꼭 이해할 개념**
  - 스코프와 **클로저** → [메모리와 클로저](/languages/js/20-memory-clusure)
  - `this` 바인딩 → [This](/languages/js/13-This)
  - 원시값 vs 참조값 (불변성, 얕은 복사·깊은 복사) → React 상태 업데이트의 핵심
  - 프로토타입과 클래스 → [Class](/languages/js/16-Class)
  - **비동기** : 콜백 → `Promise` → `async/await` → [비동기](/languages/js/14-Asynchronous)
  - **이벤트 루프** : 콜 스택, 태스크 큐, 마이크로태스크 큐
  - 모듈 : CommonJS(`require`) vs ES Modules(`import`) → [모듈](/languages/js/19-module)
- **ES6+ 문법** : 구조 분해, 스프레드/나머지, 옵셔널 체이닝(`?.`), 널 병합(`??`), 배열 메서드(`map`, `filter`, `reduce`)
- **DOM API** : 요소 선택·생성·수정, 이벤트 위임, 이벤트 버블링·캡처링
- 트랜스파일러 : `Babel`은 최신 JS를 구형 브라우저용 JS로 바꿔 주는 도구
  - 요즘은 SWC, esbuild, Oxc 같은 Rust/Go 기반 도구가 이 역할을 대부분 대신한다.
  - cf. CoffeeScript, LiveScript는 사실상 쓰이지 않는다.

### 3.2 TypeScript

이제는 **선택이 아니라 기본값** 이다. 대부분의 채용 공고, 라이브러리, 프레임워크 템플릿이 TS를 전제로 한다.

- 기본 타입, `interface` vs `type`, 유니온·리터럴 타입
- **타입 좁히기(Narrowing)** : `typeof`, `in`, 판별 유니온(discriminated union)
- **제네릭** → [Generics](/languages/ts/08-Generics)
- 유틸리티 타입 : `Partial`, `Pick`, `Omit`, `Record` → [UtilityType](/languages/ts/09-UtilityType)
- `tsconfig.json`의 `strict` 옵션은 처음부터 켜는 것을 권장
- 런타임 검증 : TS 타입은 실행 시점에 사라지므로, 외부 데이터(API 응답, 폼 입력)는 **Zod** 같은 스키마 라이브러리로 검증
- 2026년 현재
  - TypeScript 7 : 컴파일러가 Go로 재작성되어 약 10배 빨라짐
  - Node.js는 `.ts` 파일의 타입을 지우고 바로 실행하는 기능(type stripping)을 지원

## 4. 브라우저 동작 원리

"코드가 화면이 되는 과정"을 알면 성능 최적화와 디버깅이 훨씬 쉬워진다.

### 4.1 URL을 입력하면 일어나는 일

1. **DNS 조회** : 도메인(`example.com`)을 IP 주소로 변환
2. **연결 수립** : TCP 3-way handshake + TLS handshake (HTTP/3라면 QUIC으로 한 번에)
3. **HTTP 요청/응답** : 서버가 HTML을 응답
4. **파싱과 렌더링** : 브라우저가 HTML을 읽으며 CSS, JS, 이미지 등을 추가로 요청
5. **화면 표시** 후, JS가 실행되며 상호작용이 가능해짐

### 4.2 렌더링 파이프라인

1. **Parse** : HTML → `DOM 트리`, CSS → `CSSOM 트리`
2. **Style** : DOM과 CSSOM을 합쳐 각 요소의 최종 스타일 계산 (`Render 트리`)
3. **Layout(Reflow)** : 각 요소의 위치와 크기 계산
4. **Paint** : 픽셀로 그리기 (색, 글자, 그림자 등)
5. **Composite** : 여러 레이어를 합쳐 최종 화면 출력

알아 둘 점

- `width`, `top` 같은 속성을 바꾸면 Layout부터 다시 → 비쌈
- `color`, `background`를 바꾸면 Paint부터 다시
- `transform`, `opacity`는 Composite만 다시 → **애니메이션은 이 둘로 하는 게 가장 부드럽다**
- `<script>`는 기본적으로 HTML 파싱을 멈춤 → `defer`, `async`, `type="module"`로 해결

### 4.3 브라우저의 구성

- 렌더링 엔진 : Blink(Chrome, Edge), WebKit(Safari), Gecko(Firefox)
- JS 엔진 : V8(Chrome, Node.js), JavaScriptCore(Safari), SpiderMonkey(Firefox)
- 브라우저의 JS는 **싱글 스레드** 라서, 무거운 작업이 메인 스레드를 오래 잡으면 클릭·스크롤이 멈춘다. → Web Worker로 분리

cf. [브라우저 동작 원리](/cs/terms-principles/brower)

## 5. 프레임워크와 렌더링 전략

### 5.1 왜 프레임워크를 쓰나?

- 순수 JS로 DOM을 직접 조작하면, 데이터가 바뀔 때마다 **어떤 DOM을 고칠지 개발자가 다 추적** 해야 한다.
- 프레임워크는 "데이터(상태)가 이렇다면 화면은 이렇다"만 선언하면, 바뀐 부분만 알아서 갱신해 준다. (**선언적 UI**)
- 그리고 컴포넌트 단위로 화면을 쪼개 재사용할 수 있다.

### 5.2 주요 라이브러리/프레임워크

| 이름    | 특징                                                                 |
| ------- | -------------------------------------------------------------------- |
| React   | 가장 큰 생태계, 채용 시장 1위. React 19 + React Compiler            |
| Vue     | 배우기 쉬운 템플릿 문법, 국내외 꾸준한 수요                         |
| Angular | 라우팅·폼·DI까지 포함한 풀 프레임워크, 대규모 기업 프로젝트에서 사용 |
| Svelte  | 컴파일러 기반, 런타임이 가벼움 (Svelte 5 Runes)                      |
| Solid   | Signals 기반의 세밀한 반응성                                         |

처음이라면 **React 하나를 깊게** 배우는 것을 권장한다. 개념(컴포넌트, 상태, 단방향 데이터 흐름)은 다른 프레임워크에도 그대로 통한다.

cf. 공식문서 : [React](https://react.dev/), [Vue](https://vuejs.org/), [Angular](https://angular.dev/), [Svelte](https://svelte.dev/)

### 5.3 렌더링 전략

| 전략 | 화면을 만드는 곳·시점           | 장점                    | 단점                       |
| ---- | ------------------------------- | ----------------------- | -------------------------- |
| CSR  | 브라우저, 요청 후               | 페이지 전환이 빠름      | 첫 화면이 느림, SEO 불리   |
| SSR  | 서버, 요청할 때마다             | 첫 화면 빠름, SEO 유리  | 서버 부하                  |
| SSG  | 서버, 빌드할 때 한 번           | 가장 빠름, CDN 캐싱     | 자주 바뀌는 데이터에 부적합 |
| ISR  | SSG + 일정 주기마다 재생성      | SSG 속도 + 최신성       | 캐시 무효화 이해 필요      |
| RSC  | 컴포넌트 단위로 서버/클라이언트 분리 | JS 번들 감소, 서버 데이터 직접 접근 | 개념 복잡도, 서버 보안 고려 |

- **하이드레이션(Hydration)** : 서버가 만든 HTML에 브라우저가 JS 이벤트를 연결해 "살아 있게" 만드는 과정
- 지금은 한 페이지 안에서도 정적인 부분, 서버에서 그리는 부분, 브라우저에서 동작하는 부분을 **섞어서** 쓴다.

## 7. 네트워크 통신

- OSI 7계층, TCP/IP 4계층 → [네트워크](/cs/network/01-intro)
- TCP/IP 4계층 : `네트워크 접근 계층` → `인터넷 계층` → `전송 계층` → `응용 계층`

주요 프로토콜

- `이더넷` : 같은 네트워크(LAN) 안에서 데이터를 전송하는 표준 (`TCP/IP 1계층, 네트워크 접근 계층`)
  - `MAC 주소` : 물리적으로 연결된 장치끼리 통신할 때 쓰는 하드웨어 주소 (1계층)
- `IP` : 데이터를 패킷 단위로 나눠 최종 목적지(IP 주소)까지 전달 (`TCP/IP 2계층, 인터넷 계층`)
  - `IP 주소` : 최종 목적지를 나타내는 주소
- `TCP` : 연결형, 신뢰성 보장 (순서 보장, 재전송, 흐름·혼잡 제어) (`TCP/IP 3계층, 전송 계층`)
  - `3-way Handshake` : 연결 수립 (SYN → SYN+ACK → ACK)
  - `4-way Handshake` : 연결 종료 (FIN → ACK → FIN → ACK)
- `UDP` : 비연결형, 연결 설정 없이 바로 전송 (`TCP/IP 3계층, 전송 계층`)
  - TCP보다 빠르지만 흐름·혼잡 제어가 없어 신뢰성을 보장하지 않음
  - 속도가 중요한 인터넷 전화, 스트리밍, 온라인 게임 등에 사용
- `QUIC` : 구글이 2012년에 개발하고 2021년 IETF 표준(RFC 9000)이 된 프로토콜
  - UDP 위에서 TCP의 신뢰성 + TLS 암호화를 함께 구현 → 연결 수립이 빠르고, 패킷 하나가 늦어도 다른 요청이 막히지 않음
- `HTTP` : 웹에서 데이터를 주고받는 프로토콜 (`TCP/IP 4계층, 응용 계층`)
  - `클라이언트-서버 구조` : 클라이언트가 요청하고, 서버가 응답
  - `비연결성` : 요청-응답이 끝나면 연결을 끊는 것이 원래 설계
    - 단, HTTP/1.1부터는 Keep-Alive로 연결을 재사용하는 것이 기본
  - `무상태(stateless)` : 서버가 이전 요청을 기억하지 않음
    - 장점 : 서버를 늘리기(확장) 쉬움
    - 그래서 로그인 상태 유지에는 쿠키, 세션, 토큰이 필요 (→ 7.6, 7.7)

### 7.1 HTTP 메시지

- `HTTP 메시지` : 요청·응답 시 주고받는 **데이터 형식**
  - `요청 메시지` : 클라이언트 → 서버
  - `응답 메시지` : 서버 → 클라이언트
- 두 메시지 모두 시작행, 헤더, 공백행, 본문으로 구성
  - `시작행` : 요청이면 메서드·URL·버전, 응답이면 버전·상태 코드·상태 메시지
  - `헤더` : 부가 정보
  - `공백행` : 헤더의 끝 표시
  - `본문` : 실제 데이터 (조회·삭제 요청은 보통 생략)

```tex
/** 요청 메시지 시작행 구성
 * GET         ---> HTTP 메서드
 * /index.html ---> 요청 URL
 * HTTP/1.1    ---> HTTP 버전
 */

(시작행)   GET /index.html HTTP/1.1

(헤더)     Accept: text/html,application/xhtml+xml

(공백행)

(본문)     (단순 조회-삭제 요청인 경우 생략 가능)
```

```tex
/** 응답 메시지 시작행 구성
 * HTTP/1.1        ---> HTTP 버전
 * 304             ---> 상태 코드
 * Not Modified    ---> 상태 메시지
 */

(시작행)   HTTP/1.1 304 Not Modified

(헤더)     Vary: Origin
          Access-Control-Allow-Credentials: true
          ~~~~

(공백행)

(본문)     (단순 조회-삭제 요청인 경우 생략 가능)
```

- 헤더는 브라우저가 기본 정보를 자동으로 넣고, 개발자가 직접 추가할 수도 있다.
- 개발자 도구 **Network 탭** 에서 요청을 클릭하면 헤더를 볼 수 있다.
  - `General` : 요청 URL, 메서드, 상태 코드 등
  - `Response Headers` : `Set-Cookie`, `Cache-Control`, `Content-Type`, `Location` 등
  - `Request Headers` : `Host`, `User-Agent`, `Accept`, `Cookie`, `Authorization` 등

---

### 7.2 HTTP 메서드

| 메서드  | 설명                                                    |
| ------- | ------------------------------------------------------- |
| GET     | 데이터 조회                                             |
| POST    | 데이터 등록                                             |
| PUT     | 데이터 전체 수정 (없으면 생성)                          |
| PATCH   | 데이터 일부 수정                                        |
| DELETE  | 데이터 삭제                                             |
| OPTIONS | 서버가 지원하는 메서드 확인 (CORS Preflight에 사용)     |
| HEAD    | GET과 같지만 본문 없이 시작행과 헤더만 응답             |
| TRACE   | 루프백 테스트 (보안상 대부분의 서버에서 비활성화)       |
| CONNECT | 프록시를 통해 터널을 열 때 사용 (e.g. HTTPS 프록시)     |

- `안전성(safe)` : 요청이 **서버의 상태를 바꾸지 않음** (e.g. GET, HEAD, OPTIONS, TRACE)
- `멱등성(idempotent)` : 같은 요청을 여러 번 보내도 **서버 상태가 같음** (e.g. GET, PUT, DELETE, HEAD, OPTIONS)
  - POST는 멱등하지 않다 → 결제 버튼 중복 클릭 시 중복 결제가 될 수 있음 → 버튼 비활성화, 멱등 키(Idempotency-Key) 등으로 방지

### 7.3 HTTP 상태 코드

| 그룹 | 의미                 | 자주 보는 코드                                                       |
| ---- | -------------------- | -------------------------------------------------------------------- |
| 1xx  | 정보 응답            | 101 Switching Protocols (웹소켓 전환)                                |
| 2xx  | 성공                 | 200 OK, 201 Created, 204 No Content                                  |
| 3xx  | 리다이렉션           | 301 영구 이동, 302/307 임시 이동, 304 Not Modified(캐시 그대로 사용) |
| 4xx  | 클라이언트 오류      | 400 잘못된 요청, 401 인증 필요, 403 권한 없음, 404 없음, 429 요청 과다 |
| 5xx  | 서버 오류            | 500 서버 내부 오류, 502 Bad Gateway, 503 서비스 불가                 |

- `401`은 "누구인지 모름(로그인 필요)", `403`은 "누구인지는 알지만 권한 없음"으로 구분해서 처리하자.

### 7.4 HTTP 버전별 특징

- `HTTP/0.9` : 최초 버전, GET만 지원, HTML만 전달
- `HTTP/1.0` : POST, HEAD 추가, 헤더 도입, 이미지·영상 등 다양한 형식 전송
- `HTTP/1.1` : 연결 재사용(Keep-Alive), PUT·DELETE·OPTIONS 등 추가, 지금도 널리 사용
  - 한 연결에서 요청을 순서대로만 처리해서, 앞 요청이 늦으면 뒤도 막히는 문제(HOL Blocking)
- `HTTP/2` : 하나의 연결에서 여러 요청을 **병렬(멀티플렉싱)** 처리, 헤더 압축
- `HTTP/3` : TCP 대신 **QUIC(UDP 기반)** 사용, 연결이 빠르고 모바일 네트워크 전환에 강함
  - 주요 브라우저와 CDN이 모두 지원하며, 상당한 비율의 웹 트래픽이 이미 HTTP/3로 오간다.

### 7.5 HTTPS 보안 프로토콜

- `HTTP` : 기본 포트 80, 데이터를 평문으로 전송
- `HTTPS` : HTTP + `TLS` 암호화, 기본 포트 443
  - 예전 이름인 `SSL`이 남아서 `SSL/TLS`라고도 부르지만, 현재는 TLS 1.2·1.3을 사용
  - 기능 : **암호화**(엿보기 방지), **무결성**(변조 방지), **인증**(인증서로 진짜 서버인지 확인)
  - `구조` : 네트워크 접근 계층 → 인터넷 계층(IP) → 전송 계층(TCP 또는 QUIC) → `TLS` → 응용 계층(HTTP)
- 지금은 HTTPS가 기본이다. 브라우저는 HTTP 사이트를 "안전하지 않음"으로 표시하고, Service Worker·카메라 접근 같은 기능은 HTTPS에서만 동작한다.

### 7.6 쿠키

#### 7.6.1 쿠키

`쿠키(cookie)` : 서버가 만들어 브라우저에 저장시키는 작은 데이터 (클라이언트를 기억하고 구분하는 용도)

- `쿠키 전달 과정`
  1. 서버가 응답 헤더에 `Set-Cookie`를 담아 보냄
  2. 브라우저는 쿠키를 저장
  3. 이후 같은 도메인으로 요청할 때마다 `Cookie` 헤더에 자동으로 담아 보냄
  4. 서버는 쿠키를 보고 클라이언트를 식별
- 쿠키는 도메인별로 관리된다. (e.g. naver.com에서 받은 쿠키는 naver.com 요청에만 붙음)

서버에서 쿠키를 설정하는 코드 (Express)

```js
app.get('/', (req, res) => {
  res.setHeader('Set-Cookie', 'username=berenickt; HttpOnly; Secure; SameSite=Lax')
  res.sendFile(`${__dirname}/index.html`)
})
```

이후 브라우저가 보내는 모든 요청에는 다음 헤더가 붙는다.

```http
GET /test.html HTTP/1.1
Host: www.test.org
Cookie: username=berenickt
```

---

#### 7.6.2 쿠키 속성

- `만료(Expires, Max-Age)`
  - 둘 다 없으면 **세션 쿠키** → 브라우저를 닫으면 삭제
  - 지정하면 **영속 쿠키** → 해당 시점까지 유지
  - e.g. `Expires=Wed, 03 Sep 2025 09:00:00 GMT`, `Max-Age=3600`
- `범위(Domain, Path)`
  - `Domain=test.com` : test.com과 서브 도메인에서 사용
  - `Path=/mypage` : /mypage와 하위 경로에서 사용
- `Secure` : HTTPS 요청에만 쿠키 전송
- `HttpOnly` : JS(`document.cookie`)로 쿠키 접근 불가 → XSS로 쿠키를 훔치는 것을 막음
- `SameSite` : 다른 사이트에서 시작된 요청에 쿠키를 보낼지 결정 → CSRF 방어
  - `Strict` : 다른 사이트에서 온 요청에는 절대 전송하지 않음
  - `Lax` : 다른 사이트에서 링크를 눌러 **최상위 페이지로 이동하는 GET 요청** 에만 전송 (대부분 브라우저의 기본값)
  - `None` : 항상 전송, 반드시 `Secure`와 함께 써야 함 (서드파티 쿠키, 외부 위젯 등 꼭 필요할 때만)

cf. [MDN - HTTP 쿠키](https://developer.mozilla.org/ko/docs/Web/HTTP/Cookies)

### 7.7 세션과 토큰

`세션(session)` : 사용자 상태를 **서버** 에 저장하고, 클라이언트에는 식별자(세션 ID)만 주는 방식

- 과정
  1. 로그인하면 서버가 세션 저장소에 사용자 정보를 저장하고, 세션 ID를 `Set-Cookie`로 전달
  2. 브라우저는 이후 요청마다 세션 ID 쿠키를 보냄
  3. 서버는 세션 ID로 저장소를 조회해 사용자 확인
- 장점 : 서버에서 언제든 강제 로그아웃 가능 / 단점 : 서버에 저장 공간이 필요하고, 서버가 여러 대면 세션 공유 필요

`토큰(JWT)` : 사용자 정보를 서명된 토큰에 담아 **클라이언트** 가 들고 다니는 방식

- 서버는 저장 없이 서명만 검증 → 확장이 쉬움
- 단점 : 발급한 토큰을 중간에 무효화하기 어려움 → 짧은 만료의 Access Token + Refresh Token 조합
- 토큰을 `localStorage`에 두면 XSS에 취약하므로, **HttpOnly 쿠키에 저장** 하는 방식이 권장된다.

cf. [로그인 구현](/backend/login)

### 7.8 실시간 통신 (웹소켓, SSE)

HTTP는 **클라이언트가 요청해야만** 서버가 응답할 수 있어서, 채팅처럼 서버가 먼저 데이터를 보내야 하는 서비스에 불리하다.

| 방식          | 방향              | 특징                                                    | 예시                      |
| ------------- | ----------------- | ------------------------------------------------------- | ------------------------- |
| 폴링          | 클라이언트 → 서버 | 일정 주기로 계속 요청. 간단하지만 낭비가 큼             | 주기적 새로고침           |
| SSE           | 서버 → 클라이언트 | HTTP 연결을 유지하며 서버가 계속 이벤트 전송            | 알림, **AI 채팅 응답 스트리밍** |
| 웹소켓        | 양방향            | 한 번 연결하면 양쪽 모두 자유롭게 전송                  | 채팅, 실시간 협업, 게임   |

`웹소켓 연결 과정`

- 처음에는 HTTP로 요청하며, 헤더에 `Upgrade: websocket`을 보냄
- 서버가 지원하면 `101 Switching Protocols`로 응답
- 이후 같은 연결로 양방향 데이터 전송

cf. [MDN - WebSocket API](https://developer.mozilla.org/ko/docs/Web/API/WebSockets_API), [MDN - Server-Sent Events](https://developer.mozilla.org/ko/docs/Web/API/Server-sent_events)

---

### 7.9 CORS

프론트엔드 개발자가 가장 많이 만나는 에러 중 하나다.

- `동일 출처 정책(SOP)` : 브라우저는 기본적으로 **다른 출처(origin)** 의 응답을 JS가 읽지 못하게 막는다.
  - 출처 = `프로토콜 + 도메인 + 포트` (e.g. `http://localhost:3000`과 `http://localhost:8080`은 다른 출처)
- `CORS(Cross-Origin Resource Sharing)` : 서버가 "이 출처는 허용한다"고 응답 헤더로 알려 주면 브라우저가 허용하는 방식
  - `Access-Control-Allow-Origin: https://my-site.com`
- `Preflight` : 커스텀 헤더나 PUT·DELETE 등의 요청 전에 브라우저가 `OPTIONS`로 먼저 허용 여부를 물어봄
- 해결 방법
  - **서버에서** 허용 출처를 설정하는 것이 정석 (CORS는 브라우저가 막는 것이지, 서버 문제가 아니다)
  - 개발 중에는 Vite 등의 개발 서버 프록시로 같은 출처처럼 우회
  - Next.js라면 서버(Route Handler, 서버 컴포넌트)에서 대신 호출하면 브라우저 CORS를 피할 수 있다.

## 8. API

- `API(Application Programming Interface)` : 프로그램끼리 기능을 주고받기 위한 약속(인터페이스)
- `인터페이스` : 서로 다른 시스템이 소통할 수 있도록 정한 상호작용 방식

### 8.1 브라우저 API

브라우저가 JS에 제공하는 API 집합이다.

- `DOM API` : 요소 선택·탐색, 생성·조작, 이벤트 처리
- `Fetch API` : 네트워크 요청 (8.3 참고)
- `Storage API` : 브라우저에 데이터 저장
  - `웹 스토리지` : 키-값 문자열 저장
    - `localStorage` : 브라우저를 닫아도 유지
    - `sessionStorage` : 탭을 닫으면 삭제
  - `IndexedDB` : 객체를 저장하는 브라우저 내장 NoSQL DB, 대용량·오프라인 데이터에 사용
- `Geolocation API` : 사용자 위치 정보
- `History API` : 새로고침 없이 URL 변경 (SPA 라우터의 기반)
- `Intersection Observer` : 요소가 화면에 보이는지 감지 (무한 스크롤, 이미지 지연 로딩)
- `Web Worker` : 무거운 계산을 별도 스레드에서 실행
- `Service Worker` : 네트워크 요청을 가로채 캐싱 → 오프라인 지원, 푸시 알림 (PWA의 핵심)

---

### 8.2 API 디자인 패턴

#### 8.2.1 SOAP

`SOAP(Simple Object Access Protocol)` : XML 기반의 엄격한 메시지 규약

- WS-Security 같은 표준 보안 기능 지원
- 작은 데이터도 XML 구조 때문에 장황함 → 지금은 금융·공공 등 레거시 시스템 위주

#### 8.2.2 REST

`REST(Representational State Transfer)` : **자원(URL) + 행위(HTTP 메서드) + 표현(JSON 등)** 으로 API를 설계하는 방식

- e.g. `GET /users/1`, `POST /users`, `DELETE /users/1`
- 단점
  - `언더페칭` : 한 화면에 필요한 데이터를 얻으려면 여러 API를 호출해야 함
  - `오버페칭` : 필요 없는 필드까지 함께 받아 대역폭 낭비
- **OpenAPI(Swagger)** 로 명세를 작성하면, 문서와 TS 타입·API 클라이언트를 자동 생성할 수 있다.

#### 8.2.3 GraphQL

`GraphQL` : 클라이언트가 **필요한 필드만 골라서** 요청하는 쿼리 언어이자 런타임

- 언더페칭·오버페칭 해결, 스키마 기반으로 타입 안정성 확보
- 대신 캐싱이 어렵고, 서버 구현 복잡도가 올라감
- cf. [Apollo Client](/frontend/apollo-client/apollo)

#### 8.2.4 RPC 계열

- `tRPC` : 서버 함수의 TS 타입을 클라이언트가 그대로 공유 (풀스택 TS 프로젝트에서 인기)
- `gRPC` : 주로 서버 간 통신에 사용
- Next.js의 **Server Actions** 도 "서버 함수를 직접 호출"한다는 점에서 RPC에 가까운 방식이다.

---

### 8.3 API 호출 방법

- `동기 호출` : 결과가 올 때까지 다음 코드가 기다림
- `비동기 호출` : 요청을 보내 두고 다른 일을 하다가, 결과가 오면 처리
  - 2005년 제시 제임스 개럿이 이 방식을 `Ajax`라고 명명
- 구현 방법
  - `XMLHttpRequest` : 브라우저 내장 객체 (`open()`, `send()`, `abort()`, `onreadystatechange`)
  - `jQuery.ajax()` : XHR을 쓰기 쉽게 감싼 함수
  - `Axios` : Promise 기반 HTTP 클라이언트, 인터셉터·자동 JSON 변환 제공
  - `Fetch API` : 브라우저 표준, Promise 기반 ✅ 지금의 기본값
    - 주의 : `fetch`는 **404, 500 응답에도 reject하지 않는다.** `response.ok`를 직접 확인해야 한다.
    - 요청 취소는 `AbortController`
    - Node.js 18+에도 내장되어 서버/클라이언트 모두 같은 코드 사용 가능

```ts
const res = await fetch('/api/users')
if (!res.ok) throw new Error(`요청 실패: ${res.status}`)
const users = await res.json()
```

cf. [API 호출](/languages/js/15-callAPI)

---

### 8.4 데이터 교환 형식

- `JSON` : 키-값 구조, 가장 많이 사용 ✅
- `XML` : 태그 구조, SOAP·RSS 등에서 사용
- `CSV` : 쉼표로 구분된 표 데이터
- `FormData` : 파일 업로드 시 사용 (`multipart/form-data`)

### 8.5 API 테스트·문서 도구

- `Postman`, `Insomnia`, `Bruno` : API 요청을 보내 보고 저장
- `Swagger UI` : OpenAPI 명세를 문서 화면으로 보여 줌
- `MSW(Mock Service Worker)` : 백엔드 API가 아직 없을 때, 브라우저에서 요청을 가로채 가짜 응답을 줌 → 프론트엔드 단독 개발과 테스트에 유용

## 9. 상태 관리와 데이터 페칭

**상태(state)** = 화면을 그리기 위해 기억해야 하는 데이터. 어디에 두느냐가 설계의 핵심이다.

| 종류            | 예시                                   | 도구                                   |
| --------------- | -------------------------------------- | -------------------------------------- |
| 지역 상태       | 입력값, 모달 열림 여부                 | `useState`, `useReducer`               |
| 전역 클라이언트 상태 | 로그인 사용자 정보, 테마, 장바구니  | Zustand, Jotai, Redux Toolkit, Context |
| 서버 상태       | 게시글 목록, 상품 상세                 | TanStack Query, SWR, 서버 컴포넌트     |
| URL 상태        | 검색어, 필터, 페이지 번호              | 검색 파라미터(`?q=react&page=2`)       |
| 폼 상태         | 회원가입 폼, 유효성 검사               | React Hook Form + Zod, `useActionState` |

원칙

1. **가능한 한 가까운 곳에** 둔다. (전역부터 만들지 않는다)
2. 서버 데이터는 전역 스토어에 복사하지 말고, **서버 상태 도구** 나 서버 컴포넌트로 다룬다.
3. 공유·북마크가 필요한 상태(필터, 탭)는 **URL** 에 둔다.

cf. [상태 관리 라이브러리](/frontend/state-management), [Data Fetching 라이브러리](/frontend/data-fetching), [TanStack Query](/frontend/tanstack-query/00-summary)

## 10. 웹 성능

### 10.1 Core Web Vitals

구글이 정한 **사용자 체감 성능 지표** 이며, 검색 순위에도 반영된다.

| 지표 | 의미                                            | 좋음 기준   |
| ---- | ----------------------------------------------- | ----------- |
| LCP (Largest Contentful Paint) | 가장 큰 콘텐츠가 보이기까지 걸린 시간 (로딩) | 2.5초 이하  |
| INP (Interaction to Next Paint) | 클릭·입력 후 화면이 반응하기까지 걸린 시간 (반응성) | 200ms 이하 |
| CLS (Cumulative Layout Shift) | 로딩 중 레이아웃이 갑자기 밀리는 정도 (안정성) | 0.1 이하   |

- 2024년 3월부터 반응성 지표가 FID에서 **INP** 로 바뀌었다.
- 측정 도구 : Lighthouse, PageSpeed Insights, 개발자 도구 Performance 탭, 실제 사용자 데이터(RUM, `web-vitals` 라이브러리)

### 10.2 대표적인 최적화 방법

- **로딩 (LCP)**
  - 이미지 최적화 : WebP/AVIF, 적절한 크기(`srcset`), 지연 로딩(`loading="lazy"`), 중요한 이미지는 `fetchpriority="high"`
  - 코드 분할 : 페이지·컴포넌트 단위로 JS를 나눠 필요할 때 로드 (`import()`, `React.lazy`)
  - 서버 렌더링, CDN 캐싱, 폰트 최적화(`font-display: swap`, 서브셋)
- **반응성 (INP)**
  - 메인 스레드를 오래 막는 긴 작업(Long Task) 쪼개기
  - 불필요한 리렌더링 줄이기 (React Compiler가 상당 부분 자동 처리)
  - 무거운 계산은 Web Worker로
- **안정성 (CLS)**
  - 이미지·광고·임베드에 크기(`width`, `height`, `aspect-ratio`) 지정
  - 콘텐츠 위에 갑자기 끼어드는 배너 피하기
- **번들 크기** : 번들 분석기로 큰 라이브러리 찾기, 트리 셰이킹, 같은 기능의 가벼운 대안 또는 브라우저 기본 기능 사용

cf. [Next.js 최적화](/frontend/nextjs/06-optimizing)

## 11. 웹 보안

프론트엔드도 보안의 최전선이다. 특히 서버 컴포넌트·Server Actions처럼 서버 코드를 함께 다루면서 책임 범위가 넓어졌다.

- **XSS (Cross-Site Scripting)** : 사용자 입력에 악성 스크립트를 섞어 다른 사용자 브라우저에서 실행
  - React는 기본적으로 문자열을 이스케이프하지만, `dangerouslySetInnerHTML`, `href="javascript:..."`는 위험
  - HTML을 꼭 넣어야 하면 DOMPurify 같은 도구로 정화(sanitize)
- **CSRF (Cross-Site Request Forgery)** : 로그인된 사용자의 쿠키를 이용해 다른 사이트에서 요청을 위조
  - 방어 : `SameSite` 쿠키, CSRF 토큰, 상태 변경은 GET이 아닌 POST 등으로
- **CSP (Content Security Policy)** : 허용된 출처의 스크립트만 실행하도록 응답 헤더로 제한 → XSS 피해를 크게 줄임
- **CORS** : 7.9 참고. `Access-Control-Allow-Origin: *`를 인증이 필요한 API에 쓰지 말 것
- **민감 정보 노출**
  - 프론트엔드 코드는 **누구나 볼 수 있다.** API 키, 비밀 값을 클라이언트 번들에 넣지 말 것
  - Next.js에서 `NEXT_PUBLIC_` 접두사가 붙은 환경 변수는 브라우저에 그대로 노출된다.
  - 서버 함수(Server Actions, API Route)도 외부에서 직접 호출될 수 있으므로 **항상 인증·권한·입력값 검증**
- **의존성(공급망) 보안**
  - npm 패키지가 탈취되어 악성 코드가 배포되는 사고가 반복되고 있다.
  - lock 파일 커밋, `npm audit`/Dependabot, 불필요한 패키지 줄이기, 보안 패치 빠르게 적용하기
  - e.g. 2025년 12월 React 서버 컴포넌트 RCE 취약점(CVE-2025-55182) → 패치 버전으로 즉시 업데이트가 필요했다.

## 12. 웹 접근성

장애가 있는 사용자, 키보드만 쓰는 사용자, 고령자, 느린 네트워크 사용자까지 **누구나 쓸 수 있게** 만드는 것이다.
국내외 법적 의무가 있는 경우도 많고, 접근성이 좋은 페이지는 SEO와 AI 에이전트 이해도도 좋다.

- 기준 : **WCAG 2.2** (국내는 이를 바탕으로 한 KWCAG)
- 실천 체크리스트
  - 시맨틱 HTML 사용 : 클릭되는 건 `<div onClick>`이 아니라 `<button>`
  - 이미지에 의미 있는 `alt` (장식용이면 `alt=""`)
  - 입력 요소에 `<label>` 연결
  - **키보드만으로** 모든 기능 사용 가능 + 포커스가 눈에 보이게
  - 글자와 배경의 명도 대비 4.5:1 이상
  - 색만으로 정보를 전달하지 않기 (e.g. 에러를 빨간색으로만 표시하지 않기)
  - 모달을 열면 포커스를 모달 안에 가두고, 닫으면 원래 위치로 되돌리기
- `WAI-ARIA` : HTML만으로 의미를 표현하기 어려울 때 역할·상태를 추가하는 속성
  - **첫 번째 규칙 : 네이티브 HTML로 되면 ARIA를 쓰지 않는다.** 잘못된 ARIA는 없는 것보다 나쁘다.
- 도구 : axe DevTools, Lighthouse 접근성 점수, 스크린 리더(VoiceOver, NVDA)로 직접 써 보기

cf. [WAI-ARIA](/languages/html/HTML-WAI-ARIA)

## 13. 테스트

### 13.1 테스트 유형

- `유닛 테스트` : 함수·훅 같은 가장 작은 단위를 독립적으로 검증
- `통합 테스트` : 여러 컴포넌트·모듈을 합쳐서 사용자 관점으로 검증 (프론트엔드에서 가장 가성비가 좋음)
- `E2E 테스트` : 실제 브라우저에서 사용자 시나리오를 처음부터 끝까지 실행
- `시각적 회귀 테스트` : 스크린샷을 비교해 의도치 않은 UI 변경 감지
- `접근성 테스트` : 장애가 있는 사용자도 문제없이 쓸 수 있는지 검증
- `성능 테스트` : 로딩·반응 속도가 기준을 만족하는지 검증

> 테스트 트로피(Testing Trophy) : 정적 분석(TS, ESLint)을 바닥에 깔고, **통합 테스트에 가장 많이 투자** 하자는 프론트엔드 테스트 전략

---

### 13.2 테스트 도구

#### 13.2.1 수동 테스트 도구 : 브라우저 개발자 도구

- `Elements` : DOM과 스타일 확인·수정
- `Console` : 로그 확인, JS 실행
- `Network` : 모든 HTTP 요청·응답, 느린 네트워크 시뮬레이션
- `Sources` : 소스 확인, 중단점(breakpoint) 디버깅
- `Performance` : 렌더링·스크립트 실행 시간 분석, Core Web Vitals 확인
- `Memory` : 메모리 누수 탐지
- `Application` : 쿠키, 스토리지, 캐시, Service Worker 확인
- `Lighthouse` : 성능, 접근성, 모범 사례, SEO 검사 보고서
- React DevTools, TanStack Query DevTools 같은 라이브러리 전용 확장 도구도 함께 쓰자.

## 14. 배포와 운영

### 14.1 배포 플랫폼

| 플랫폼             | 특징                                                  |
| ------------------ | ----------------------------------------------------- |
| Vercel             | Next.js 제작사, Git 푸시만으로 배포, 미리보기 URL 제공 |
| Netlify            | 정적 사이트·Jamstack에 강함                           |
| Cloudflare Pages/Workers | 전 세계 엣지에서 실행, 저렴한 비용             |
| GitHub Pages       | 정적 사이트 무료 호스팅                               |
| AWS (S3 + CloudFront, Amplify) | 세밀한 제어, 기업 환경                    |
| Docker + 서버      | 직접 운영, 자유도 높음 (Node 서버로 SSR 실행)        |

### 14.2 알아야 할 개념

- **CI/CD** : 푸시하면 자동으로 린트·테스트·빌드·배포 (e.g. GitHub Actions) → [CI/CD](/cs/terms-principles/ci-cd)
- **CDN** : 전 세계 서버에 정적 파일을 복사해, 사용자와 가까운 곳에서 응답
- **캐싱 전략** : `Cache-Control` 헤더, 파일명에 해시(`app.3f9a1c.js`)를 붙여 변경 시에만 새로 받기
- **환경 변수** : 개발·스테이징·운영 환경별 설정 분리, 비밀 값은 서버에만
- **도메인과 DNS, HTTPS 인증서** → [도메인](/frontend/deploy/02-domain)
- **모니터링** : 에러 추적(Sentry), 실제 사용자 성능(RUM), 로그
- **롤백** : 배포 후 문제가 생기면 이전 버전으로 즉시 되돌릴 수 있어야 한다.

cf. [배포](/frontend/deploy/01-deploy), [Next.js 배포](/frontend/nextjs/10-deploying)

## 15. AI와 함께 개발하기

2026년 지금, AI 코딩 도구는 프론트엔드 개발의 일상이 되었다.

- **도구**
  - 에디터 통합 : Cursor, GitHub Copilot
  - 에이전트형 : Claude Code 등 → 여러 파일을 읽고 수정하고, 테스트까지 실행
  - UI 생성 : v0, Figma의 AI 기능 → 디자인·설명에서 컴포넌트 초안 생성
  - MCP(Model Context Protocol) : AI가 Figma, 브라우저, 이슈 트래커 등에 직접 연결되는 표준
- **잘 쓰는 법**
  - 요구사항과 제약(사용 스택, 디자인 시스템, 접근성 기준)을 **글로 명확히** 전달
  - 생성된 코드는 반드시 읽고 이해한 뒤 반영 (특히 보안·접근성·성능)
  - 테스트와 타입이 잘 갖춰진 프로젝트일수록 AI가 만든 변경을 안전하게 검증할 수 있다.
- **그래서 무엇을 공부해야 하나?**
  - 코드 작성 속도의 차이는 줄어든다. 대신 **기본기(1~14장)로 결과물을 판단하는 능력** 의 가치가 커진다.
  - 문제를 정의하고, 설계하고, 사람들과 소통하는 능력이 더 중요해진다.

cf. [프론트엔드 역사와 미래 - 6.5 AI와 함께 일하는 프론트엔드](/frontend/front-architecture)

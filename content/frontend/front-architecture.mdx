> 2026년 11월 기준으로 다시 정리한 글이다.
> 웹의 탄생부터 지금(React 19 · Next.js 16 · Vite 8 · TypeScript 7)까지의 흐름과,
> 그 과정에서 바뀌어 온 프론트엔드 아키텍처, 그리고 앞으로의 방향을 다룬다.

## 1. 프론트엔드의 역사

한 줄로 요약하면 **"서버가 다 하던 시대 → 브라우저가 다 하는 시대 → 둘을 다시 섞는 시대"** 다.

| 시기      | 키워드                     | 화면은 누가 만드나        |
| --------- | -------------------------- | ------------------------- |
| 1990~2004 | 정적 문서, CGI·PHP         | 서버                      |
| 2005~2012 | Ajax, jQuery, 웹 표준      | 서버 + 브라우저 일부      |
| 2013~2019 | SPA, 컴포넌트, 번들러      | 브라우저(CSR)             |
| 2020~2024 | 메타 프레임워크, SSR 회귀  | 서버 + 브라우저(하이브리드) |
| 2025~     | 서버 컴포넌트, 컴파일러, AI | 상황에 따라 나눠서         |

---

### 1.1 Web 1.0 : 문서의 웹 (1990 ~ 2004)

- 1990, 팀 버너스리가 WWW를 만듦 (HTML, HTTP, URL)
- 1993, CGI(Common Gateway Interface) 등장 → 서버가 요청마다 HTML을 동적으로 생성
  - 이후 1995년 PHP, 1999년 JSP 등으로 이어짐
- 1994, 넷스케이프 내비게이터 출시
- 1995, 브렌던 아이크가 약 10일 만에 JavaScript를 만듦 (브라우저에서 동작 제어)
- 1996, CSS1 발표, Flash(당시 FutureSplash) 등장
- 1995~2001, 1차 브라우저 전쟁 → IE가 점유율 90% 이상을 차지하며 승리
- 1999, IE5에 `XMLHttpRequest`의 원형이 들어감 (나중에 Ajax의 기반)
- 2000~2001, 닷컴 버블 붕괴

이 시기의 웹은 **서버가 완성된 HTML을 내려주고, 브라우저는 보여주기만** 했다.
"프론트엔드 개발자"라는 직군은 없었고, 화면은 서버 개발자나 웹 디자이너(퍼블리셔)의 몫이었다.

---

### 1.2 Web 2.0 : Ajax와 프론트엔드의 탄생 (2005 ~ 2012)

- 2004, Gmail / 2005, Google Maps
  - 페이지 새로고침 없이 데이터를 주고받는 경험이 충격을 줌
  - 2005년 제시 제임스 개럿이 이 기법에 **Ajax(Asynchronous JavaScript and XML)** 라는 이름을 붙임
- 2004, 브라우저 제조사들이 WHATWG를 만들고 HTML5 작업 시작 (2014년 W3C 권고안)
- 2006, jQuery 등장 → 브라우저마다 다른 DOM API를 하나로 감싸 크로스 브라우징 문제를 해결
- 2008, 구글 크롬과 V8 엔진 출시 → JS 실행 속도가 비약적으로 빨라짐
- 2009, Node.js 등장 / 2010, npm 등장 → JS가 브라우저 밖으로 나옴
- 2010, 스티브 잡스의 "Thoughts on Flash" → 아이폰에서 Flash 미지원, 이후 HTML5로 대체
  - Flash는 2020년 12월 31일 공식 지원 종료
- 2010, Backbone.js(MVC), Knockout.js(MVVM), AngularJS 등장 → 브라우저에서 "앱"을 만들기 시작
- 2012, TypeScript, Webpack 등장

화면 로직이 브라우저로 넘어오면서 **백엔드와 프론트엔드의 전문성이 분리**되었고,
이때부터 프론트엔드 개발자라는 직군이 본격적으로 생겼다.

---

### 1.3 SPA와 컴포넌트의 시대 (2013 ~ 2019)

- 2013, 페이스북이 React 공개 → Virtual DOM, 단방향 데이터 흐름, JSX
- 2014, Vue.js 등장, 페이스북이 Flux 아키텍처 발표, Babel 등장
- 2015, ES2015(ES6) 표준화 → `class`, 모듈, `Promise`, 화살표 함수 등
- 2015, Redux, React Native 등장
- 2016, Angular(2+) 정식 출시 (AngularJS와 호환되지 않는 재작성), Svelte, Next.js, Nuxt 등장
- 2019, React Hooks(16.8) 발표 → 클래스 컴포넌트에서 함수 컴포넌트로 전환
- 2019, React Query(현 TanStack Query) 등장 → 서버 상태 관리 개념 확산

이 시기의 기본값은 **CSR(Client Side Rendering) 기반 SPA** 였다.
서버는 JSON API만 주고, 빈 HTML에 JS 번들을 내려받아 브라우저가 화면을 그린다.
대신 번들이 커지고, 첫 화면이 늦고, SEO가 어렵다는 문제가 쌓였다.

> React, Vue, Angular가 "3대장"으로 정착한 시기이며, 이후 판도는 지금까지도 React가 압도적이다.

---

### 1.4 서버로의 회귀 : 메타 프레임워크 (2020 ~ 2024)

SPA의 문제를 해결하려고, **다시 서버에서 HTML을 만들되 이후에는 SPA처럼 동작**시키는 쪽으로 돌아왔다.

- Next.js, Nuxt, SvelteKit, Remix, Astro 같은 **메타 프레임워크**가 표준이 됨
  - 라우팅, SSR/SSG/ISR, 데이터 페칭, 번들링을 한 번에 제공
  - 자세한 렌더링 방식은 [CSR, SSR, SSG](/frontend/nextjs/00-csr-ssr-ssg) 참고
- 2020, React 팀이 **React Server Components(RSC)** 를 처음 공개
- 2020~2021, Vite 등장 → 개발 서버에서 번들링을 생략(Native ESM)해 Webpack 대비 압도적으로 빠름
- 2022, Next.js 13 App Router 발표 → RSC를 실서비스에 처음 도입
- 2022, IE 공식 지원 종료 → 크로스 브라우징 부담이 크게 줄어듦
- 2023~, Signals 유행 : Angular, Preact, Solid, Svelte, Vue 등이 세밀한 반응성(fine-grained reactivity)을 채택
- 2024, React 19 정식 출시 → Server Components / Server Actions / `use` / Actions 정식화
- 2024, Svelte 5(Runes) 출시, Remix가 React Router v7로 합쳐짐

---

### 1.5 지금 (2025 ~ 2026)

- **React 생태계**
  - 2025, Create React App 공식 지원 종료(deprecated) → Vite나 프레임워크 사용 권장
  - 2025, Recoil 저장소 아카이브(개발 중단)
  - 2025, **React Compiler 1.0** → `useMemo`, `useCallback`, `memo`를 컴파일러가 자동으로 처리
  - 2025, React 19.2 → `<Activity>`, `useEffectEvent` 추가
  - 2025.12, RSC 관련 원격 코드 실행 취약점(CVE-2025-55182)이 공개되어 19.2.3에서 패치
    - 서버로 로직이 옮겨 갈수록 **프론트엔드도 서버 보안을 신경 써야 한다**는 걸 보여준 사건
  - 2026.02, **React Foundation** 이 리눅스 재단 아래 출범 → React, React Native, JSX가 메타 소유에서 벗어남
- **Next.js**
  - 2025.10, Next.js 16 → Turbopack이 기본 번들러, `use cache` 기반의 **Cache Components**(명시적 캐싱)
  - 2026, 16.x 업데이트에서 Cache Components를 모든 앱의 기본 선택으로 권장, Next.js 17에서 기본값이 될 예정
- **툴체인의 네이티브화 (Rust / Go)**
  - 2025, Tailwind CSS v4 → Rust 기반 엔진(Oxide), CSS 우선 설정
  - 2026.03, **Vite 8** → esbuild + Rollup을 Rust 기반 번들러 **Rolldown** 하나로 통합
  - 2026.07, **TypeScript 7** → 컴파일러를 Go로 재작성(Project Corsa), 약 10배 빨라짐
  - Biome, Oxlint 등 Rust 기반 린터/포매터가 ESLint·Prettier의 대안으로 자리 잡는 중
- **AI 코딩 도구의 일상화**
  - Cursor, Claude Code, v0 같은 도구로 UI 코드 생성이 일상이 됨
  - MCP(Model Context Protocol)로 AI가 디자인 도구, 브라우저, 저장소에 직접 접근

### 1.6 Web3는?

- 원래 "Web 3.0"은 팀 버너스리가 말한 **시맨틱 웹**(기계가 의미를 이해하는 웹)을 가리키는 말이었다.
- 2021년 무렵 유행한 "Web3"는 **블록체인 기반의 탈중앙화 웹**(e.g. 암호화폐, NFT, dApp)을 뜻한다.
- 2022년 이후 열기가 크게 식었고, 프론트엔드 실무에서는 일부 영역(지갑 연동 등)에 한정된 기술로 남았다.
- 지금 웹의 다음 변화로 더 자주 이야기되는 것은 블록체인보다 **AI 에이전트가 웹을 쓰는 방식**이다.

## 2. 프론트엔드 아키텍처의 역사

1. **HTML, CSS, JS의 탄생** : 관심사의 분리와 느슨한 결합
2. **jQuery 시대** : DOM을 쉽게 쓰자
3. **MVC 프레임워크** (2010~) : 브라우저에도 구조를 만들자
   - Backbone.js가 MVC 패턴을 브라우저에 도입
4. **MVVM 프레임워크** : 데이터 바인딩 + 템플릿
   - Knockout.js, AngularJS 등장으로 선언적 UI가 시작됨
   - 이후 React, Vue, Angular가 3대장으로 정착
5. **Container - Presenter 패턴** : 컴포넌트 간 데이터 교환이 너무 복잡
   - 데이터 조작을 다루는 `Container 컴포넌트`
   - 뷰를 보여주는 `Presenter 컴포넌트`
   - Container에서 props를 Presenter로 내려주면서 로직을 한 곳에 모음
6. **Flux 패턴과 Redux** (2014~) : Props Drilling 문제 대두
   - 상위 props를 하위로 전달하려면, 중간 컴포넌트가 쓰지도 않는 props를 계속 넘겨야 함
   - 그래서 View와 비즈니스 로직을 분리하고 **단방향 데이터 흐름**을 갖는 Flux 패턴이 등장
   - 이렇게 비즈니스 로직을 컴포넌트 밖에서 관리하는 도구를 **상태 관리(State Management)** 라고 부름
   - e.g. Redux, Vuex(Vue 진영), MobX(클래스 데코레이터로 더 쉽게 사용)
7. **Hooks와 Context, Atom 기반 상태 관리** (2019~) : Redux 너무 복잡하다, 쉽게 가자
   - Redux는 보일러플레이트(반복되는 상용구 코드)가 너무 많음
   - Hooks로 로직을 재사용하고, Context로 Props Drilling 없이 값을 전달
   - 작은 단위의 전역 상태(Atom)나 가벼운 Store를 쓰는 도구들이 등장
     - e.g. Recoil(2025년 아카이브), Jotai, Zustand
   - Redux 팀도 순수 Redux 대신 **Redux Toolkit** 을 공식 권장
8. **서버 상태 관리 도구** (2019~) : TanStack Query(React Query), SWR, RTK Query
   - 전역 상태가 커진 이유를 보니 대부분 **서버에서 받아 온 데이터**였음
   - 서버 데이터는 클라이언트가 "소유"하는 게 아니라 **캐시**하는 것이라고 보고 분리
   - 로딩, 캐싱, 무효화, 재요청 로직을 라이브러리가 처리
9. **서버 컴포넌트와 Server Actions** (2023~) : 데이터 페칭 자체를 서버로
   - 서버에서만 실행되는 컴포넌트가 DB/API에 바로 접근하고, 결과 UI만 브라우저로 보냄
   - 폼 제출 같은 변경도 Server Actions로 서버 함수를 직접 호출
   - 클라이언트 쪽 데이터 페칭 코드와 전역 상태가 크게 줄어듦
10. **Signals와 컴파일러** (2023~) : 다시 세밀한 반응성으로
    - 값이 바뀐 곳만 정확히 갱신(Signals) → Solid, Svelte 5 Runes, Angular Signals, Vue Vapor Mode
    - React는 Signals 대신 **React Compiler** 로 불필요한 리렌더링을 자동으로 제거하는 길을 택함
    - TC39에서 Signals를 JS 표준으로 넣자는 제안도 논의 중

### 2.1 프론트엔드에서 MV\* 아키텍처

1. **순수 MVC 아키텍처**
   - `Model(데이터)` : e.g. JS Object, 서버 API, DB
   - `View(화면)` : HTML, CSS
   - `Controller` : Model과 View 사이의 중간자
   - 초창기 웹은 DB를 Model, HTML/CSS/JS를 View,
     라우터를 통해 새 HTML을 보여주는 백엔드를 Controller로 취급 (e.g. PHP, JSP)
2. **jQuery MVC 아키텍처**
   - Ajax로 받는 데이터를 Model, HTML/CSS를 View로 보고
   - JS가 서버 데이터를 받아 이벤트를 처리하고 다시 서버로 보내는 Controller 역할
3. **MVVM 아키텍처**
   - jQuery의 문제점
     - 데이터를 찾고, 수정하고, 이벤트를 연결하는 반복 패턴
     - `{{ }}`, `<?= ?>`, `<%= %>` 같은 치환자를 써도, 바뀔 부분을 일일이 찾아 고쳐야 함
   - AngularJS(2010) 등이 **템플릿** 과 **바인딩** 개념을 대중화
   - Controller의 역할이 명령형 DOM 조작에서 템플릿과 바인딩을 통한 **선언적 방식** 으로 바뀜
   - Controller가 View를 그리는 Model만 다루게 되었다는 의미로 `ViewModel` 이라고 부름
   - React, Vue, Angular, Svelte 모두 템플릿과 바인딩을 쓰는 문법이 다를 뿐 큰 틀은 같음
4. **Flux 아키텍처**
   - MVC가 아닌 단방향 패턴 : `Action → Dispatcher → Store → View`
     - View(사용자 클릭)에서 Action(이벤트) 호출
     - Dispatcher가 Store에 전달해 데이터 보관
     - Store에서 다시 View로 전달
   - 대표 구현체 : Redux
   - 단점 : 보일러플레이트가 많아 문법이 장황하고 학습이 어려움
5. **MVI 아키텍처**
   - Flux의 Dispatch, Action, Update를 Observable 기반 **스트림** 으로 처리해 비동기 문제를 해결
   - iOS(SwiftUI), Android(Jetpack Compose) 진영에서도 비슷한 단방향 구조가 주류가 됨
6. **현대 아키텍처의 방향**
   1. **Context + Hooks** : Props Drilling만 문제라면 React 기본 기능으로 해결
   2. **Atomic / 가벼운 Store** : Zustand, Jotai, Vue Composition API, Svelte Runes
      - Action ~ Dispatch ~ Reducer 같은 복잡한 구조 제거
      - 컴포넌트 밖의 공통 데이터를 get/set 하면서 동기화
   3. **서버 상태 분리** : TanStack Query, SWR
      - Model : 서버 / View : React / Controller : query와 mutation
      - 캐싱, 동기화, refetch를 라이브러리가 관리
   4. **Schema 기반** : GraphQL, tRPC, OpenAPI 코드 생성
      - 스키마를 먼저 정의하고, 그 타입대로 서버-클라이언트가 통신
   5. **서버 우선(Server-first)** : RSC, Server Actions, Remix/React Router의 loader·action
      - 데이터 읽기와 쓰기를 서버로 옮기고, 클라이언트에는 상호작용이 필요한 부분만 남김

어떤 것이든 칼같이 딱 떨어지지 않는다.
만든 사람들이 서로를 보고 참고하며 계속 발전시키기 때문이다.
`MV*` 가 무엇이든, 결국 **Model과 View 사이를 무엇이 어떻게 조정하느냐** 의 문제다.

## 3. MVVM

### 3.1 MVVM 탄생

- 2004년 마틴 파울러, 프레젠테이션 모델(PM) 패턴 발표
  - 프레젠테이션 모델 = 뷰의 추상화
  - 뷰는 프레젠테이션 모델을 렌더링한 결과일 뿐
  - 프레젠테이션 모델은 뷰를 자주 업데이트해 동기화 상태를 유지
- 2005년 마이크로소프트의 존 고스먼(John Gossman), MVVM 패턴 발표
  - PM 패턴을 WPF, Silverlight 플랫폼에 맞게 특화시킨 것
  - 두 패턴 모두 뷰의 상태와 동작을 추상화

---

### 3.2 MVVM 소개

- 하나의 환경, 하나의 언어를 쓰던 과거와 달리, 다양한 도구·언어·사람이 함께 UI를 만드는 환경에 맞춘 MVC의 발전형
- 핵심 메커니즘은 **데이터 바인딩**

> 엔지니어가 디자이너에게 ViewModel만 넘기면, 디자이너가 코드를 작성하지 않고도 GUI를 구축할 수 있다고 가정한다.
> MVVM의 가장 큰 특성인 데이터 바인딩을 통해 이를 달성한다.

---

### 3.3 MVVM의 장점

- 독립적인 Model을 만들고, ViewModel이 어댑터 역할을 해 Model 코드의 간섭을 줄인다.
- View 없이 ViewModel과 Model만으로 단위 테스트를 만들 수 있다.
- 상태와 동작이 ViewModel에 있으므로 UI 수정이 유연하다.
- 디자이너와 개발자가 독립적으로, 동시에 작업할 수 있다.

---

### 3.4 MVVM 구조

![위키백과-MVVM](https://upload.wikimedia.org/wikipedia/commons/8/87/MVVMPattern.png)

> 💡 View → ViewModel → Model
>
> - `View`는 `ViewModel`을 알지만, `ViewModel`은 `View`를 알지 못한다.
> - `ViewModel`은 `Model`을 알지만, `Model`은 `ViewModel`을 알지 못한다.
>
> 이 구조로 **`ViewModel`과 `Model`이 `View`로부터 독립** 하고,
> **UI에서 비즈니스 로직과 프레젠테이션 로직을 분리** 할 수 있다.

사용 시나리오

1. 사용자가 `View`를 통해 요청한다.
2. `View`가 `ViewModel`에 요청을 전달한다.
3. `ViewModel`은 필요한 데이터를 `Model`에 요청한다.
4. `Model`이 데이터를 응답한다.
5. `ViewModel`이 응답 데이터를 가공해 저장한다.
6. `View`는 데이터 바인딩으로 `ViewModel`의 데이터를 즉시 전달받아 화면에 나타낸다.

---

#### 3.4.1 Model

- MVC의 Model과 같다.
- 앱 데이터를 저장하고, 도메인 처리와 유효성 검사를 수행하는, UI와 완전히 독립된 데이터·비즈니스 로직

#### 3.4.2 View

- 사용자에게 보이는 모든 UI 구성요소를 담당
- 선언적으로 정의되며, 단방향 혹은 양방향 데이터 바인딩으로 ViewModel에 연결된다.
  - `데이터 바인딩` : UI와 그 UI가 표시하는 데이터를 연결하는 것
  - `단방향 바인딩` : 데이터가 한 방향으로만 흐른다

#### 3.4.3 ViewModel

![마이크로소프트-MVVM](https://learn.microsoft.com/ko-kr/dotnet/architecture/maui/media/mvvm-pattern.png)

- View의 추상화이자, 말 그대로 **View를 위한 Model**

`View - ViewModel 관계`

- ViewModel은 View가 바인딩할 속성과 명령을 구현하고, 변경을 View에 알린다.
- ViewModel은 View를 알지 못하므로, 하나의 ViewModel을 여러 View에서 재사용할 수 있다. (1:N)
- ViewModel에서 버튼, 리스트 같은 View 타입을 직접 참조하면 안 된다. (강한 결합 발생)

`ViewModel - Model 관계`

- ViewModel은 Model 데이터를 View가 쓰기 쉬운 형태로 가공해 제공한다.
- Model은 ViewModel도 View도 알지 못하므로, View와 독립적으로 발전할 수 있다.

---

### 3.5 MVVM과 MVC의 차이

- MVC의 Controller는 입력을 받아 Model과 View를 **직접** 조작한다.
- MVVM의 ViewModel은 View를 모른 채 상태만 노출하고, View가 **바인딩으로** 알아서 따라간다.
- 즉, 추상화를 통해 프레젠테이션 로직을 View에서 분리한 것이 핵심 차이다.

## 4. 클라이언트 상태와 서버 상태의 분리

상태(state) = 컴포넌트의 메모리 (e.g. 팝업을 띄울지 말지, 주문·배달 진행 상황)

배달의민족 프론트엔드 팀이 소개한 방식이 지금도 가장 널리 쓰이는 기본 조합이다.

- **Client State** : 클라이언트가 소유하고 온전히 제어하는 상태 → `Zustand`
- **Server State** : 클라이언트 밖(서버)이 소유하고, 클라이언트는 캐시만 하는 상태 → `TanStack Query`

### 4.1 Zustand : 클라이언트 상태 관리

- 컴포넌트 밖에서도 상태 변경 가능
- 사용법이 단순해 러닝커브가 낮고, 코드량이 적음
- Redux DevTools 확장 프로그램 활용 가능

### 4.2 TanStack Query : 서버 상태 관리

- API 호출 코드로 비대해진 Store를 목적에 맞게 분리
- 훅 기반의 직관적인 사용법
- 캐싱, 재요청, 무효화, 낙관적 업데이트를 적은 코드로 처리
- 자체 개발도구 제공

### 4.3 서버 컴포넌트 시대에는?

- Next.js App Router처럼 RSC를 쓰면, **읽기 위주 데이터는 서버 컴포넌트에서 바로 가져오는** 경우가 많아졌다.
- 그래서 TanStack Query는 무한 스크롤, 폴링, 낙관적 업데이트처럼 **클라이언트에서 계속 바뀌는 데이터** 에 집중하고,
- 전역 클라이언트 상태도 URL(검색 파라미터)이나 폼 상태로 옮겨지면서 점점 작아지는 추세다.
- 정리하면 **"서버 데이터는 서버에서, 남는 것만 클라이언트에서"** 가 지금의 기본값이다.

## 5. FSD 폴더 아키텍처

- 과거 : Hooks 등장 전, `Container - Presenter` 패턴
- 이후 : Hooks 등장 후, 역할별 폴더 (`components`, `hooks`, `pages`, `utils`, `types` ...)
  - 프로젝트가 커지면 하나의 기능을 고치려고 여러 폴더를 오가야 하는 문제가 생김
- 그래서 **기능 단위로 폴더 규칙을 정한 것** 이 `기능 분할 설계(Feature-Sliced Design, FSD)` 다.

---

### 5.1 FSD 구조

![FSD 폴더 패턴](https://media.dev.to/cdn-cgi/image/width=800%2Cheight=%2Cfit=scale-down%2Cgravity=auto%2Cformat=auto/https%3A%2F%2Fdev-to-uploads.s3.amazonaws.com%2Fuploads%2Farticles%2Fvscch6q7ej44oxkwensa.jpg)

`레이어(Layer) > 슬라이스(Slice) > 세그먼트(Segment)` 3단계로 구성된다.

**Layer** (위에서 아래 순서, ✅는 핵심 레이어)

- `app` ✅ : 앱 초기화. 프로바이더, 라우터, 전역 스타일 등. 앱의 진입점
- `processes` ❌ : 여러 페이지에 걸친 프로세스(e.g. 단계별 회원가입). **공식적으로 deprecated** 이며 `features`나 `app`으로 옮기길 권장
- `pages` ✅ : 페이지
- `widgets` : 페이지에 들어가는 큰 독립 UI 블록
- `features` : 사용자에게 가치를 주는 **행동** (동사, e.g. 좋아요 누르기, 리뷰 작성)
- `entities` ✅ : 비즈니스 **엔티티** (명사, e.g. 사용자, 리뷰, 댓글)
- `shared` ✅ : 비즈니스에 종속되지 않는 재사용 코드 (UI 키트, API 클라이언트, 설정, 헬퍼)

핵심 규칙

- **위 레이어는 아래 레이어만 import 할 수 있다.**
  - e.g. `features`는 `entities`, `shared`를 import 가능하지만, 위의 `widgets`는 import 불가
- 같은 레이어의 다른 슬라이스끼리도 import 하지 않는다.
- `app`과 `shared`에는 슬라이스가 없고, 바로 세그먼트로 이어진다.
- 각 슬라이스는 `index` 파일(Public API)로만 밖에 공개한다.
  - index에서 export 한 것은 public, 나머지는 private → **캡슐화**

**Slice** : 레이어 안을 비즈니스 도메인으로 나눈 것 (e.g. `user`, `post`, `comment`)

- Redux Toolkit의 slice와 비슷한 개념

**Segment** : 슬라이스 안을 기술적 목적으로 나눈 것

- `ui` : 화면
- `model` : 상태, 비즈니스 로직
- `api` : 서버 통신 (fetch, axios, GraphQL)
- `lib` : 슬라이스 내부 유틸
- `config` : 설정, 상수

주의할 점

- 강제된 규칙이 아니라서 팀 전원이 이해하고 지키려는 의지가 있어야 한다.
- 다른 구조에 비해 진입장벽이 있고, 작은 프로젝트에는 과할 수 있다.
- Next.js App Router처럼 `app/` 폴더 이름을 프레임워크가 점유하는 경우, FSD의 `app`·`pages` 레이어와 이름이 겹치므로 별도 폴더(e.g. `src/`)로 분리해서 쓴다.
- 아토믹 디자인을 함께 쓰고 싶다면 `shared/ui` 안에서만 적용하는 식으로 섞을 수 있다.

## 6. 프론트엔드의 미래

### 6.1 서버와 클라이언트의 경계가 흐려진다

- CSR이냐 SSR이냐를 페이지 단위로 고르던 시대에서, **컴포넌트 단위로 어디서 실행할지 고르는** 시대로 왔다.
- 서버 컴포넌트, 스트리밍, 부분 사전 렌더링(PPR/Cache Components)이 한 페이지 안에서 섞인다.
- 프론트엔드 개발자가 캐싱, 인증, 데이터베이스 접근, **서버 보안** 까지 이해해야 하는 범위가 넓어졌다.

### 6.2 최적화는 컴파일러가 한다

- React Compiler가 메모이제이션을 자동화하고, Svelte·Vue Vapor·Solid는 컴파일 단계에서 필요한 갱신 코드만 만든다.
- 개발자가 `useMemo`를 어디에 넣을지 고민하던 시간은 줄고, **올바른 데이터 흐름을 설계하는 것** 이 더 중요해진다.

### 6.3 툴체인은 네이티브 언어로

- Vite 8(Rolldown), Turbopack, Biome, Oxlint, TypeScript 7까지, 빌드 도구의 핵심이 Rust·Go로 옮겨 갔다.
- 결과적으로 "빌드가 느려서" 생기던 복잡한 설정과 우회책이 사라지는 중이다.
- Vite 진영은 Vite·Vitest·Oxlint 등을 하나로 묶은 통합 툴체인(Vite+)도 준비하고 있다.

### 6.4 웹 플랫폼 자체가 강해진다

라이브러리로 해결하던 것들이 브라우저 기본 기능이 되고 있다.

- CSS : 컨테이너 쿼리, `:has()`, 네이티브 중첩(nesting), 앵커 포지셔닝, 스크롤 기반 애니메이션
- HTML : `<dialog>`, Popover API, 커스터마이즈 가능한 `<select>`
- JS : View Transitions API, Temporal(날짜/시간), Signals 표준화 논의
- [Baseline](https://web.dev/baseline)으로 "모든 주요 브라우저에서 쓸 수 있는지"를 쉽게 확인할 수 있다.

→ **라이브러리를 추가하기 전에 플랫폼 기능으로 되는지 먼저 확인하는 습관** 이 중요해졌다.

### 6.5 AI와 함께 일하는 프론트엔드

- 디자인 → 코드 변환, 컴포넌트 생성, 테스트 작성은 AI가 빠르게 초안을 만든다.
- 그만큼 사람의 역할은 **무엇을 만들지 정하고, 생성된 코드를 판단하고, 품질(접근성·성능·보안)을 책임지는 것** 으로 옮겨 간다.
- AI가 잘 다루는 것은 "많이 쓰이는 표준 기술"이라, React·TypeScript·Tailwind 같은 주류 스택 쏠림이 더 강해지는 경향도 있다.
- 사용자 쪽에서도 AI 에이전트가 웹을 대신 탐색하는 일이 늘면서, **시맨틱 HTML과 접근성** 이 사람뿐 아니라 기계를 위해서도 중요해졌다.

## 7. 프론트엔드 포지션에 대한 이해

일반적으로 프론트엔드가 하는 업무는 크게 4가지로 나눌 수 있다.

1. 데이터를 (예쁘게) 잘 보여주기
2. 데이터(화면)를 조작하기
3. 서버로 데이터를 보내기
4. 서버에서 받은 데이터를 다루기

회사나 프로젝트에 따라 사용자에 가까운 쪽을 맡느냐, 백엔드에 가까운 쪽을 맡느냐에 따라 주 업무의 모양새가 달라진다.

- 퍼블리셔는 대개 1~2의 영역을,
- 백엔드는 3~4의 영역을 다루는 것이 일반적인 견해다.

프론트엔드가 1~4를 혼자 다 하느냐 하면 꼭 그렇지는 않고, 사람마다 주력 포지션이 1~4 어딘가에 있다.
칼같이 구분할 수는 없지만 회사마다 경계선은 존재한다.
프론트엔드가 갑자기 튀어나온 게 아니라, 웹이 커지면서 기존 역할을 나누며 생겼기 때문이다.

> 최근에는 서버 컴포넌트와 BFF(Backend For Frontend) 덕분에 3~4의 영역이 다시 프론트엔드 쪽으로 넓어지고 있다.
> 1장에서 본 "서버 → 브라우저 → 다시 섞기" 흐름이 직무에도 그대로 나타나는 셈이다.

- `코딩만 잘하는 개발자 !== 잘하는 개발자`
- `(코딩 + 일정 관리 + 협업을 잘하는 개발자) === 잘하는 개발자`

프론트엔드의 기술적 가치는 안타깝게도 생각만큼 결정적이지 않을 때가 많다.
화면이 조금 덜 다듬어져도 사업은 돌아가기 때문이다.
그래서 일반적으로 일정을 잘 지키는 개발자가 좋은 개발자로 평가받고, 주니어를 벗어났는지 보는 주요 기준도 일정을 컨트롤할 수 있는지다.

그런데 `기획 → 디자인 → 백엔드 → 프론트엔드` 순서에서 프론트엔드는 다른 포지션과 협업이 가장 많고,
모든 작업의 마지막에서 마무리를 하기 때문에 일정 산출이 어렵다.
그래서 일정을 잘 산출하려면 다른 포지션에 대한 이해와 지식이 풍부해야 한다.

기획, 디자인, 백엔드, QA, UX, 사업, 사용자까지 협업 라인 전반의 지식을 쌓아야 한다.
또 소통 방식에는 말과 글이 있는데, 회사 규모가 커질수록 문서의 중요도가 높아진다.
말로 끝나면 시간이 지나 잊히고, 담당자가 퇴사하면 답이 없다.
문서를 잘 쓰는 것은 중요한 능력이고, 그래서 개발자 채용에서 블로그를 보는 것이다.

> AI가 코드를 빠르게 써 주는 지금은 이 이야기가 더 중요해졌다.
> 코드 작성 속도의 차이는 줄어들고, **요구사항을 정확히 글로 정리하고, 결과물을 판단하고, 사람들과 맞춰 가는 능력** 의 차이가 커진다.

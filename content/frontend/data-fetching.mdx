## 1. 왜 데이터 페칭 라이브러리가 필요할까?

`fetch` 하나로도 서버 데이터는 가져올 수 있다.
문제는 **실제 서비스에서 필요한 나머지 일들** 이다.

```tsx
// useEffect + fetch로 직접 구현하면...
function Posts() {
  const [posts, setPosts] = useState<Post[]>([])
  const [isLoading, setIsLoading] = useState(true)
  const [error, setError] = useState<Error | null>(null)

  useEffect(() => {
    let ignore = false // 경쟁 상태(race condition) 방지
    fetch('/api/posts')
      .then(res => {
        if (!res.ok) throw new Error(`요청 실패: ${res.status}`)
        return res.json()
      })
      .then(data => !ignore && setPosts(data))
      .catch(err => !ignore && setError(err))
      .finally(() => !ignore && setIsLoading(false))
    return () => {
      ignore = true
    }
  }, [])
  // ...
}
```

이렇게 직접 짜면 다음을 전부 손으로 처리해야 한다.

- 로딩 · 에러 상태 관리
- **캐싱** : 같은 데이터를 다른 화면에서 또 요청하지 않기
- **중복 요청 제거** : 여러 컴포넌트가 동시에 같은 API를 부를 때 한 번만 요청
- **최신화** : 탭으로 돌아오거나 네트워크가 다시 연결되면 다시 가져오기
- **경쟁 상태** : 느린 이전 요청의 응답이 최신 응답을 덮어쓰는 문제
- 데이터 변경(mutation) 후 관련 목록 **무효화와 재요청**
- 페이지네이션, 무한 스크롤, 낙관적 업데이트, 재시도

그래서 이 일들을 대신해 주는 **서버 상태(Server State) 관리 라이브러리** 가 등장했다.

> 💡 서버 상태 vs 클라이언트 상태
>
> - **클라이언트 상태** : 브라우저가 소유하고 완전히 통제하는 값 (e.g. 모달 열림 여부, 다크 모드)
> - **서버 상태** : 서버가 소유하고, 브라우저는 그 **복사본(캐시)** 을 들고 있을 뿐인 값 (e.g. 게시글 목록)
>   - 언제든 다른 사람이 바꿀 수 있으므로 "오래됐는지(stale)"를 관리해야 한다.
>
> 서버 상태를 Redux 같은 전역 스토어에 복사해 두던 방식이 복잡했던 이유가 바로 이것이다.

## 2. 2026년 데이터 페칭 도구 지형

| 분류                       | 도구                                                  | 한 줄 설명                                          |
| -------------------------- | ----------------------------------------------------- | --------------------------------------------------- |
| HTTP 클라이언트            | `fetch`, Axios, ky, ofetch                            | 요청을 보내는 도구 (캐싱 없음)                      |
| 서버 상태 관리             | **TanStack Query** ✅, SWR, RTK Query                 | 캐싱·동기화·재요청을 관리                           |
| GraphQL 클라이언트         | **Apollo Client** ✅, urql, Relay                     | GraphQL 요청 + 정규화 캐시                          |
| 타입 공유 / 코드 생성      | tRPC, openapi-typescript, Orval                       | 서버 API 타입을 클라이언트에서 그대로 사용          |
| 프레임워크 내장            | React 서버 컴포넌트, Next.js `use cache`, React Router loader, SvelteKit `load`, Nuxt `useFetch` | 프레임워크가 서버에서 데이터를 가져와 렌더링 |

- 이 도구들은 서로 **경쟁 관계라기보다 층(layer)이 다르다.**
  - e.g. `TanStack Query`가 캐싱을 맡고, 실제 요청은 `fetch`나 Axios가 한다.
  - e.g. Next.js에서 첫 화면 데이터는 서버 컴포넌트로, 이후 상호작용 데이터는 TanStack Query로 가져온다.

다운로드 추이 비교 : [npm trends](https://npmtrends.com/@apollo/client-vs-@tanstack/react-query-vs-swr-vs-axios-vs-ky)

### 2.1 HTTP 클라이언트

| 도구      | 특징                                                                                   |
| --------- | -------------------------------------------------------------------------------------- |
| `fetch`   | 브라우저·Node.js 표준 내장. 추가 설치가 필요 없고, Next.js 캐싱과도 연동 ✅ 기본값      |
| Axios     | 인터셉터, 자동 JSON 변환, 4xx/5xx 에러 자동 throw. 여전히 가장 많이 설치되는 라이브러리 |
| ky        | `fetch` 위의 얇은 래퍼. 재시도, 타임아웃, 훅(인터셉터) 제공, 아주 가벼움                |
| ofetch    | Nuxt 진영에서 만든 `fetch` 래퍼. 서버·브라우저·엣지에서 동일하게 동작                   |

`fetch`를 쓸 때 주의할 점

- **404, 500 응답에도 reject하지 않는다.** → `response.ok`를 직접 확인
- 타임아웃이 기본으로 없다. → `AbortSignal.timeout(5000)`
- 요청 취소는 `AbortController`

```ts
// 프로젝트에서 공통으로 쓰는 fetch 래퍼 예시
export async function api<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`${import.meta.env.VITE_API_URL}${path}`, {
    ...init,
    headers: { 'Content-Type': 'application/json', ...init?.headers },
    signal: init?.signal ?? AbortSignal.timeout(10_000),
  })
  if (!res.ok) throw new Error(`API ${res.status}: ${path}`)
  return res.json() as Promise<T>
}
```

> 새 프로젝트라면 `fetch`(+ 얇은 래퍼)로 시작하고, 인터셉터가 많이 필요해지면 ky나 Axios를 고려하면 된다.

### 2.2 서버 상태 관리 라이브러리

| 도구               | 특징                                                                                           | 추천 상황                     |
| ------------------ | ---------------------------------------------------------------------------------------------- | ----------------------------- |
| **TanStack Query** | 가장 기능이 많고 널리 쓰임. React·Vue·Svelte·Solid·Angular 지원, 전용 DevTools                  | 대부분의 경우 ✅              |
| SWR                | Vercel 제작. API가 단순하고 가벼움. "stale-while-revalidate" 전략                              | 조회 위주의 단순한 앱         |
| RTK Query          | Redux Toolkit에 포함. API를 한 곳에 정의하면 훅이 자동 생성됨                                  | 이미 Redux를 쓰는 프로젝트    |

- TanStack Query는 2026년 현재 React용은 **v5** 가 최신 메이저다. (Svelte·Solid 바인딩은 v6가 진행 중)
- 세 라이브러리 모두 핵심 개념은 같다 : **쿼리 키(캐시 키)** 로 데이터를 저장하고, **변경(mutation) 후 관련 키를 무효화** 한다.

자세한 사용법은 [TanStack Query](/frontend/tanstack-query/00-summary) 참고

### 2.3 GraphQL 클라이언트

| 도구          | 특징                                                                                   |
| ------------- | -------------------------------------------------------------------------------------- |
| Apollo Client | 가장 대중적. **정규화 캐시** 로 같은 객체를 여러 쿼리가 공유. 2025년 9월 v4 출시      |
| urql          | 가볍고 단순. 필요한 기능을 exchange(플러그인)로 추가                                   |
| Relay         | 메타 제작. 컴포넌트마다 필요한 데이터를 fragment로 선언, 대규모 앱에 강하지만 학습 비용 큼 |

- Apollo Client 4 : 번들 크기 감소, 로컬 상태 관리 opt-in, 에러 타입 세분화, 더 엄격한 TS 타입, RxJS 기반
- GraphQL이라도 단순한 앱이라면 `graphql-request` + TanStack Query 조합으로도 충분하다.

cf. [Apollo Client](/frontend/apollo-client/apollo)

### 2.4 타입 공유와 코드 생성

프론트엔드에서 API 응답 타입을 손으로 작성하면, 서버가 바뀌었을 때 **런타임에야** 깨진 걸 알게 된다.
그래서 서버의 명세(스키마)에서 타입을 자동으로 가져오는 방식이 기본이 되었다.

- **OpenAPI(Swagger) 기반** : 백엔드가 OpenAPI 명세를 제공하면
  - `openapi-typescript` + `openapi-fetch` : 타입과 타입 안전한 fetch 클라이언트 생성
  - `Orval` : TanStack Query 훅까지 자동 생성
- **GraphQL** : GraphQL Code Generator, gql.tada로 쿼리마다 정확한 타입 생성
- **tRPC** : 서버와 클라이언트가 모두 TS일 때, 서버 함수의 타입을 **코드 생성 없이** 그대로 공유
- **런타임 검증** : TS 타입은 실행 시점에 사라지므로, 외부 API처럼 믿을 수 없는 응답은 **Zod** 등으로 한 번 더 검증

### 2.5 프레임워크 내장 데이터 페칭

메타 프레임워크를 쓰면 **서버에서 데이터를 가져와 HTML과 함께 보내는 것** 이 기본이다.

React 서버 컴포넌트 (Next.js App Router)

```tsx
// app/posts/page.tsx — 서버에서만 실행된다
export default async function PostsPage() {
  const posts = await db.post.findMany() // DB나 내부 API에 바로 접근 가능
  return <PostList posts={posts} />
}
```

- 로딩 상태, 캐싱, 클라이언트 번들 걱정 없이 `async/await` 그대로 사용
- Next.js 16에서는 `'use cache'` 지시어로 **명시적으로** 캐싱한다 (Cache Components)
- 데이터 변경은 **Server Actions** 로 서버 함수를 호출하고, `revalidatePath` / `updateTag` 등으로 캐시 갱신

React 19의 `use`

```tsx
// 서버 컴포넌트에서 Promise를 만들어 넘기고, 클라이언트 컴포넌트에서 기다린다
'use client'
import { use } from 'react'

export function Comments({ commentsPromise }: { commentsPromise: Promise<Comment[]> }) {
  const comments = use(commentsPromise) // Suspense가 로딩을 처리
  return comments.map(c => <p key={c.id}>{c.text}</p>)
}
```

다른 프레임워크

- React Router(구 Remix) : 라우트마다 `loader`(읽기) · `action`(쓰기)
- SvelteKit : `load` 함수 / Nuxt : `useFetch`, `useAsyncData`

cf. [Next.js 데이터 페칭](/frontend/nextjs/02-data-fetching/01-fetching-caching-revalidating), [Server Actions](/frontend/nextjs/02-data-fetching/02-server-actions-mutations)

## 3. 어떤 걸 골라야 할까?

```
서버 컴포넌트를 쓰는 프레임워크(Next.js App Router 등)인가?
├─ YES → 첫 화면 데이터는 서버 컴포넌트에서 직접 가져오기
│        ├─ 쓰기(폼 제출 등)는 Server Actions
│        └─ 무한 스크롤·폴링·낙관적 업데이트처럼 클라이언트에서 계속 바뀌는 데이터 → TanStack Query 추가
└─ NO (Vite + React SPA 등)
   ├─ API가 GraphQL → Apollo Client (단순하면 urql)
   ├─ 이미 Redux Toolkit을 사용 → RTK Query
   └─ 그 외 → TanStack Query ✅
        └─ 백엔드가 OpenAPI 명세를 준다 → Orval / openapi-typescript로 타입·훅 자동 생성
```

## 4. 알아 두면 좋은 데이터 페칭 패턴

### 4.1 워터폴(Waterfall) 피하기

서로 의존하지 않는 요청을 **순서대로** 기다리면 시간이 합산된다.

```ts
// ❌ 순차 실행 : 1초 + 1초 = 2초
const user = await getUser()
const posts = await getPosts()

// ✅ 병렬 실행 : 약 1초
const [user, posts] = await Promise.all([getUser(), getPosts()])
```

- 컴포넌트 트리에서도 부모가 데이터를 받아야 자식이 요청을 시작하는 구조면 워터폴이 생긴다.
- 해결 : 라우트 단위로 미리 가져오기(prefetch), 서버 컴포넌트에서 병렬로 시작하기, TanStack Query의 `useQueries`·`prefetchQuery`

### 4.2 Suspense와 에러 바운더리

- 로딩·에러 처리를 컴포넌트 안에서 `if (isLoading)`으로 하지 않고, 바깥의 `<Suspense>`·`<ErrorBoundary>`에 맡기는 방식
- TanStack Query의 `useSuspenseQuery`, React 19의 `use`, 서버 컴포넌트 스트리밍이 모두 이 방식이다.

### 4.3 낙관적 업데이트(Optimistic Update)

- 서버 응답을 기다리지 않고 **성공했다고 가정하고 먼저 화면을 바꾼 뒤**, 실패하면 되돌리는 방식
- e.g. 좋아요 버튼 → 누르는 즉시 하트가 채워짐
- 도구 : TanStack Query의 `onMutate`, React 19의 `useOptimistic`

### 4.4 그 밖에

- **무한 스크롤** : `useInfiniteQuery` + Intersection Observer
- **요청 취소** : 검색어를 빠르게 바꿀 때 이전 요청은 `AbortController`로 취소 (TanStack Query는 `signal`을 자동 전달)
- **실시간 데이터** : 짧은 주기 폴링(`refetchInterval`), 서버 푸시(SSE, 웹소켓)를 받아 캐시 갱신

## 5. API

- **API (Application Programming Interface)** : 서로 다른 프로그램이 소통할 수 있게 정한 약속(인터페이스)
  - 웹에서는 "**클라이언트가 서버에 어떻게 요청하면 어떤 데이터를 받는지**"에 대한 약속
- e.g. "누군가 `/write`로 접속하면 `write.html`을 보내 준다"도 서버의 API다.

> 💡 서버(Server) = 알바생
>
> - **요청을 받으면 데이터를 갖다주는 컴퓨터(프로그램)**
> - (음식을) 서빙(Serving)한다 = 무언가를 갖다준다 → 서버(Server) = 무언가를 갖다주는 컴퓨터
> - e.g. 웹 서버 = "웹툰 페이지 주세요" 하면 웹툰 페이지를 가져다주는 기계

> 💡 GET 요청 = 읽기 요청
>
> - 브라우저 주소창에 URL을 입력하는 것 자체가 GET 요청이다.

## 6. REST API

- `REST(Representational State Transfer)`
- HTTP 명세 작성에 참여한 **로이 필딩(Roy Fielding)** 이 2000년 박사 논문에서 소개
- "웹의 장점(HTTP)을 최대한 활용하는 아키텍처 스타일"로, 특정 기술이 아닌 **설계 원칙** 이다.
- **자원(URL) + 행위(HTTP 메서드) + 표현(JSON 등)** 으로 API를 구성
- cf. [그런 REST API로 괜찮은가](https://youtu.be/RP_f5dMoHFc)
- cf. REST 이전에는 XML 기반의 SOAP를 많이 썼다.

---

### 6.1 REST 6가지 제약 조건

#### 6.1.1 Uniform Interface (일관된 인터페이스) ⭐

- **하나의 URL은 하나의 자원** 을 가리킨다. (같은 자원에 URL을 두 개 만들지 말자)
- **간결하고 예측 가능하게** (URL 하나를 알면 다른 것도 짐작할 수 있게)
- URL 이름 짓기 관습을 따른다 (6.2)
- 원래 논문에는 응답 안에 다음 행동 링크를 담는 **HATEOAS** 도 포함되지만, 실무에서 완전히 지키는 API는 드물다.

> 💡 URI와 URL
>
> - `URI(Uniform Resource Identifier)` : 자원을 **식별** 하는 문자열 전체를 가리키는 큰 개념
> - `URL(Uniform Resource Locator)` : URI 중에서 자원의 **위치(어디서 어떻게 가져오는지)** 를 나타내는 것
> - 즉, **URL ⊂ URI** 다. 웹에서 쓰는 주소는 대부분 URL이라 둘을 섞어 부르기도 한다.

#### 6.1.2 Client-Server (역할 분리)

- 클라이언트는 URL만 알면 서버 자원을 쓸 수 있다.
- 클라이언트에게 서버 역할을 맡기거나, DB에 직접 접근하게 하면 안 된다.
- 덕분에 프론트엔드와 백엔드가 **독립적으로 개발·배포** 될 수 있다.

#### 6.1.3 Stateless (무상태)

- **요청은 각각 독립적으로 처리** 된다. 서버는 이전 요청을 기억하지 않는다.
- 요청 하나만으로 처리할 수 있게, **필요한 정보(e.g. 인증 토큰)를 매 요청에 담아** 보낸다.

#### 6.1.4 Cacheable (캐시 가능)

- 응답은 **캐시 가능한지, 얼마나 캐시할지** 를 표시해야 한다. (`Cache-Control`, `ETag` 헤더)

> 💡 캐싱(Caching)
>
> 자주 쓰는 파일(로고, CSS 등)을 가까운 곳에 저장해 두고, 서버에 다시 요청하지 않고 꺼내 쓰는 것.
> 서버 상태 라이브러리의 캐시도 같은 아이디어를 **API 응답 데이터** 에 적용한 것이다.

#### 6.1.5 Layered System (계층 구조)

- 클라이언트와 서버 사이에 로드 밸런서, 캐시 서버(CDN), API 게이트웨이 같은 **여러 계층을 둘 수 있다.**
- 클라이언트는 중간 계층이 있는지 몰라도 된다.

#### 6.1.6 Code on Demand (선택)

- 서버가 **실행 가능한 코드(e.g. JS)를 보내 줄 수 있다.** 6가지 중 유일한 선택 사항이다.

---

### 6.2 좋은 URL 이름 짓기 관습

```
GET    /posts           게시글 목록
GET    /posts/42        42번 게시글
POST   /posts           게시글 작성
PATCH  /posts/42        42번 게시글 일부 수정
DELETE /posts/42        42번 게시글 삭제
GET    /posts/42/comments   42번 게시글의 댓글 목록
GET    /posts?page=2&sort=latest   필터·정렬·페이지는 쿼리 스트링으로
```

- 동사보다 **명사(복수형)** 로 자원을 표현하고, 행위는 HTTP 메서드로 표현 (`/getPosts` ❌)
- 일관성이 있어 하나를 보면 다른 것도 예측 가능해야 함
- 띄어쓰기는 언더바(`_`) 대신 **대시(`-`)**, 소문자 사용
- 파일 확장자(`.html`, `.json`)는 쓰지 않기
- 계층 관계는 `/`로 표현

---

### 6.3 HTTP 메서드

메서드 자체가 용도를 강제하지는 않는다. POST 하나로 조회·수정·삭제를 다 할 수도 있지만,
**RESTful하게 만들려면 의도에 맞게 구분해서 사용** 해야 한다.

| 메서드   | 용도               | Body | 멱등성 |
| -------- | ------------------ | ---- | ------ |
| `GET`    | 조회(Read)         | ❌   | ✅     |
| `POST`   | 생성(Create)       | ✅   | ❌     |
| `PUT`    | 전체 교체(Update)  | ✅   | ✅     |
| `PATCH`  | 일부 수정(Update)  | ✅   | ❌(보통) |
| `DELETE` | 삭제(Delete)       | -    | ✅     |

- `PUT`은 자원 **전체를** 보낸 값으로 교체, `PATCH`는 **보낸 필드만** 변경

## 7. REST API의 한계

### 7.1 Over-Fetching

- **필요한 것보다 많은 데이터** 를 받는 것
  - e.g. 목록 화면에 `title`만 필요한데 `id, title, content, author, tags...`를 전부 받음
- 네트워크 낭비, 특히 모바일에서 느려짐
- 화면마다 필요한 필드 조합을 모두 고려해 API를 만들기도 어렵다.

### 7.2 Under-Fetching

- 한 화면에 필요한 데이터를 얻으려면 **여러 번 요청** 해야 하는 것
  - e.g. 게시글 + 작성자 정보 + 댓글 → API 3번 호출
- 요청 횟수가 늘고, 받은 결과를 조합하는 코드가 필요

### 7.3 API마다 다른 엔드포인트

- 만드는 쪽은 API마다 이름(URL)을 지어야 하고, 쓰는 쪽은 계속 문서를 확인해야 한다.
- → OpenAPI 명세 + 코드 생성(2.4)으로 상당 부분 완화할 수 있다.

> 이런 한계를 해결하는 방법으로 **GraphQL**, 그리고 프론트엔드용 API를 따로 두는 **BFF(Backend For Frontend)** 패턴이 쓰인다.
> 서버 컴포넌트도 서버에서 여러 API를 모아 필요한 것만 내려준다는 점에서 BFF와 비슷한 역할을 한다.

## 8. GraphQL

REST의 한계를 해결하려고 페이스북(현 메타)이 2012년 내부에서 만들고 2015년 공개한
**API를 위한 쿼리 언어이자 런타임** 이다.

- **클라이언트가 원하는 데이터의 모양을 직접 정해서 요청** 한다.
- 엔드포인트가 보통 `/graphql` **하나** 뿐이다.
- 한 번의 요청으로 화면에 필요한 데이터를 정확히 가져온다. → Over/Under-Fetching 해결
- **스키마(타입 시스템)** 가 있어서 API 자체가 문서가 되고, TS 타입을 자동 생성하기 좋다.
- cf. SQL처럼 "쿼리 언어"라는 이름이 붙었지만, **DB를 조회하는 언어가 아니라 API 요청을 위한 언어** 다. 데이터가 DB에 있든 다른 REST API에 있든 상관없다.

```graphql
query {
  post(id: 42) {
    title
    author {
      name
    }
    comments(first: 3) {
      text
    }
  }
}
```

### 8.1 Operation type

- `Query` : 데이터 조회
- `Mutation` : 데이터 변경
- `Subscription` : 실시간 데이터 수신 (주로 웹소켓)

### 8.2 GraphQL의 단점

- HTTP 캐시(CDN 등)를 그대로 활용하기 어렵다. (대부분 POST 한 곳으로 요청하므로)
- 클라이언트가 지나치게 복잡한 쿼리를 보내면 서버 부담이 커진다. (쿼리 깊이·비용 제한 필요)
- 서버 구현과 클라이언트 캐시(정규화)의 학습 비용이 있다.
- 단순한 CRUD 앱에는 과할 수 있다.

### 8.3 GraphQL 학습 자료

- [GraphQL 공식](https://graphql.org/), [GraphQL 한국어 문서](https://graphql-kr.github.io/learn/)
- GraphiQL, Apollo Sandbox 같은 브라우저 도구로 스키마를 탐색하고 쿼리를 바로 실행해 볼 수 있다.
- cf. [얄팍한 GraphQL & Apollo 강좌](https://youtu.be/9BIXcXHsj0A)

## 9. REST vs GraphQL vs tRPC 정리

|                    | REST                     | GraphQL                         | tRPC                               |
| ------------------ | ------------------------ | ------------------------------- | ---------------------------------- |
| 엔드포인트         | 자원마다 여러 개         | 보통 하나                       | 함수(프로시저)마다                 |
| 응답 모양 결정     | 서버                     | 클라이언트                      | 서버 함수의 반환 타입              |
| 타입 공유          | OpenAPI + 코드 생성      | 스키마 + 코드 생성              | 코드 생성 없이 TS로 직접 공유      |
| HTTP 캐시 활용     | 쉬움                     | 어려움                          | 보통                               |
| 잘 맞는 경우       | 공개 API, 대부분의 서비스 | 화면이 다양하고 데이터 관계가 복잡한 서비스 | 프론트·백엔드 모두 TS인 풀스택 프로젝트 |

- 정답은 없다. **API의 사용자(공개 API인지, 우리 프론트엔드 전용인지)와 팀 구성** 에 맞춰 고르면 된다.
- 한 서비스에서 섞어 쓰는 것도 흔하다. (e.g. 외부 공개는 REST, 내부 화면은 GraphQL)
